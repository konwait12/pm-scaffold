01主程序流程 每个判断有条件

从「需求输入」到「交付 prd.md」的主链路。每个 work_item 输出独立产物文件，前置确认才解锁下一步。

028 步执行循环 每个 work_item 必走

机器止步于 ready_for_human_review，人工确认后变 confirmed。状态机不可绕过。

  1. Preflight：DoR 检查（≥1 个 SRC 材料、领域路由判定）
  2. Intake：成熟度判定 L0–L4，决定进入条件
  3. Think：调用 thinking-core 6 个核心透镜
  4. Clarify：缺口问题进 issue-record，循环直到无 UNKNOWN 阻塞
  5. Generate：填模板 → 写出独立产物文件
  6. Audit：本地校验器 + 一致性检查
  7. Human Gate：写 ready_for_human_review，永远不能写 confirmed
  8. Commit / Reflow：confirmed 后进入下一 work_item；变更触发级联失效

状态机：draft → ready_for_human_review → confirmed （needs_user_input / conditional_review 为中间态；superseded / simulated 为特殊态）

03六态知识标注 证据与不确定性必须可见

每条声明必须标知识状态。AI 不得把推断当事实、忽略冲突、漏掉未知。

标签语义典型场景
FACT有源可查的客观事实用户原话、邮件原文、API 文档
DECISION已达成的人为决策采纳/拒绝某方案的会议结论
ASSUMPTION为推进而做的假设目标用户规模、性能基线
AI_INFERENCEAI 推断（非事实）从已确认信息演绎出的二级结论
UNKNOWN不知道，需要澄清缺少业务规则、字段定义
CONFLICT来源说法矛盾不同 stakeholder 对同一问题不同答案

10命令全集 pipeline.py 一条命令链

唯一入口 python3 src/scripts/pipeline.py，所有操作经此。

# 1. 创建新需求骨架
python3 src/scripts/pipeline.py init REQ-NNN-topic-name

# 2. 把输入材料放进 requirements/REQ-NNN-topic-name/00-input/

# 3. 查状态（active / next / 越级检测）
python3 src/scripts/pipeline.py requirements/REQ-NNN-topic status

# 4. 跑机器闸门（不改状态，只校验）
python3 src/scripts/pipeline.py requirements/REQ-NNN-topic gate \
  --work-item project-background-goal

# 5. 人工确认（带真实姓名 + reviewer-id）
python3 src/scripts/pipeline.py requirements/REQ-NNN-topic review \
  --work-item project-background-goal --decision approve \
  --reviewer "评审人姓名" --reviewer-id "USR-XXX" \
  --reviewer-role "business_owner"

# 6. 变更回流 / 级联失效
python3 src/scripts/pipeline.py requirements/REQ-NNN-topic reflow \
  --work-item project-background-goal --apply

# 7. 全量自检
bash run_tests_mac.sh
python3 src/scripts/consistency_check.py

128 条硬宪法 违反即缺陷

来自 src/framework/constitution.md。每条都有自动化检查或人工闸门强制。

§1
confirmed 永远不能由 AI 设置——只有 pipeline.py review --decision approve（带真实人名 + 授权清单匹配）才能产生。
§2
上游未 confirmed，下游不启动——orchestrator 检测越级并阻止。
§3
PRD assembly 只聚合、不发明——发现缺口路由回最早的 Work Item 重来。
§4
知识状态必须标注——FACT / DECISION / ASSUMPTION / AI_INFERENCE / UNKNOWN / CONFLICT，不得把推断当事实。
§5
产物单点存放——一个 artifact 一个位置，版本演进用 v0.* 快照，不在别处复制。
§6
变更已确认内容使下游失效——回归到最早受影响的 Work Item 重跑。
§7
注册表是唯一真相源——workflow-registry.json 唯一；禁止硬编码路径 / 阶段名 / Skill 名。
§8
事件日志不可篡改 + 校验器统一错误格式——.audit/events.jsonl append-only；prev_hash 链断即 CRITICAL；所有校验器必须用 validation_errors.make_issue 输出。

📖 新手教程 · 从这里开始

这个项目是什么

PM Scaffold 是一个 PRD-only 产品经理 AI 脚手架：把原始需求（BRD、会议纪要、邮件、PPT、图片）逐步转化为一份经真实人工确认的中文 prd.md。

三条硬哲学：业务真相由人类拥有、证据与不确定性必须可见、AI 不得伪造人工确认。

10 步上手剧本

  • 第 1 步：打开驾驶舱（本页面），从左侧导航跳到任一章节了解全貌。
  • 第 2 步：阅读 AGENTS.md（项目唯一入口文件），理解 AI Agent 如何启动。
  • 第 3 步：按顺序读 src/framework/ 的 5 个核心文件（registry / constitution / workflow / thinking-core / contracts）。
  • 第 4 步：跑 bash run_tests_mac.sh 看 78 项测试基线，确认环境正确。
  • 第 5 步：用 python3 src/scripts/pipeline.py init REQ-001-your-topic 创建第一个需求骨架。
  • 第 6 步：把原始材料放进 00-input/，登记 authorized-reviewers.json。
  • 第 7 步：让 AI 按 8 步循环跑 project-background-goal → user-journey → … → prd-assembly。
  • 第 8 步：每个 work_item 完成后用 pipeline.py gate 跑机器闸门。
  • 第 9 步：人工 review：用 pipeline.py review --decision approve --reviewer "姓名" --reviewer-id "USR-XXX" 写 confirmed。
  • 第 10 步：所有 12 上游 confirmed 后 prd-assembly 自动可启动。

三条红线

  • 不要伪造 confirmed：AI 永远不能写 status: confirmed（宪法第 1 条）。
  • 不要硬编码路径：所有 skill 路径从 workflow-registry.json 读（宪法第 7 条）。
  • 不要跳过知识状态标注：每条声明必须标 FACT / DECISION / UNKNOWN 等（宪法第 4 条）。
