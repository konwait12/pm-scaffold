# 隐性痛点与情绪信号识别（Latent Pain Signal）

> 本文将相关实践转化为本项目的可选方法，不引入外部运行时依赖。
>
> **定位**：很多 stakeholder 不会直接说出"我痛在哪里"——他们只说"想要 X"（W 诉求型）或"觉得 Y 不太好"（O 意见型）。AI 经常跳过 O 型信号直接抄 W，结果 PRD 解决的是 stakeholder 提的方案，而不是 stakeholder 真实的痛点。本技法把这些"沉默的声音"显式化。
>
> **触发**：RR Intake 时遇到以下信号——
> - stakeholder 说"想要 X"但不解释为什么（典型 W 型）
> - stakeholder 说"以前我们试过 X 不行"（典型 O 型）
> - stakeholder 沉默 / 表情凝重 / 反复皱眉
> - 团队内部"大家都觉得这个有问题"但没人提
>
> **按需加载，不设全局闸门。**

## 2. 4 类隐性信号

### 信号 1：沉默信号（Silence Signal）

stakeholder **该说话但没说话**——沉默本身是信息。

| 场景 | 推断 |
|---|---|
| 通知开会没人回 | 可能是有意放弃 / 等别人先表态 |
| 评审时所有人沉默 | 没人反对 ≠ 全员通过 |
| stakeholder 私下说"我不方便说" | 必有顾虑 / 政治原因 |
| 之前提过的问题突然不问了 | 已绕过 / 已被其他人处理 / 已放弃 |

**处理**：
- 标 INF 类（信息缺口），target_close 7 天
- 7 天未升级，14 天升级到 stakeholder 上级

### 信号 2：情绪信号（Emotion Signal）

stakeholder **说话时带情绪**——情绪强度反映真实痛点。

| 情绪 | 推断 |
|---|---|
| "我每天都因为这个加班" | 高频痛点，可能是 V1 高价值 |
| "老板上次因为这个骂我了" | 政治痛点，必做 |
| "客户打电话过来骂我们" | 客户痛点，必做 |
| "我不在乎这个" | 低优先级候选 |
| "这个我们以后再说" | 已被推迟，可能有更深顾虑 |

**处理**：
- 标 RR-XXX 的情绪强度字段
- 把情绪 → 实际痛点 → 业务结果的转化写进 RR §stakeholder 自查反馈位
- 不要只抄 stakeholder 提的方案，要追问"为什么"

### 信号 3：迂回信号（Evasive Signal）

stakeholder **绕弯说话**——绕的内容是关键。

| 说话方式 | 推断 |
|---|---|
| "这个……嗯……其实" | 接下来是关键 / 顾虑 |
| "我不是说 X 不好，但……" | 实际是 X 不好 |
| "老板说要这么干" | 自己不一定认可 |
| "你看怎么合适就怎么干吧" | 自己不担责，让 AI 决定 |
| 反复用"我们"代替"我" | 团队共识但个人有保留 |

**处理**：
- 追问"你说的'我们'具体是谁？"
- "老板说要"——追问"你自己觉得呢？"
- "你看怎么合适"——AI 不替决策；标 GR 灰信号二次询问

### 信号 4：沉默多数信号（Silent Majority）

**多人评审时只有少数人发言**——沉默的多数人可能有不同意见。

| 场景 | 推断 |
|---|---|
| 评审时 3 人发言，5 人沉默 | 沉默的人未必同意 |
| 群里 @ 所有人只有 1 人回 | 其他人不知道 / 不想参与 / 等别人先说 |
| 老板说"大家都同意吧？"没人反对 | 没人反对 ≠ 全员通过 |

**处理**：
- 标 INF 类，target_close 7 天
- 二次询问时显式点名沉默者（"X 同学你怎么看？"）
- 不能用"沉默 = 同意"的默认假设

## 3. 应对 12 类典型追问

### 追问 1："stakeholder 说'想要 X'，但 X 看起来不像痛点，怎么办？"
**答**：追问"为什么想要 X？"——W 诉求型背后必有痛点。例："想要自动报表" → 追问 → "因为每周花 4 小时做报表" → 痛点是"重复劳动 4h/周"。

### 追问 2："stakeholder 沉默 7 天，怎么办？"
**答**：标 INF + 二次询问。仍沉默 → 标 `implicit_disagreement` + 升级到上级。

### 追问 3："stakeholder 说'我不在乎这个'，但业务上要做，怎么办？"
**答**：stakeholder 的优先级 ≠ 业务优先级。追问"为什么不在乎？"——可能 stakeholder 没看到全局影响。让 stakeholder 自己判断。

### 追问 4："老板私下说要这么干，但群里没明确说，怎么办？"
**答**：私下口头承诺标 ASSUMPTION，要求 stakeholder 在正式渠道（邮件/工单）确认。AI 不把私下口头当正式决策。

### 追问 5："团队里有几个老员工一直抱怨新功能，但他们不直接说，怎么办？"
**答**：标 O 意见型——"老员工抱怨"是 latent signal。1v1 访谈收集具体场景；不要忽略"老员工"的声音（他们见过更多失败）。

### 追问 6："客户调研说他们喜欢 X，但销售说客户其实喜欢 Y，怎么办？"
**答**：客户调研 vs 销售经验冲突——标 CLS。追问"调研是怎么做的？" / "销售判断基于什么案例？"——证据强弱对比。

### 追问 7："stakeholder 说'我以前试过 X 不行'，但没说为什么，怎么办？"
**答**：追问"那次试的具体场景是什么？失败原因？"——失败案例是 O 意见型信号，含高价值信息。

### 追问 8："stakeholder 说话时明显很烦躁，怎么办？"
**答**：标情绪信号——追问"看起来这个话题让你很烦，能多说说吗？"——情绪背后是痛点。

### 追问 9："stakeholder 说'这个以后再说'，但项目就要截止了，怎么办？"
**答**：标"已被推迟"——但追问"为什么以后？"——可能有 stakeholder 没明说的顾虑。ISS-XXX 记录"以后"的条件（什么时候再提？触发条件？）。

### 追问 10："团队里有人离职前吐槽了很多问题，新人接手怎么办？"
**答**：离职面谈记录常含高价值信号——但要小心：离职原因可能带情绪。新人接手要重新跑 RR，不直接继承离职者的所有判断。

### 追问 11："stakeholder 在群里说'同意'，但私下跟我抱怨，怎么办？"
**答**：群内同意是正式表态（白信号）；私下抱怨是 O 意见型——两者并存是 CLS 类。让 stakeholder 在群内澄清，或在 RR §4 自查反馈位记录私下声音。

### 追问 12："老板说'都听业务方的'，业务方说'听老板的'，怎么办？"
**答**：典型责任规避。AI 不替决策——追问"谁是决策 owner？"明确责任人后让责任人书面签字。

## 5. 错误示例

❌ **只抄 stakeholder 提的方案**："stakeholder 说要做自动报表 → FEA-XXX 自动报表"
✅ 追问"为什么想要自动报表？" → "每周花 4h 做" → RR-XXX 痛点 = "重复劳动 4h/周" → 方案 = "自动报表"（但也要评估其他方案如"减少报表字段"）

❌ **沉默 = 同意**："没人反对 = 全员通过"
✅ 沉默 = INF 类未决，二次询问显式点名沉默者

❌ **忽略离职面谈的信号**："老员工走了，意见不重要"
✅ 离职面谈含高价值 O 意见型信号——但要带情绪过滤

❌ **私下口头承诺当正式决策**："老板昨天吃饭时说就这么干"
✅ 私下口头 = ASSUMPTION，要求正式渠道确认

❌ **把"我不在乎"当 stakeholder 没需求**："业务方不在乎 → 不做"
✅ stakeholder 在乎的可能不是这个——追问"为什么不在乎"挖掘更深痛点

❌ **老板说"都同意吧"没人反对 → 当全员同意**
✅ "没人反对" ≠ "全员同意"——显式点名确认
