# L0/L1 产品产出质量契约

> 目的：把经过评估的 PRD、用户研究、方案评估和反向评审实践，收敛为本项目可追溯、可执行的最低质量要求。只有落到来源、决策、验收和人工确认的内容才算项目能力。

## 能力分层

| 能力 | L0：单点变更 | L1：受限场景 | 命中后升级/按需触发 |
|---|---|---|---|
| 事实与知识状态 | 每个关键主张标 `FACT/DECISION/ASSUMPTION/UNKNOWN`，至少一个可定位来源 | 每个上游产物保留事实账本、假设/未知/冲突及 owner | 多来源冲突、敏感事实或证据不足时进入 L2 |
| 用户影响 | 说明受影响角色、入口、可观察结果和不受影响边界 | 旅程覆盖角色×阶段，痛点→机会→故事可追溯 | 多角色冲突、外部角色或复杂旅程进入 L2 |
| 范围与替代方案 | 记录本次变更、不做什么、至少一个被排除的替代方案及理由 | In/Out/Deferred/Conditional 有业务决策、代价和触发条件 | 多方案取舍影响架构、成本或发布策略时进入 L2 |
| 价值/成本/风险 | 说明价值结果、回退成本和主要风险；不编造数字 | 对 P0/P1 功能记录价值-成本-风险判断及证据 | 成本倒挂、不可逆、高风险或合规信号进入 L2 |
| 失败与回退 | 至少一条真实失败边界，或给出无需新增回退的事实依据 | 主流程、分支、异常、恢复/升级路径均可追溯 | 状态机、多个独立恢复路径或不可逆操作进入 L2 |
| 反向验证 | 写出成功不成立时的可证伪条件/停止条件 | 评审前回答“什么证据会推翻当前方案”，形成质疑记录 | 方案争议、竞品替代或高不确定性触发深度评审 |
| 验收 | 至少一条可观察 Given/When/Then，含判定方法 | 每个 P0 功能覆盖正常和异常验收，阈值必须有来源或标待确认 | 性能、可用性、合规或模型指标进入 L2/NFR |

## 统一证据块

L0 mini-prd 和 L1 上游产物都可以使用以下表格。字段为空不能伪装成完成；不适用必须写事实依据、来源、判断人和日期。

```markdown
## 产品质量增强记录

| 项目 | 结论 | 知识状态 | 来源/位置 | 判断人 | 复核触发 |
|---|---|---|---|---|---|
| 受影响角色与结果 |  | FACT/DECISION/ASSUMPTION/UNKNOWN |  |  |  |
| 采用方案与被排除替代 |  | DECISION/ASSUMPTION |  |  |  |
| 价值-成本-风险 |  | FACT/AI_INFERENCE/UNKNOWN |  |  |  |
| 失败边界与回退 |  | FACT/DECISION/UNKNOWN |  |  |  |
| 可证伪条件/停止条件 |  | DECISION/UNKNOWN |  |  |  |
```

## 不允许的捷径

- 不能用“用户体验提升”“按需”“本期不适用”“风险可控”作为完整结论；必须补充对象、判据、依据和负责人。
- 不能把 AI 推断写成事实，也不能把一个方案直接当成需求本身。
- 不能用编号、优先级或日期中的数字冒充量化验收阈值。
- 不能因为 L0/L1 少做上游工项，就删除最终 PRD 必须回答的问题。

## 与三档的关系

L0/L1 的区别是证据深度与工作项数量，不是产品思考质量。L0 用一份紧凑记录承载上述能力；L1 将其分布到背景、旅程、故事、功能、流程、规则和验收产物；L2 在需要时增加页面、交互、字段、状态和异常的独立深度产物。

新产物在 frontmatter 写 `quality_contract_version: "1"` 后启用机器门槛。没有该字段的历史产物只读兼容，下一次 reflow/review/release 时必须迁移。
