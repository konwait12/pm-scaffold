# 假设反事实验证（Assumption Stress-Test）

> 本文将相关实践转化为本项目的可选方法，不引入外部运行时依赖。
>
> **定位**：每条 ASSUMPTION / AI_INFERENCE 必须能写出"什么证据出现时，此判断会降级/推翻"——否则视为 weak，不得进正文。本技法把这条规则系统化。
>
> **触发**：Intake 后 RR 定稿前，对每条 ASSUMPTION 类主张做反事实验证。
>
> **按需加载，不设全局闸门。**

## 2. 假设三态分级（承接 thinking-core §1.6.1）

| 级别 | 判定 | 标注 | 产物行为 |
|---|---|---|---|
| **strong** | ≥2 条独立来源交叉支撑 | `AI_INFERENCE(strong)` | 可写入产物正文，进入评审基线 |
| **medium** | 单条来源或推断链成立但未交叉验证 | `AI_INFERENCE(medium)` | 写入正文但标 `待确认`，进 Clarify |
| **weak** | 无来源、凭经验补全 | `AI_INFERENCE(weak)` | 不写入产物正文，只进 Clarify 问题清单 |

**可证伪条件（必须写清什么证据会改变判断）**：

每条 AI_INFERENCE 附带"若出现 X 证据，此判断降级/推翻"。

例：
```
ASSUMPTION: 销售每日录入跟进 1 次
（AI_INFERENCE(medium)，若访谈 3 个客户中 ≥2 个反馈实际每日 3 次，则降级 UNKNOWN 并重走 Intake）
```

**写不出可证伪条件的推断视为 weak，不得进正文。**

---

## 3. 反事实验证 4 问

对每条 ASSUMPTION / AI_INFERENCE，按顺序回答：

### 问 1：若假设反转会怎样？
- "如果假设 X 不成立，会导致什么可观察后果？"
- 后果若是 PRD 的核心承诺（如目标、范围、合规底线），假设必须升级验证强度
- 后果若是边缘功能（如某个细节 UI 文案），假设可降级为 weak

### 问 2：什么证据会证伪？
- "什么数据 / 反馈 / 实验结果出现，能推翻这条假设？"
- 证据必须可观测、可获取、可验证
- 例：销售每日跟进 1 次的假设，可证伪证据是"访谈 3 个销售，≥2 个说实际每日 3 次"

### 问 3：证伪后怎么回流？
- "假设被推翻后，是降级到 UNKNOWN 重走 Intake，还是直接终止该 RR-XXX？"
- 终止条件：假设是 RR-XXX 的前提，前提不成立则 RR-XXX 整体作废
- 降级条件：假设是 RR-XXX 的补充说明，前提不成立可拆分或重写

### 问 4：若不验证，最坏会怎样？
- "如果今天不验证假设就直接进入下游产物，最坏后果是什么？"
- 后果若涉及合规 / 资金 / 安全 → 强制验证，必须 BLOCKING
- 后果若是体验优化 → 可放宽到 CONDITIONAL 或 ADVISORY

## 4. 应对 12 类典型追问

### 追问 1："这个假设太显然了吧，还需要验证吗？"
**答**：显然 ≠ 真。`evidence-four-dimension-check.md` 的"方向"维度问的就是这个——证据方向是否与假设同向？反例："用户不需要这个功能"显然错，但"用户需要 X 程度的功能"显然吗？

### 追问 2："业务方没说要验证，为什么 AI 要加这一步？"
**答**：AI 行为硬约束——`src/framework/thinking-core.md` §1.6 要求每条推断写可证伪条件。这不是业务方要求，是体系要求。

### 追问 3："没时间验证，能不能先写进 PRD 然后再补？"
**答**：可写为 `AI_INFERENCE(weak)` + 进 issue-record（INF 类）——但**不进 PRD 正文**，正文只写 `待确认`。

### 追问 4："已经做过调研了，还要再验证吗？"
**答**：调研 ≠ 验证。调研看的是"现状如何"；验证看的是"假设成立吗"。调研后假设仍可能错——加访谈或 A/B 测试。

### 追问 5："这条假设是产品经理的直觉，能用吗？"
**答**：PM 直觉可作为 AI_INFERENCE(medium) 的来源——但必须有可证伪条件。PM 直觉作为"来源 [PM 个人判断]"记录。

### 追问 6："假设失败会导致整个 PRD 重做，太重了，怎么办？"
**答**：拆分——把假设作为可选项写进 BG §约束章节，标 "若 X 假设不成立，PRD 范围需重评"。比整体重做轻。

### 追问 7："上游 stakeholder 已经确认了，还要再验证吗？"
**答**：上游确认的是事实（FACT），不是假设（ASSUMPTION）。若 stakeholder 的"确认"本身是基于一个假设，仍需验证那个假设。

### 追问 8："假设 A 和假设 B 互斥，怎么处理？"
**答**：标 CLS 类冲突，路由 issue-record。让 stakeholder 裁决 A 还是 B，或承认两者不可同时成立、范围需拆分。

### 追问 9："这条假设已经写在 issue-record 里了，能直接进 PRD 吗？"
**答**：issue-record 是"未决"，PRD 是"已确认"——issue-record 中的假设必须先升级为 DECISION / FACT 才进 PRD。

### 追问 10："假设太多，每条都写可证伪条件太繁琐，能简化吗？"
**答**：不能简化——但可对假设做分级：影响 PRD 核心承诺的假设 → 必写；影响边缘功能的假设 → 可合并到一类假设写一条。

### 追问 11："业务方说'反正我们老板会拍板，验证啥'，怎么办？"
**答**：AI 不替业务方决策（`contracts.md`）。验证是 AI 行为硬约束——业务方不验证 ≠ AI 可以不写可证伪条件。

### 追问 12："已经做 A/B 测试了，假设验证过了，还要再写吗？"
**答**：A/B 测试是验证手段之一，验证结果是事实。但仍需在 RR-XXX 中记录"已 A/B 测试，结果支持/推翻假设"——审计需要。

## 6. 错误示例

❌ **写不出可证伪条件**："我们假设用户喜欢这个"——什么证据出现会推翻？
✅ "假设用户喜欢 X 功能（AI_INFERENCE(medium)，若访谈 5 个目标用户中 ≥3 个反馈不喜欢 X，则降级 UNKNOWN 并重走 Intake）"

❌ **把"显然"当证据**："显然业务方知道这个"——显然不是证据
✅ "业务方知道这个 [SRC-001 §3.2，2026-08-15 会议]"——有具体来源

❌ **混淆 stakeholder 确认 vs 假设验证**：业务方确认 ≠ 假设验证
✅ stakeholder 确认是关于 stakeholder 自己的话；假设验证是关于客观事实

❌ **跳过 weak 假设**：weak 假设就不写
✅ weak 假设进 issue-record（INF 类），不写进 PRD 正文，但留审计痕迹

❌ **假设失败后沉默重写**：假设被推翻就悄悄改 PRD
✅ ChangeRecord 记录假设变更时间 + 推论变更范围 + 影响下游
