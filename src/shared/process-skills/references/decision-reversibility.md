# 决策可逆性分级（Decision Reversibility）

> 本文将相关实践转化为本项目的可选方法，不引入外部运行时依赖。
>
> **定位**：每个 PRD 决策都隐含"做了能不能撤"——AI 经常把所有决策一视同仁，结果该慢的（不可逆）很快做了，该快的（可逆）反而纠结。本技法把可逆性分级显式化，逼出 stakeholder 真实紧迫度。
>
> **触发**：RR Intake 时遇到以下信号——
> - 含合规 / 资金 / PII / 法律告知类决策
> - 含数据迁移 / 系统替换 / 供应商锁定类决策
> - stakeholder 说"赶紧做" / "这事很重要"
> - 多个方案取舍
>
> **按需加载，不设全局闸门。**

## 2. 4 级可逆性

### Level 4：完全可逆（Easy Reversible）

**改错了可以立刻回退，零成本**。

例：
- UI 文案 / 按钮文字
- 字段顺序 / 排序
- 默认值调整
- 配色 / 布局

**处理**：默认快速通过。无需 RR 复述。验证强度 = 单测。

### Level 3：可逆但有成本（Reversible with Cost）

**改错了可以回退，但要花时间 / 资源**。

例：
- 数据库 schema 改动（migration 脚本可回滚）
- API 接口调整（但下游需同步改）
- 业务流程重排（人员需重新培训）

**处理**：标 reversal_cost。决策需 RR 复述，但可并行推进。验证强度 = 集成测试 + 灰度。

### Level 2：难可逆（Hard Reversible）

**改错了要花大力气才能回退，可能有数据损失**。

例：
- 数据迁移（脏数据 / 部分转换失败）
- 状态机变更（旧订单 / 老用户的状态迁移）
- 供应商锁定（切换供应商成本高）
- 公开 API 承诺（外部依赖你的接口）

**处理**：必须 RR 复述 + 多源验证 + 灰度 + 回滚预案。验证强度 = 完整 UAT + 数据校验。

### Level 1：不可逆（Irreversible）

**改错了回不去，可能永久损失**。

例：
- 删库 / 清空数据
- 资金扣款（不可退）
- 合规告知（一旦发出无法撤回）
- 法律承诺（一旦签字不可撤）
- 关闭某账号 / 终止某服务
- 不可逆的数据变形（如哈希）

**处理**：**强制 RR 复述 + 多 stakeholder 签字 + 法务 / 合规审核 + 完整回滚预案 + 演练**。验证强度 = 多轮审计 + 演练。

## 3. 应对 12 类典型追问

### 追问 1："老板说'赶紧做'，但这事是不可逆的，怎么办？"
**答**：不可逆决策不因紧迫性而加快（`time-sensitivity-and-decision-window.md`）。追问"为什么紧迫？"——紧迫可能源于 stakeholder 没意识到不可逆性，或真的需要快。不可逆必须慢做。

### 追问 2："删数据是不可逆的，但数据库确实要清理，怎么办？"
**答**：不可逆 + R2 高风险。必须 RR 复述 + 多 stakeholder 签字 + 完整备份 + 演练 + 灰度。**绝不能"先删后补"**。

### 追问 3："可逆决策需要 RR 复述吗？"
**答**：Level 3-4 不需要 RR 复述（除非 stakeholder 主动要求）。Level 1-2 必须。

### 追问 4："数据迁移是 Level 2，怎么降低风险？"
**答**：完整回滚预案——双写（旧库 + 新库同步）+ 切流（按比例切流量）+ 数据校验（双写对比）+ 演练（在测试环境跑一遍完整流程）。

### 追问 5："供应商锁定不可避免，怎么办？"
**答**：标 Level 1-2。在合同里加退出条款（退出成本 / 数据导出 / 过渡期）；不要签独家；保留备选供应商评估。

### 追问 6："业务方说'这个决策可以反悔'，但其实不可逆，怎么办？"
**答**：标 CLS 类冲突。让 stakeholder 实际走一遍回滚流程——若发现回滚成本高 / 数据损失，重新分级。

### 追问 7："可逆决策但 stakeholder 反复改，怎么办？"
**答**：可逆 ≠ 频繁改。频繁改说明 stakeholder 没想清楚——用 `multi-stakeholder-alignment-matrix.md` 跑一遍对齐。

### 追问 8："不可逆决策的时间窗很紧（比如月底合规上线），怎么办？"
**答**：不可逆 + 时间紧 = R3 高风险。标 BLK 类 + 业务方书面签字接受风险。AI 不替决策。

### 追问 9："删账号是 Level 1，但客服说'客户要求立即删'，怎么办？"
**答**：不可逆 + R3 + 时间紧。先冻结（Level 2）再走审批流程——冻结后还有时间补救。

### 追问 10："API 公开承诺一旦失误影响所有外部调用方，怎么办？"
**答**：标 Level 1。承诺前必须有 deprecation 策略（旧版本保留 N 个月）+ 版本管理（v1 / v2）+ 客户通知（N 个月前预告）。

### 追问 11："决策可逆性 vs 误读代价怎么平衡？"
**答**：不可逆 + 低误读代价 = R1 中风险（仍可逆但要慢）。不可逆 + 高误读代价 = R3 高风险（必须多 stakeholder 签字）。

### 追问 12："AI 替 stakeholder 评估可逆性可靠吗？"
**答**：不可靠——AI 不知道真实业务背景。可逆性必须 stakeholder 自己评估（RR §4 stakeholder 自查反馈位）。AI 提示框架和问法。

## 5. 错误示例

❌ **不可逆决策被"赶紧做"加速**："老板说赶紧删 → AI 直接删"
✅ 不可逆必须 RR 复述 + 多 stakeholder 签字 + 演练 + 灰度

❌ **可逆决策被反复纠结**："UI 文案改个词要 3 轮评审"
✅ Level 4 可逆决策快速通过，无需 RR 复述

❌ **数据迁移"先做了再说"**："先迁数据，回滚方案后写"
✅ 数据迁移是 Level 2，必须完整回滚预案 + 演练在前

❌ **供应商锁定无退出条款**："签了独家，没考虑退出"
✅ 合同必须含退出条款 + 数据导出 + 过渡期

❌ **删账号/扣款无审计**："客户要求删 → AI 直接删"
✅ 不可逆操作必须审计日志 + 多 stakeholder 签字 + 法务确认

❌ **把可逆决策说成不可逆**："改字段名很重要，要法务审核"
✅ 改字段名 Level 4，无需法务审核
