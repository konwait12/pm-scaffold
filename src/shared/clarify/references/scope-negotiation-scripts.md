# 范围谈判脚本技法（Scope Negotiation Scripts）

> 来源吸收：work buddy `product-management/references/prioritization-frameworks.md` §Scope Negotiation Scripts 的 4 个范围谈判脚本（"Can we add X?" / "This is a must-have" / "The competitor has this" / "Everything is priority 1"），适配 to B 场景话术，作为 shared/clarify 的可选落地能力（供 Clarify 阶段范围争议与 feature-list 优先级裁决复用）。
> 定位：`confirmation-signal-technique.md` 解决"用户答了什么、算不算确认"；本文档解决"需求方想加/想压范围时，如何把'加'与'砍'变成有代价、可裁决的谈判"——让 AI 在 Clarify 阶段把模糊的范围诉求结构化，不直接说"好"或"不行"，而是给出 trade-off 让业务方决策。
> 触发：Clarify 阶段遇到范围扩张（加 X）、压测（must-have）、竞品对标（竞品有）、优先级摊平（全是 P1）四类信号时使用。**按需加载，不设全局闸门**。

## 1. 输入映射（pm-scaffold 语境）

| 外部 skill 输入 | pm-scaffold 对应产物 | 说明 |
|---|---|---|
| "Can we add X?" 脚本（加 X 的代价 = 推迟现有 Y） | Clarify 提问 / feature-list 范围裁决 | 把"加功能"转化为"谁被推迟/挤掉"的显式 trade-off |
| "This is a must-have" 脚本（缩小范围试错 80% 价值） | Clarify 提问 / user-stories In/Out | 把"必须做"压到可快速验证的最小范围 |
| "The competitor has this" 脚本（查 win/loss 与真实决策驱动） | Clarify 提问 / 竞品对标 | 用证据区分"决策驱动因素"与"可有可无的清单项" |
| "Everything is priority 1" 脚本（强制排序 top N） | feature-list 优先级裁决（P0/P1/P2） | 打破"全 P1"，逼出真正的优先级序列 |

> **共同原则**：谈判不是替业务方做决策，而是把隐藏的代价显式化——AI 产出选项与影响，取舍权在人（呼应 `confirmation-signal-technique.md` §8 不替业务方决策）。

## 2. 脚本一："Can we add X?"（加需求谈判）

需求方要求加功能 X 时，不直接答"可以/不行"，把代价摆上台面：

```
话术骨架：
"可以加 X。代价是：现有 [REQ-NNN / FEA-XXX] 会被推迟约 [N] 周。
X 比 [REQ-NNN / FEA-XXX] 更重要吗？
→ 是 → 我们做交换（X 进本期，[REQ-NNN / FEA-XXX] 降级/移出）。
→ 否 → X 记入 backlog，排进下一期。"
```

to B 适配示例（企业客户管理系统后台）：
- "可以加'销售周报自动生成'。代价是：现有 FEA-002 销售跟进记录迭代推迟 3 周。自动周报比跟进记录迭代更重要吗？是 → 交换；否 → 进 backlog 下一期。"

要点：
- **必须点名被推迟项与时长**——不给"挤时间出来"的模糊承诺；排不出被推迟项 = 未完成谈判。
- **交换优先于追加**：范围是固定的，加 X = 移走 Y，不允许"预算外追加"。
- **结果落到两态**：`交换（X 进 / Y 移）` 或 `backlog（X 后置）`，二选一，不挂起。

## 3. 脚本二："This is a must-have"（必须做谈判）

需求方强调某功能"必须做、一步到位"时，把"必须"压到可验证的最小范围：

```
话术骨架：
"我理解你要的最终结果是 [目标 outcome]。我复述一下：[Listen 后复述]。
我们能否用 [更小范围方案] 在 [更短时间] 先实现？它能达到约 80% 的价值。
→ 可以 → 先做小范围，上线验证再迭代（MVP 路径）。
→ 不行 → 请说明缺的 20% 是哪部分、为什么缺它就无法上线。"
```

to B 适配示例：
- "我理解你要的是'销售看不到自己的漏斗就别上线'。复述：销售要能实时看漏斗。能否先用 FEA-004 漏斗报表的只读版（3 天上线）？它覆盖 80% 的看数诉求。可以 → MVP 先行；不行 → 请说明缺的 20%（如导出）为何必须首版。"

要点：
- **先复述目标，不接方案**——把"必须做 X"转成"必须达成 outcome"，为缩小范围留空间（呼应 `confirmation-signal-technique.md` §3.2 二次询问用业务语言复述）。
- **80% 价值是默认锚点**——小于 80% 需人工确认是否仍值得做；大于 80% 就应走 MVP。
- **拒绝缩小必须给理由**——"不行"必须有缺项清单，防止无依据的一步到位。

## 4. 脚本三："The competitor has this"（竞品对标谈判）

需求方以"竞品有这个功能"要求跟进时，用证据区分真需求与清单心理：

```
话术骨架：
"竞品确实有。问题是：客户选他们是因为这个功能，还是没有它也不影响选型？
我去核对 win/loss 数据 + 访谈 3 个真实客户（确认：赢单因它？输单因缺它？）。
→ 它是真实决策驱动 → 排进本期。
→ 只是清单项/无证据 → 不进本期，记录为观察项。"
```

to B 适配示例：
- "竞品的审批流确实有'多级会签'。客户选竞品是因为会签，还是没有会签也没影响？核对近 3 个月 win/loss 记录 + 访谈 3 个流失客户。若 3 个中 ≥2 个因缺会签流失 → 排进本期；否则 → 不进本期。"

要点：
- **先找证据再表态**——不因为"竞品有"就默认本期做；证据来源 = win/loss 记录 + 客户访谈，二者缺一不可。
- **判据写死**——访谈 N 人中 M 人提及 = 决策驱动；写不出判据 = 尚未完成谈判。
- **记录去向**——不是决策驱动也登记为观察项（后续数据出现再复审），不静默丢弃。

## 5. 脚本四："Everything is priority 1"（优先级摊平谈判）

需求方把一批功能全标 P1/P0 时，用强制排序打破摊平：

```
话术骨架：
"如果全部都是 P1，那其实没有 P1。请做强制排序：只取 Top [N]。
如果本期只能上线一个功能，你选哪个？那才是 P0。
→ 逐个排出 P0 → P1 → P2，允许并列但每级数量有限。
→ 排完再对照 REQ 目标：Top 项是否覆盖核心目标？落不上的降级。"
```

to B 适配示例：
- "8 个功能全标 P1 等于没有优先级。本期只能上线 1 个，你选哪个？→ FEA-001 客户名单导入。再选第 2、3 个。剩下的 P1 降为 P2 或移出本期。Top 3 是否覆盖了'销售能发起邀约活动'这个核心目标？"

要点：
- **强制单选起手**——"只发一个"逼出真正 P0，防止"都重要"式摊平（呼应 `feature-priority-quant.md` §3 伪精确反模式）。
- **排序结果与目标对齐校验**——Top 项必须能覆盖已确认目标（BG-XXX），覆盖不了的强制降级。
- **每级限数量**——P0/P1/P2 各级有限额，杜绝"10 个 P0"。

## 6. 谈判输出与登记

每次谈判结束，结果必须落到产物（不留在对话里）：

| 谈判类型 | 输出到哪 | 登记内容 |
|---|---|---|
| Can we add X | feature-list.md 范围基线 / 优先级 | 交换项（X 进 / Y 移）或 backlog 项，含被推迟的 FEA-XXX 与时长 |
| This is a must-have | user-stories.md In/Out / 功能 MVP 边界 | 缩小后的小范围项 + 80% 价值依据；拒绝缩小的缺项清单 |
| Competitor has this | 竞品对标 / feature-list 优先级 | 证据（win/loss + 访谈判据）+ 进本期 / 观察项结论 |
| Everything is P1 | feature-list.md 优先级列 | 强制排序结果（P0→P1→P2）+ 与 BG-XXX 目标对齐校验结论 |

- **结果两态必落一态**：进本期（P0/P1）或后置（backlog / 观察项 / P2），不留"再议"。
- **涉及范围增减时路由**：影响已确认范围基线的谈判结果，登记 issue-record 并走 `needs_user_input`，不自行改写已确认基线。

## 7. 核心硬规则

1. **不加预算外追加**：加 X = 移走 Y，被推迟项与时长必须点名。
2. **先复述目标再接方案**：must-have 谈判先用业务语言复述最终结果，不直接接"做 X"。
3. **竞品对标先找证据**：win/loss 记录 + 客户访谈，判据写死（N 人中 M 人），无证据不进本期。
4. **摊平必须强制排序**："全 P1"用"只发一个"逼出 P0；Top 项须对齐已确认目标。
5. **结果两态落一态**：进本期或后置，不留"再议"；影响已确认基线须登记 issue-record 并路由 `needs_user_input`。
6. **不替业务方决策**：AI 只给 trade-off / 选项 / 影响，取舍权在产品/业务负责人。

## 8. 边界（Do Not）

- 不直接替需求方拍板"做/不做"——谈判产出选项与影响，决策权在人。
- 不用脚本回避真实反馈——must-have 拒绝缩小时的缺项清单必须如实转达。
- 不把竞品对标做成"竞品有就抄"——只处理有证据的决策驱动项。
- 不把范围谈判结果留在对话里——必须落到 feature-list / user-stories / 竞品对标 产物。
- 不自行改写已确认的范围基线——涉及基线增减走 issue-record + `needs_user_input`。

## 9. 质量自检清单

- [ ] "加 X"谈判点名了被推迟项与时长，结果落到 交换 / backlog 两态之一
- [ ] "must-have"先复述目标再给小范围方案，拒绝缩小有缺项清单
- [ ] "竞品有"核对过 win/loss + 客户访谈，判据写死，结论为 进本期 / 观察项 之一
- [ ] "全 P1"完成了强制排序（Top N + 只发一个），并与 BG-XXX 目标对齐
- [ ] 谈判结果均已登记到产物（feature-list / user-stories / 竞品对标），无"再议"挂起
- [ ] 影响已确认基线的变更已登记 issue-record 并路由 `needs_user_input`
- [ ] 全程未替业务方做最终取舍，只提供 trade-off / 选项 / 影响
