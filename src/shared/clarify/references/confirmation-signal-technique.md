# MRC 门禁与确认信号技法参考（Confirmation Signal Technique）

> 本文将相关实践转化为本项目的可选方法，不引入外部运行时依赖。
> 定位：各 skill 的 Clarify 阶段文本是权威；本文档提供"用完整度阈值与确认信号识别驱动澄清收敛"的技法，增强人工确认质量。
> 触发：当 Clarify 阶段需判断澄清完整度、或用户回复需判定是否真正确认时使用。**按需加载，不设全局闸门**。

## 2. MRC 门禁（Minimum Runnable Clarification，最小可行性澄清，G1-G6）

送审前逐项判定；任一不满足则路由 `needs_user_input`，不进入 Human Gate。MRC 通过仅代表"可输出最终确认表"，**不等于可推进**——须用户对确认表显式确认方可推进。

| 门禁 | 判定标准 | 来源 |
|---|---|---|
| G1 核心信息完整 | 5 基础维度（基础信息/目标用户/核心功能/目标价值/非目标）均有值 | BG-XXX / user-journey / user-stories |
| G2 P0 功能可定义 | P0 功能 ≥3 个且可定义优先级 | feature-list |
| G3 范围基线 | In/Out/Deferred 有依据 | user-stories |
| G4 约束显式 | 业务约束 ≥1 条（合规/时间/预算/组织/历史） | BG-XXX |
| G5 冲突消解 | 无未决 CONFLICT（矛盾项已用户裁决） | issue-record |
| G6 来源可追溯 | 每条声明有 SRC-/FACT/DECISION 归类 | source-handling |

> **快速路径**：当成熟度=L3（完整功能清单+优先级+流程+非目标+验收期望）且 D1 模糊度=明确、D2 需求量=少（功能点≤3）时，MRC 简化为 G1+G2+G4 三项即可。

## 3. 白/灰/黑确认信号识别（完整词表）

对用户的每条回复判定确认强度。词表吸收自 prd-to-prototype 全局铁律 #3。

### 3.1 白名单（明确通过 → 转 DECISION）

确认 / 确认通过 / 通过 / OK / 可以 / 没问题 / 同意 / 进入下一步 / 进入原型

> 前文已无异议后接"好的 / 行"按白名单处理。

### 3.2 灰名单（模糊表述或沉默 → 触发二次询问，不视为确认）

看起来不错 / 应该可以 / 差不多 / 先这样吧 / 嗯 / 没意见 / 随便 / 你看着办 / 未回复沉默

**二次询问话术**（灰名单触发，须用业务语言复述并要求明确表态）：

```
请问您是确认通过吗？
A) 确认通过，进入下一步
B) 还有修改（请说明）
C) 其他__
```

二次仍灰则标 `待确认` 阻断，不推进。

### 3.3 黑名单（否定/异议 → 记录 CONFLICT，路由回流）

修改 / 不对 / 不行 / 等等 / 暂停 / 我再看看 / 让我想想 / 有问题 / 有疑问 / 不确定

按用户反馈修订后重新进入暂停等待状态，不自动推进。

## 4. 业务需求汇总确认表（Excel 10 列·业务语言）

MRC 通过后用户选择停止追问时，输出最终确认表作为模块交接产物。确认表**只含业务需求内容**（不含方法/成熟度等过程性维度）。

| 列 | 列名 | 说明 | 示例 |
|----|------|------|------|
| A | 序号 | 跨轮次连续编号 | 1 |
| B | 维度 | 业务维度（中文） | 目标用户/核心功能/目标价值/非目标 |
| C | 需求点 | 一句话标题 | 目标用户为 B 端会员 |
| D | 需求描述 | 详细说明（含特征/规则/边界） | 会员分普通/VIP 两类，权限有差异 |
| E | 目标用户 | 谁用 | B 端会员（普通+VIP） |
| F | 用户场景 | 什么场景下用 | 会员攒了积分想兑换优惠券 |
| G | 用户价值 | 用户得到什么 | 积分有消耗去处，激励持续消费 |
| H | 优先级 | P0/P1/P2 | P0 |
| I | 需求来源 | 来源追溯 | 用户描述/PM 推断/竞品分析 |
| J | 状态 | ⬜待确认/✅已确认/⚠️冲突 | ⬜待确认 |

### 维度分类（5 基础必填 + 3 扩展按场景选填）

**基础维度（所有场景必填 5 类）**：基础信息 / 目标用户 / 核心功能 / 目标价值 / 非目标

**扩展维度（按场景选填 3 类）**：
- 使用场景：C 端产品/MVP 验证（时间/地点/触发/频次/上下文）
- 角色权限：B 端系统/管理后台（多角色权限矩阵、审批流程、数据隔离规则）
- 依赖约束：所有场景必填子项（技术依赖：接口/系统/数据 + 业务约束：合规/时间/预算/组织/历史）

> **需求来源三段式**：来源类型（用户反馈/竞品分析/战略规划/老板指示/数据分析/合规要求）+ 来源人（角色+部门，脱敏后）+ 来源场合（需求评审会/用户访谈/工单系统/老板 1v1/战略会）

## 5. 交接校验清单（模块切换时自动执行）

- 5 基础维度均有值
- 扩展维度按场景覆盖（C 端使用场景 / B 端角色权限 / 全场景依赖约束）
- P0 功能 ≥3 个
- 矛盾项已解决（无未决 ⚠️）
- 业务约束 ≥1 条
- 字段级自检：优先级仅 P0-P2 / 功能编号连续不重复 / 页面编号连续

## 6. 工作流程

1. **跑门禁**：Clarify 末逐项判定 G1-G6；不满足项生成 ISS-XXX。
2. **识别信号**：对用户回复按白/灰/黑分类；灰名单触发二次询问话术。
3. **登记**：确认转 DECISION；异议转 CONFLICT；未决标 UNKNOWN。
4. **收口**：门禁全绿 + 无未决 CONFLICT + 用户对确认表显式确认，才可送审推进。

## 7. 核心硬规则

1. **门禁不全则不送审**：G1-G6 任一不满足路由 `needs_user_input`，绝不绕过进 Human Gate。
2. **灰名单不视为确认**：模糊回复触发二次询问；不得把"差不多/应该可以"当 DECISION。
3. **信号与知识状态对齐**：白→DECISION、灰→UNKNOWN、黑→CONFLICT，不发明新标签。
4. **二次询问用业务语言**：复述确认须用业务术语，不诱导用户答"是"。
5. **MRC 通过≠可推进**：MRC 通过仅代表信息完整，须用户对最终确认表显式确认方可推进。
6. **矛盾必须暴露**：检测到冲突在确认表标 ⚠️，须用户裁决后方可推进。

## 8. 边界（Do Not）

- 不替代各 skill 的 Clarify 文本——门禁是收敛工具，文本是权威。
- 不替业务方决策——只识别信号，决策权在人。
- 不设全局闸门阻断 pipeline——门禁产 `needs_user_input`，由各 skill 自行处理。
- 不强制 100% 信息完整才出 PRD——MRC 是"最小可行性澄清"，非满分要求。
