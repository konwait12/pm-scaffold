# 问题沟通与升级技法（Issue Communication & Escalation）

> 来源吸收：`pm888`（专业产品经理 Agent 系统提示词）的 §10.3 坏消息公式 / §10.4 软化规则 / §2.5 状态诚实与反西瓜规则 / §9 决策预注册与四象限复盘、`juloko`（research-to-prd）的 references/fact-extraction.md §3 冲突识别、`pmaster`（PM Master）的 §9.1 预死亡分析三类风险，作为 issue-record 的可选落地能力。
> 定位：把"登记问题"升级为"会沟通、会升级"——坏消息按公式说、冲突按 4 模式识别、风险按概率×影响定级并按阈值升级、待决决策用四象限复盘、Human Gate 用标准呈现模板。
> 触发：需要向干系人通报坏消息/风险、识别来源冲突、判断 RSK 是否升级、DEC 复盘、或准备 Human Gate 呈现时加载。**按需加载，不设全局闸门**。

## 1. 输入映射（pm-scaffold 语境）

| 外部 skill 输入 | pm-scaffold 对应产物 | 说明 |
|---|---|---|
| 坏消息公式（事实→影响→在做→诉求） | issue-record 的 BLK / RSK 通报文案 | 干系人更新时的沟通结构 |
| 冲突识别 4 模式 | issue-record 的 CLS（歧义）与 CONFLICT 知识状态 | 冲突雏形 → 登记 + 恒 P0 |
| 状态诚实（🟢/🟡/🔴 判定） | issue-record 的 state 字段判定 | open / in_progress / blocked 的诚实口径 |
| 风险概率×影响矩阵 | RSK 条目的 mitigation 与升级判定 | 风险分级细则 |
| 决策预注册 + 四象限复盘 | DEC 条目的 target_close 与升级路由 | 待决决策的复盘与收口 |
| 预死亡分析三类风险（老虎/纸老虎/大象） | RSK 识别口径 | 什么算真风险、什么只是被夸大 |

> **问题不是写给自己看的**：issue-record 是给业务方的权威"还有什么没解决"清单。每条问题的描述、状态、升级理由都必须能直接端给干系人读，无需翻译。

## 2. 坏消息公式（pm888 §10.3）

### 2.1 公式结构

**事实 → 影响 → 我们在做 → 明确诉求**。无软化前言、无归咎、无"不幸地是"。

| 步骤 | 内容 | 反例（❌） | 正例（✅） |
|---|---|---|---|
| 1 事实 | 发生了什么（时间、数字、范围） | "由于不可预见的情况，可能会有一些延迟。" | "支付 API 弃用让我们损失 2 周。" |
| 2 影响 | 对承诺/里程碑/干系人的后果 | （无） | "上线从 2/5 推到 2/19。" |
| 3 在做 | 当前缓解动作 | （无） | "正在评估砍掉发票范围以保住日期。" |
| 4 诉求 | 需要谁在什么时间做什么决策 | （无） | "除非砍发票范围，否则需在周五前决策。" |

### 2.2 完整正例

- ✅ "我们唯一的 iOS 工程师 3/1 离职去 [X]。2/10 前无补人决策，移动里程碑滑一个 sprint。已联系 2 家外包，需你在周五前选 A/B。"
- ✅ "合同审批在合规卡了 12 天，超出 target_close（本周五）将无法按计划进实施。我们已预出合规材料包（见 issue ISS-002，RSK），需法务本周三前复核。"

### 2.3 软化规则（pm888 §10.4）

1. **删 hedge**：删除"somewhat / may potentially / it seems"；不确定性只在真实且量化时保留（"60/40 我们能赶上日期"）。
2. **不预归咎**："如前所述…"读作自保；重要就平实重述风险。
3. **每个问题配决策**：无诉求的坏消息是 venting，有诉求的才是管理。RSK/BLK 的 description 末尾必须含"需要谁在何时做什么"。

## 3. 冲突识别 4 模式（juloko fact-extraction §3）

同一议题在不同来源出现不一致，全部挑出登记，**优先级恒为 P0**，不自行调和，交 stakeholder 仲裁：

| 冲突模式 | 识别信号 | 例子 |
|---|---|---|
| 来源矛盾 | 文档 vs 听记 / 不同文档间 | 规则文档说超时 24h，会上王经理说 48h |
| 口径矛盾 | 同一听记内互相打脸 / 前后口径不一 | 王经理说"全线上"，张总说"大额还是线下" |
| 数据矛盾 | 现状描述 vs 诉求目标互相冲突 | 说"要全自动"，又承认"最后一步必须人审" |
| 规则矛盾 | 版本/版本间规则不一致 | v1 说 A，v2 说 B，但没说改了 |

登记格式（沿用脚手架 ISS-NNN（CLS）与 CONFLICT 知识状态）：
`争议点 | 说法A(来源) | 说法B(来源) | 建议采信 | 仲裁人`

> **冲突恒 P0 的含义**：冲突不阻塞任务主线，但必须逐条登记、标 P0、指派仲裁人；未仲裁的冲突不得在产物里"悄悄选一个方便的说法"。

## 4. 风险分级与升级阈值（RSK 判定细则）

### 4.1 什么算真风险（pmaster 预死亡分析三类）

| 类型 | 定义 | 处理 |
|---|---|---|
| 老虎 | 真实问题，可能让项目脱轨 | 必须登记 RSK，进概率×影响矩阵 |
| 纸老虎 | 被夸大的担忧 | 记录以对齐干系人，不必登 RSK 或登记后标低概率 |
| 大象 | 未被说出的隐忧 | 值得深挖——访谈/会议里"欲言又止"的担忧要主动问出来 |

### 4.2 概率×影响矩阵（风险分级）

| 概率 \ 影响 | 低 | 中 | 高 |
|---|---|---|---|
| 高 | 中风险 | 高风险 | **严重** |
| 中 | 低风险 | 中风险 | 高风险 |
| 低 | 低风险 | 低风险 | 中风险 |

- **严重** = 升级路径：立即 flag 给决策 owner（见 4.3）。
- **高风险** = 必须带 mitigation 且 mitigation 有 owner；连续两个 review 周期未降级 → 升级。
- **中/低风险** = 常规跟踪，随 issue-record 定期盘点。

### 4.3 升级阈值（与脚手架 target_close 配合）

| 时间点 | 动作 | 判定细则 |
|---|---|---|
| 登记即日 | 标 state + owner + target_close | BLK/DEC 必须有 target_close；RSK 必须有 mitigation |
| **7 天** | **flag（⚠️ 红旗）** | open 超过 7 天且无进展事件 → 在 description 加 flag 标记 + 提醒 owner；同一风险连续两次 🟡（pm888 反西瓜）即升级或重新规划 |
| **14 天** | **escalate（升级）** | open 超过 14 天仍未收口 → state 置 `escalated`，填 `escalated_to`（新 Owner 或机构），并套用坏消息公式通报 |
| 30 天 | 审计兜底 | 30 天以上 open 必须有 escalation 记录（脚手架 Audit 钩子硬查） |

**flag 细则**：flag 不改变 state，只是"到点提醒"；escalate 才改变 state 并移交。判定是否升级看两问——"owner 有权解决吗？""缺什么才能解决？"两问任一答否 → 立即 escalate，不等 14 天。

## 5. 决策四象限复盘（pm888 §9.2，用于 DEC 条目升级）

DEC（Decision-in-waiting）收口后，复盘必须按四象限归类，**先命名象限、再写教训**：

| 象限 | 过程 | 结果 | 处理 |
|---|---|---|---|
| **技能 skill** | 好 | 好 | 沉淀为可复用打法，记录可复现条件 |
| **方差 variance** | 好 | 坏 | 什么都不改——好过程遇上差运气 |
| **运气 lucky** | 坏 | 好 | **最危险**——坏过程撞上好结果，正教坏习惯，必须警惕"下次还能赢"的错觉 |
| **学费 tuition** | 坏 | 坏 | 提炼教训，写出过程改进点 |

复盘模板（每个 DEC 收口一条）：

```text
## Outcome Review — [日期]
What happened: [实际结果]  vs. expected: [预期]
Quadrant: [技能/方差/运气/学费] — [原因]
Transferable lesson: [一句话，关于过程而非此事件]
```

**DEC 升级路由**：DEC 条目被裁决后，复盘落四象限；**运气象限的 DEC 要特别标记并追加一次复盘**（防止坏习惯固化）；技能象限的结论可回写为业务方下次决策的默认选项。每 ~10 次复盘跨条读，识别决策者的系统性偏差（pm888 §2.7 模式胜过单条）。

## 6. 问题呈现模板（Human Gate 用）

Human Gate 前按以下结构呈现（脚手架 issue-record SKILL.md §7：按类别与状态计数、critical top5、待决清单、accepted 风险、audit 结果）：

```markdown
## 问题清单呈现 · [日期]

### 1. 总览计数
| 类别 | 总数 | open | in_progress | blocked | accepted | resolved | escalated |
|---|---|---|---|---|---|---|---|
| BLK | | | | | | | |
| RSK | | | | | | | |
| DEC | | | | | | | |
| INF | | | | | | | |
| CLS | | | | | | | |
| OUT | | | | | | | |

### 2. Critical Top 5（按阻断影响排序）
| # | ID | 类别 | 标题 | owner | target_close | 升级状态 |
|---|---|---|---|---|---|---|
| 1 | | | | | | |

### 3. 待决清单（需决策者本周裁决）
| ID | 决策点 | 选项摘要 | 需要谁 | 最迟日期 | 不决策的后果 |
|---|---|---|---|---|---|

### 4. Accepted 风险（决策者已显式接受）
| ID | 风险 | 概率×影响 | 接受人 | 接受日期 |
|---|---|---|---|---|

### 5. 审计结果
- [ ] 每个 open 有 owner；BLK/DEC 有 target_close
- [ ] 30 天以上 open 有 escalation；7 天 flag / 14 天 escalate 已执行
- [ ] accepted 均为决策 owner 显式设置（非 AI 代设）
- [ ] 冲突条目（CLS/CONFLICT）已指派仲裁人
```

> 呈现口径遵守 pm888 状态诚实：🟡 必须带具名风险 + 概率；🔴（blocked）必须带明确诉求；指标与状态一致（计数表里红条目多，就不能给绿结论）。

## 7. 工作流程

1. **识别信号**：从任何产物的"待确认 / 矛盾 / 风险"信号中挑出候选问题。
2. **冲突扫描**：用 4 模式（来源/口径/数据/规则）对照现有素材，冲突一律登记为 CLS + P0 + 仲裁人。
3. **风险分级**：RSK 先过"老虎/纸老虎/大象"判定，再入概率×影响矩阵定级；严重/高直接走 4.3 升级路径。
4. **登记与定时**：登记经用户确认（AI 主动询问契约）；BLK/DEC 定 target_close，RSK 定 mitigation + owner。
5. **7 天 flag**：open 7 天无进展 → 打旗提醒 owner；连续两次 🟡 → 升级或重新规划。
6. **14 天 escalate**：仍未收口 → `escalated` + `escalated_to` + 坏消息公式通报。
7. **DEC 复盘**：DEC 裁决后四象限归类，先命名象限再写教训；运气象限追加复盘。
8. **Human Gate 呈现**：按 §6 模板输出计数 + critical top5 + 待决 + accepted + 审计结果。

## 8. 核心硬规则

1. **坏消息四段式**：事实→影响→在做→诉求，缺"诉求"就是 venting 不是管理；删 hedge、不预归咎。
2. **冲突恒 P0**：冲突按 4 模式全部挑出、登记、指派仲裁人；绝不自行调和选一个"方便说法"。
3. **升级有阈值**：7 天 flag / 14 天 escalate 是硬线；owner 无权限或缺资源时立即 escalate，不等 14 天。
4. **状态是预测不是情绪**：🟡 必须带具名风险+概率；🔴 必须带明确诉求；无事件不改善状态。
5. **accepted 只能由决策 owner 设**：AI 永不代设 accepted（脚手架铁律）。
6. **复盘先命名象限**：DEC 复盘必须先落四象限（技能/方差/运气/学费）再写教训；运气象限必须追加复盘。

## 9. 边界（Do Not）

- 不把"决策方案"写进 issue-record——只列"卡点/风险/待决"，方案交后续 Skill。
- 不替业务方接受风险、不替仲裁人定"以哪个说法为准"——只给建议采信与仲裁人。
- 不因"问题解决了"直接改 state 为 accepted——resolved 必须链接到关闭它的产物变更。
- 不用 hedge 词软化坏消息（"可能有点"/"稍微担心"）——不确定只在量化时保留。
- 不把纸老虎当老虎登记成严重风险，也不把大象（未说出的隐忧）漏掉——两类都点出来。
- 不把 Human Gate 呈现写成"全绿"——计数与结论必须一致，红条目多就得给红结论。
