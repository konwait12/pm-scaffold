# Audit Checklist · acceptance-criteria

每次提交 acceptance-criteria.md 产物前自审。先跑确定性校验器，再逐条过本清单。

## 1. Structural Gate（结构门：章节存在、ID 前缀齐全）

- [ ] 独立产物 `acceptance-criteria.md` 中包含「验收标准」章节，且每条 `AC-XXX` 都引用某个 `FEA-XXX`
- [ ] 至少存在一条 `AC-\d+` 标识，且未出现「待确认」占位 ID
- [ ] AC ID 全局唯一、稳定且不可复用；删除/合并后允许保留编号空洞，不为补洞重编号
- [ ] 每条 `AC-XXX` 都引用某个 `FEA-XXX`，没有游离于所有功能之外的孤儿验收标准
- [ ] 验收依据表头列与模板一致：`ID | 验收标准（Given/When/Then） | 量化阈值 | 来源目标 | 优先级`
- [ ] `python3 scripts/validate_artifact.py <acceptance-criteria.md> --json` 返回 `"ok": true`

## 2. Content Gate（内容门：验收依据产出是否完整且正确）

- [ ] 每个 P0 `FEA-XXX` 至少有 1 条主流程 AC + 1 条异常路径 AC；P1 功能按需覆盖，无遗漏也无空壳占位
- [ ] 每条 AC 都采用 Given/When/Then 三段式，缺一不可，且 `then` 的结果是可观测的系统产出，而非过程描述
- [ ] 每条 AC 只判定一个行为（原子），若一个验收需拆成多条才能独立执行，则已拆分
- [ ] 涉及性能、容量、时间、金额等可量化结果时，已写入具体阈值（如 `≤ 2 秒`、`≥ 99.9%`、`0 元`），而非「快速」「流畅」
- [ ] 量化阈值可回溯到 Stage 1 目标 `G-XXX`，未凭空设定与业务目标无关的数字
- [ ] 每条 AC 的通过/失败判据明确——给定输入，能否唯一判定成功与否；不可判定即打回重写
- [ ] 覆盖主流程 AND 主要异常路径（缺失、失败、拒绝、超时等），未只写 happy path
- [ ] `优先级` 与该 `FEA-XXX` 的优先级一致，无 P0 功能全部低优、P1 功能反而高优的错位

## 3. Boundary Gate（边界门：内容不泄漏到其他 work_item）

- [ ] 未写可执行的测试用例、断言脚本或自动化测试实现（→ 测试技能）
- [ ] 未定义领域业务规则、计算与强制逻辑（→ business-rules `BR-XXX`）
- [ ] 未写字段格式/长度/必填/跨字段校验规则（→ validation-rules `VL-XXX`）
- [ ] 未把「用户操作 → 系统响应」、UI 呈现与文案写进验收标准（→ interaction-rules `IX-XXX`）
- [ ] 未写状态迁移、触发事件与副作用（→ state-machine）
- [ ] 未写异常失败的处理流程、恢复方式（→ exception-handling）
- [ ] 未引入架构、API、数据库、测试框架等实现层细节；验收标准只描述行为与结果
- [ ] 与已产出的业务规则/校验规则无重复定义、无口径冲突，验收是对上述内容的度量而非重写

## 4. Semantic Gate（语义门：知识状态、可追溯性）

- [ ] 每条 `AC-XXX` 都标注来源：`FEA-XXX` → 目标 `G-XXX` / `ST-XXX`，可一路追溯
- [ ] 阈值与判据区分知识状态：来自已确认目标/决策的标 `FACT`/`DECISION`，推断补充的标 `AI_INFERENCE`，未知的标 `UNKNOWN`
- [ ] `Given` 前置条件与上游已确认的 UX、业务规则一致，未虚构前置状态或相互矛盾
- [ ] 反向检查：每个 P0 `FEA-XXX` 都至少有两条件为支撑（主流程 + 异常路径），无功能零验收
- [ ] AC 与已确认的业务规则 `BR`、校验规则 `VL` 在触发条件与预期结果上无冲突
- [ ] 无法量化的验收已降级为 `UNKNOWN` 并登记到 acceptance-criteria.md「待确认问题」，不静默编造阈值

## 5. Human Gate（人工门：可以提交）

- [ ] 阻塞性确认项（成功/失败定义、关键量化阈值、异常路径取舍）均已有明确答案，非阻塞项已注明原因
- [ ] 无 `待确认` 残留在已确认的 AC 行内；仍有占位的内容已降级为 `UNKNOWN` 并给出责任人
- [ ] 下游（QA / 研发验收）可无歧义地消费本产出：每条 AC 都能构造通过/失败的验证输入
- [ ] 与编排约定一致（在全部规则类 work_item 之后产出、作为最终验收依据），无越权写入
- [ ] 本 work_item 产出已写入独立产物 `acceptance-criteria.md`，且未改动其他 work_item 产物

## 6. 验收可验证性好/坏对比（advisory）

> 来源吸收：prd skillhub 的"验收标准可验证性"检查。advisory 级，不阻断 gate。

### 好的验收标准（可验证）
- "提交后订单状态转为 PROCESSING，3 秒内返回成功响应"——可观测行为 + 量化阈值
- "审批通过后余额扣减，扣减值与 BR-007 一致"——可追溯 + 可判定
- "未授权角色点击审批按钮，返回 403 且记录审计日志"——可构造通过/失败输入

### 坏的验收标准（不可验证，判不合格须改写）
- "Works correctly" / "正常工作"——无可观测行为
- "体验流畅" / "响应快速"——无量化阈值
- "符合要求"——无具体判据

### 规则
- 含"正常 / 流畅 / 快速 / 符合要求 / works correctly"等不可量化表述的 AC 判为不合格，须改写为"可观测行为 + 量化阈值"。
- 每条 AC 必须能构造通过/失败的验证输入；无法构造即标 `UNKNOWN` 交人工。

## 7. 新批次审计项（2026-08 第二轮吸收，advisory）

### 7.1 AI 功能验收 4 维度（来源 prd-writter，AI 功能时启用）
- [ ] 准确性：结果与预期一致的比例有量化阈值（如 ≥95%）
- [ ] 完整性：覆盖所有输入场景，缺字段/缺结果有判定
- [ ] 稳定性：同输入多次调用结果一致（含非确定性说明）
- [ ] 幻觉率：无中生有的输出有上限阈值与抽检方法
- [ ] 评测集覆盖 4 类用例：正常/边界/异常/对抗

### 7.2 字段三元组一致性（来源 product-spec-generator）
- [ ] 每个字段三处对齐：定义（VL-XXX）↔ 使用（页面/交互）↔ 枚举（状态/选项）
- [ ] 状态机（STATE-XXX）↔ 异常（EX-XXX）↔ 规则（BR-XXX）三元无冲突
- [ ] 交叉引用无悬空（BR/AC/E/FR 引用对象均存在）
