# 验收标准自检技法（Acceptance Criteria Self-Check）

> 来源吸收：`incremental-prd-collaboration` 的 `prd-output-review-rubric`（fetch → inspect → deep_check → scoring → decision 五步引擎、deep_check 只输出"问题+严重度+证据"、禁止建议、问题必可追溯原文）+ 高频遗漏检查清单（页面/按钮/倒计时/输入限制/状态/拦截/边界规则），以及 `product-spec-generator` 的可测试性要求（验收标准必须可测试、澄清门禁禁 TBD、模块十汇总全部验收项），作为 acceptance-criteria 的可选逐条 AC 自检能力。
> 定位：在 AC-XXX 行写完后，逐条过「GWT 完整性 → 阈值量化 → 4 类覆盖 → 可构造输入 → 追溯 → deep_check」六步自检，把不可测、空泛、缺覆盖的 AC 挡在 Audit 之前。
> 触发：Generate 完 AC 行后、Audit 前逐条自检；或 Human Gate 前对 AC 区块整体 deep_check。**按需加载，不设全局闸门**。

## 1. 输入映射（pm-scaffold 语境）

| 外部 skill 输入 | pm-scaffold 对应产物 | 说明 |
|---|---|---|
| deep_check 五步引擎（prd-output-review-rubric） | acceptance-criteria Audit 阶段 | 问题清单化，禁止输出建议 |
| 高频遗漏清单（incremental） | AC 的 4 类覆盖范围 | 正常/边界/异常/权限哪类漏了 |
| 验收标准必须可测试（product-spec-generator） | AC 可构造通过/失败输入 | 不可构造即不合格 |
| 澄清门禁禁 TBD（product-spec-generator） | AC 行禁止 `待确认` 占位 | 缺口转 issue 交人工 |
| 模块十汇总（product-spec-generator） | AC 回指 FEA-XXX/BR-XXX/G-XXX | 每条 AC 可追溯、无孤儿 |

> **上游未 confirmed，不启动 AC 自检**：FEA/BR/VL/ST/EX/G 未确认时只登记缺口，不替 AC 编造阈值或判据。

## 2. GWT 三要素完整性检查

对每条 AC 拆解 Given / When / Then，**缺一不可**。缺省即不合格，回到 Generate 补全。

| 要素 | 职责 | 缺省症状 | 判定方法 | 修正 |
|---|---|---|---|---|
| Given（前置条件） | 描述进入本行为的已确认前置状态 | 无前置，或前置无来源 | 前置必须可指向上游 BR/VL/ST/EX 已确认条件 | 补"已登录 XX 角色"等可验证前置 |
| When（触发动作） | 描述操作者做了什么 | 无主语/无操作者（"当提交时"） | 动作必须有明确操作者与动词 | 补"当审批经理点击通过时" |
| Then（预期结果） | 描述可观察的系统结果 | 只写内部调用 / 无结果 | 结果必须是从外部可观察的状态/产出 | 补可观察结果 + 阈值 |

### 2.1 常见缺省示例

| ❌ 不合格 | 缺了什么 | ✅ 合格 |
|---|---|---|
| 点击提交后系统应正确处理 | Then 无结果 | Given 已登录提交人填写完整表单，when 点击提交，then 3 秒内进入二次确认页 |
| 当用户符合条件时允许通过 | Given/When 无操作者 | Given 审批经理持有审批权限，when 点击通过，then 工单进入已通过状态 |
| 系统应显示正确信息 | Then 无可判定结果 | Given 审批被驳回，when 查看工单详情，then 展示驳回原因字段非空 |

## 3. 阈值量化检查（空泛词检测）

来源吸收：product-spec-generator 澄清门禁（非功能指标含糊如"导出文件大小上限/并发数/超时"未给具体值必须追问）+ 脚手架 audit-checklist §6 好坏对比。本技法给**逐条 AC 的判定流程**。

### 3.1 空泛词黑名单

| 空泛词 | 为什么不合格 | 改写方向 |
|---|---|---|
| 正常 / 正常工作 / Works correctly | 无可观察行为 | 描述具体状态变化与产出 |
| 流畅 / 快速 / 及时 | 无基线 | ≤ 2 秒 / ≤ 500ms（追溯 G-XXX） |
| 合理 / 符合要求 | 无判据 | 给出判定标准（字段值/数量/状态） |
| 尽量 / 大约 / 大概 | 不可复现 | 给确定阈值 |
| 提升体验 / 优化 | 目标性而非行为 | 拆为可测行为（转化率/时长/成功率） |

### 3.2 可量化维度清单（逐维核对）

| 维度 | 量化形式 | 示例 |
|---|---|---|
| 性能 | 时长/吞吐/并发 | 响应 ≤ 2 秒；支持 ≥ 100 并发 |
| 容量 | 上限/下限 | 单次上传 ≤ 20MB |
| 时间 | 时点/时长 | 超时 30 分钟自动取消 |
| 金额 | 数额/百分比 | 扣减 = BR-007 计算值；退款 = 100% 原路 |
| 比例 | 成功率/覆盖率 | 预约成功率 ≥ 99% |
| 一致性 | 与规则一致 | 校验错误条数 = 0，与 VL-XXX 一致 |

> **阈值可溯源**：阈值必须能回溯到已确认 G-XXX / BR-XXX；AI 推断的阈值标 `AI_INFERENCE` 交人工拍板，不得静默当事实。

## 4. 4 类用例覆盖检查（正常 / 边界 / 异常 / 权限）

来源吸收：incremental-prd-collaboration 高频遗漏清单 + product-spec-generator 模块八（异常至少覆盖空数据/网络/权限/业务约束 4 类）。每个 P0 FEA 至少：**主流程 AC ≥1 + 异常/边界 AC ≥1**；权限类 AC 在 to B 场景**必查**。

| 类型 | 检查内容 | 高频遗漏（incremental 清单摘录） |
|---|---|---|
| 正常 | 主路径成功结果 | 成功后的去向、会话有效性、主按钮文案对应行为 |
| 边界 | 输入限制、边界值、倒计时、账号限制 | 倒计时文案与重试文案、输入限制与可点击条件、账号限制和边界规则 |
| 异常 | 失败/超时/拦截的兜底结果 | 成功/失败/异常三态齐全、自动处理条件与强拦截条件、阻断文案与报错文案 |
| 权限 | 未授权角色/越权操作的拒绝结果 | 无权限时的拒绝行为、审计记录、操作日志 |

### 4.1 判定流程

1. 列出该 FEA 的关键交互点（按钮/提交/查询/操作）。
2. 对每个交互点问：正常怎么验？边界值怎么验？失败怎么验？谁不能做？
3. 四类任一缺失 → 补 AC 或标 `待确认`（说明不适用原因）。

## 5. 可构造验证输入检查

来源吸收：product-spec-generator 可测试性要求——验收标准必须可测试，任何人能仅凭构造输入判定通过/失败。

### 5.1 判定规则

- 每条 AC 必须能给出 **一组通过输入** 与 **一组失败输入**。
- 无法构造验证输入 → 该 AC 降级为 `UNKNOWN`，登记到待确认问题，不静默保留。

### 5.2 通过/失败输入构造表

| AC | 通过输入（应通过） | 失败输入（应失败） | 判定标准 |
|---|---|---|---|
| 审批通过 AC | 审批经理 + 合法工单 + 审批备注 ≥10 字 | 审批备注 <10 字 | 前者状态=已通过，后者拒绝并提示 |
| 超时 AC | 超过 8 小时未响应 | 未超时触发 | 前者自动置已超时，后者不触发 |
| 权限 AC | 审批经理角色 | 提交人角色点击通过 | 前者成功，后者返回 403 + 审计日志 |

> **澄清门禁**：任何 `待确认` / `TBD` / `可再细化` 占位严禁进入 AC 正文；发现即触发 Clarify 追问或转 issue-record。

## 6. 追溯检查（AC 回指 FEA / BR / G）

来源吸收：product-spec-generator 引用完整性（每处 AC 引用模块十必须存在对应条目；引用对象不存在即悬空）。

### 6.1 引用完整性核对表

| AC 字段 | 必须回指 | 悬空症状 |
|---|---|---|
| 挂载功能 | FEA-XXX（来自 feature-list.md） | AC 未引用任何 FEA-XXX |
| 触发条件来源 | BR-XXX / VL-XXX / ST-XXX / EX-XXX | 前置条件无上游规则支撑 |
| 量化阈值 | G-XXX | 阈值无目标来源 / 凭空设定 |
| 优先级 | 与 FEA 优先级一致 | P0 功能全低优、P1 功能反高优 |

### 6.2 判定流程

1. 每条 AC 标注 `FEA-XXX → G-XXX` 链路。
2. 阈值追溯到已确认 G-XXX；推断阈值标 `AI_INFERENCE`。
3. 交叉引用逐号核对（AC/BR/VL/ST/EX 均存在），悬空即 P0。

## 7. deep_check 纪律（问题 + 严重度 + 证据）

来源吸收：incremental-prd-collaboration `prd-output-review-rubric` §3.3——**deep_check 只允许输出"问题是什么、严重度是什么、证据是什么"，禁止输出任何修改建议**（"可以补充""建议增加"一律禁止）。

### 7.1 输出表模板

| ID | 模块 | 严重度 | 问题（不带建议） | 证据（原文依据） |
|---|---|---|---|---|
| AC-001 | 验收标准 | critical / major / minor | 描述现象 | 章节 + 原文片段 |

### 7.2 严重度定义

| 级别 | 定义 |
|---|---|
| critical | 核心验收缺失导致无法判断完成；规则与验收明显冲突；主流程无法闭环；关键异常场景缺失 |
| major | 阈值模糊、覆盖缺类、可追溯性不足 |
| minor | 表述冗余、口径不统一、非阻塞 |

### 7.3 纪律硬约束

- 问题必须附原文依据（章节 + 原文片段），禁止凭印象下结论。
- `finding` 只描述问题，不得夹带建议。
- 跳过 deep_check、只查部分 AC、输出散文式结论 → 均不合格。

## 8. 完整示例：to B 审批 AC 自检（正常 / 超时 / 权限不足 / 并发）

**输入**：FEA-008（工单审批）+ BR-021（审批 8 小时超时自动流转）+ BR-025（驳回需备注 ≥10 字）+ G-003（审批时效：80% 工单 24 小时内完成）+ 角色（提交人 / 审批经理）。

### 8.1 4 条 AC（完整 GWT）

```
AC-101 正常：Given 审批经理持有待处理工单 W-001 且备注 ≥10 字，
       when 点击通过，
       then 工单状态变为已通过，提交人收到通知，且响应时间计入 G-003。

AC-102 超时：Given 工单 W-002 处于待审批且已超过 8 小时，
       when 触发系统定时任务，
       then 工单自动置为已超时，通知双方，产生超时记录（关联 EX-031）。

AC-103 权限不足：Given 提交人以客户视角打开审批操作页，
       when 尝试点击通过，
       then 操作被拒绝（无状态变化），且写入审计日志。

AC-104 并发：Given 审批经理 A、B 同时打开工单 W-003，
       when A 点击通过成功，
       then B 提交操作返回"已被处理"，工单不重复流转，终态唯一。
```

### 8.2 逐条自检结果

| AC | GWT 完整 | 阈值量化 | 4 类覆盖 | 可构造输入 | 追溯 | 结论 |
|---|---|---|---|---|---|---|
| AC-101 | ✅ 三段齐全 | ✅ 备注 ≥10 字、响应时间计 G-003 | 正常 | ✅ 通过/失败可构造 | FEA-008 → G-003 / BR-025 | PASS |
| AC-102 | ✅ | ✅ 8 小时、自动流转 | 异常(超时) | ✅ | BR-021 / EX-031 | PASS |
| AC-103 | ✅ | ✅ 无状态变化（可判） | 权限 | ✅ 403+审计 | BR 权限规则 | PASS |
| AC-104 | ✅ | ✅ 终态唯一 | 边界(并发) | ✅ 双操作可复现 | ST-XXX 终态语义 | PASS |

### 8.3 deep_check 输出（示例）

| ID | 模块 | 严重度 | 问题 | 证据 |
|---|---|---|---|---|
| D-01 | 验收标准 | major | AC-101 的"响应时间计入 G-003"无时间窗口口径，无法独立判定 | §8.1 AC-101 原文 |
| D-02 | 验收标准 | minor | AC-102 与 AC-103 通知文案未指定渠道 | §8.1 AC-102/103 原文 |

> 处理：D-01 属阻塞（口径缺失）→ 转 Clarify 问 metric_owner 时间窗口；D-02 非阻塞 → 记录到待确认问题。

## 9. 工作流程

1. **逐条拆解**：每条 AC 拆 Given/When/Then，缺省即打回。
2. **阈值扫描**：空泛词黑名单逐词扫，命中即改写并追溯 G-XXX。
3. **四类覆盖**：按 FEA 交互点核对正常/边界/异常/权限，缺类补 AC 或标 `待确认`。
4. **构造输入**：每条 AC 写通过/失败输入各一组；不可构造转 `UNKNOWN`。
5. **追溯核对**：FEA/BR/G 链路逐号核对，悬空即 P0。
6. **deep_check**：对 AC 区块整体出问题表（问题+严重度+证据），禁止带建议。
7. **收口**：critical 必须修复；major 修复或交业务确认；minor 记录。全部通过进入 Audit。

## 10. 核心硬规则

1. **GWT 三段缺一不可**：Given 有来源、When 有操作者、Then 有可观察结果；缺省即不合格。
2. **空泛词零容忍**：含"正常/流畅/快速/符合要求/合理"的 AC 判不合格，须改写为可观测行为 + 量化阈值。
3. **四类覆盖必查**：正常/边界/异常/权限四类；to B 场景权限类 AC 必查，缺失即补。
4. **可构造输入是底线**：每条 AC 能构造通过/失败输入；不能构造就标 `UNKNOWN` 交人工，禁止虚留。
5. **追溯不悬空**：AC 回指 FEA-XXX/BR-XXX/G-XXX；悬空引用 = P0。
6. **deep_check 不带建议**：只输出问题 + 严重度 + 证据；"可以补充""建议增加"一律禁止。
7. **TBD 不进正文**：`待确认` 占位严禁进入 AC 行；缺口转 issue-record 或 Clarify。

## 11. 边界（Do Not）

- 不写可执行测试脚本 / 断言代码（属 QA）。
- 不把接口调用 / 数据库操作写进 `then`（只写可观察结果）。
- 不重写 BR/VL/ST/EX 规则——AC 是对上游的度量，不是复制。
- 不在 deep_check 阶段给修复建议——建议留到后续修复轮。
- 不替业务方拍板阈值——阈值来自 G-XXX，推断值标 `AI_INFERENCE`。
- 不因"覆盖不全"而给空壳 AC 占位——缺什么就标 `待确认` 什么。

## 12. 质量自检清单

- [ ] 每条 AC 的 Given/When/Then 三段齐全，无缺省
- [ ] 空泛词扫描通过（无"正常/流畅/快速/符合要求/合理"）
- [ ] 可量化结果全部带阈值，且阈值追溯 G-XXX / BR-XXX
- [ ] 正常/边界/异常/权限四类覆盖已核对，to B 含权限 AC
- [ ] 每条 AC 可构造通过/失败输入各一组
- [ ] AC 回指 FEA-XXX/BR-XXX/G-XXX，无悬空引用
- [ ] deep_check 已执行：输出表格含 ID/模块/严重度/问题/证据
- [ ] deep_check 未夹带任何修改建议
- [ ] 无 `待确认`/`TBD` 残留在 AC 行内
- [ ] AI 推断阈值已标 `AI_INFERENCE` 并登记待确认
