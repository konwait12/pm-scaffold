# 研发评审版 PRD 硬标准 13 项（Dev-Review PRD Standard-13）

> 来源吸收：`pm-master-prosl` 的 SKILL.md §7「研发评审版 PRD 硬标准」、`workflows/write-prd.md` 输出格式与质量自检、`references/anti-patterns-and-faq.md` 反模式清单，作为 feature-list 功能清单的信息密度参考。
> 定位：给「功能清单要写到多细才算研发可评审」一个 13 项硬标准——每一项给达标判据，配合 8 条反模式纠偏，保证 FEA-XXX 产出的信息能支撑研发评审，而不是一张只有功能名的薄表。
> 触发：Generate FEA-XXX 时对照信息密度；Human Gate 前判断「这份功能清单是否达到研发评审标准」时。**按需加载，不设全局闸门。**

## 1. 输入映射

| 外部 skill 输入 | pm-scaffold 对应产物 | 说明 |
|---|---|---|
| 研发评审版 PRD 硬标准 13 项 | feature-list.md（FEA-XXX 功能表） | 每项 FEA 的信息密度对照标准 |
| 输出格式（背景/目标/用户场景/范围/验收等 12 节） | feature-list + 下游各 work_item 产物 | 功能清单只承担 WHAT，其他节由下游 work_item 承担 |
| 反模式 8 条 | FEA-XXX 生成过程 | 防「把老板意见写进功能」等错误 |
| 「信息不足先出初稿」策略 | 稀疏输入降级输出 | FEA 无法写细时列假设与待确认问题 |

## 2. 13 项硬标准（每项含达标判据）

默认要求：用户要 PRD 且没有明确说「简版」时，按研发评审版标准覆盖以下 13 项。对 feature-list 而言，**功能清单必须为这 13 项提供可消费的输入**。

| # | 标准项 | 达标判据 | feature-list 侧对应 |
|---|---|---|---|
| 1 | 版本 / 评审信息 | 有版本号、作者、状态、评审人；修订记录含版本+日期+修改内容 | feature-list 头部元数据 + 变更摘要 |
| 2 | 目标与非目标 | 目标可衡量（数字+期限）；明确不做什么（Non-goals / Out-of-Scope） | 功能边界 in/out 表述 |
| 3 | 北极星指标、过程指标、反向指标 | 每层指标都有定义与口径；反向指标（护栏）防止赢了指标害了用户 | FEA 关联的目标引用 |
| 4 | 用户角色、场景、任务流 | 角色明确（谁能用）；场景有触发条件；任务流从触发到完成闭环 | FEA 链接的 ST-XXX 故事 |
| 5 | 组件级需求 | 需求拆到组件粒度（按钮/表单/列表/弹窗级别），不是整页一句话 | 功能粒度建议与故事匹配 |
| 6 | 任务 / 配置表 | 关键任务有配置表（参数/默认值/选项/校验），配置化需求不模糊 | 功能内需配置项时的字段线索 |
| 7 | 状态机或关键状态流转 | 状态枚举完整（含起止）、迁移可判定、无死锁状态 | 链接 SM-XXX（下游状态机） |
| 8 | 主路径、分支、异常、空状态、权限流程 | 主路径 + 至少覆盖：分支、异常、空状态、权限差异 | 功能边界需声明覆盖的流程类型 |
| 9 | 埋点字段 | 关键事件有事件名、触发时机、上报字段 | 链接 tracking-plan（EV-XXX） |
| 10 | 接口/配置建议 | 接口/配置仅给业务约束与建议，标注「待研发确认」，不写死实现 | 不越权到 API 定义 |
| 11 | 异常降级与安全边界 | 每个异常有降级方案；安全边界（权限/数据/合规）显式声明 | 链接 EX-XXX / BR-XXX |
| 12 | 验收用例 | 验收标准可测试（Given/When/Then 或可观察行为），每功能 ≥1 条 | FEA 一句话描述可支撑 AC 消费 |
| 13 | 结果交付路径 | 说清成功后的去向、结果如何交付给用户/系统 | 功能描述含输出物去向 |

## 3. 达标判据细化（研发/测试能否直接下一步）

对每个 FEA-XXX，自问四个问题（对应 write-prd 质量自检）：

1. **背景是否说明用户痛点和业务目标？** —— 没有背景的功能名是悬空功能。
2. **目标是否可衡量？** —— 「提升体验」不达标，「注册完成率提升至 75%」达标。
3. **范围是否有明确不做什么？** —— 只写 in 不写 out 会让评审争议。
4. **验收标准是否可测试？** —— 测试同学能否直接据此写用例。

## 4. 信息不足时的策略（先出初稿，不空等）

- 信息不足时**不要停在追问**：先输出「可评审初稿 + 待确认问题」。
- 明确标注三类：**已确认信息**、**基于假设补全的信息**、**待确认问题**。
- 例如一句话需求「帮我写一个会员积分功能 PRD」→ 先给初稿（暂定目标/本期范围/核心流程/验收标准/必须确认的问题 5 条），再等业务确认积分规则、成本、上线范围。
- 不把业务规则拍脑袋写成最终结论。

## 5. 反模式 8 条（对照纠偏）

| # | 反模式 | 错误表现 | 正确做法 |
|---|---|---|---|
| 1 | 把老板意见直接写成需求 | 老板说「做会员积分」，PRD 直接写「上线会员积分」 | 先还原业务问题与用户场景，功能作为方案之一 |
| 2 | 只写功能，不写用户价值 | 只列「新增按钮、列表、筛选、导出」 | 每个核心功能连接用户场景、收益与业务目标 |
| 3 | PRD 背景模糊 | 只写「为了提升体验」 | 背景含现状、问题、影响、目标用户、业务目标、约束 |
| 4 | 验收标准不可测试 | 写「页面简洁、体验流畅」 | 用可观察/可触发/可判断标准，必要时 Given-When-Then |
| 5 | 只写正常流程，不写异常流程 | 只写成功支付/成功提交 | 至少覆盖空状态、边界值、权限不足、网络异常、重复操作 |
| 6 | 优先级评分伪精确 | RICE/ICE 分数填满但无依据 | 每个分数写理由；Confidence 绑定证据来源；说明放弃什么 |
| 7 | 指标只看增长不看质量 | 只看注册数/访问量上涨 | 同时定义北极星、输入指标、健康指标、护栏指标 |
| 8 | 发布说明只写技术变更 | 写「优化接口、修复 bug」 | 按对象拆分：用户版/内部版/客服版/销售版/技术变更版 |

## 6. 工作流程

1. Generate FEA-XXX 前：按 13 项标准审视「每个功能要写到什么粒度」。
2. 每个 FEA 填写时：对照达标判据——是否可追溯故事、边界 in/out 清晰、粒度与故事匹配。
3. 信息不足：走稀疏输入降级——标 UNKNOWN、列待确认问题、停在 needs_user_input。
4. 逐条对照反模式 8 条：发现「把老板意见写进功能」「只写功能不写价值」等立即重写。
5. Audit 阶段：以 13 项标准核对功能清单的信息密度，缺口路由回上游或登记。
6. Human Gate 前：用「研发/测试能否直接下一步」四问做最终检查。

## 7. 核心硬规则

1. 功能清单的信息密度以 13 项标准为参照，不能只有功能名。
2. 每个 FEA 必须可追溯故事、边界 in/out 清晰、优先级带理由。
3. 验收性表述必须可测试，禁止「体验流畅」「页面简洁」类模糊词。
4. 指标必须有定义与口径，反向/护栏指标不可省。
5. 接口/配置只给建议与业务约束，标「待研发确认」，不写实现细节。
6. 信息不足先出初稿 + 列待确认问题，不空等也不脑补。

## 8. 边界（Do Not）

1. 不在 feature-list 中展开完整 PRD 的 13 项正文——功能清单只承担 WHAT，其他项由下游 work_item（functional-flow / business-rules / state-machine / tracking-plan 等）承担。
2. 不写 API 路径、HTTP 方法、异常码、数据库结构、字段类型。
3. 不把老板/干系人一句话当最终需求直接入库。
4. 不用伪精确的评分掩盖主观偏好——分数必须带理由与证据。
5. 不因信息不足就编造业务规则。
6. 不把 13 项标准当作机器校验——validate_artifact.py 结构校验仍必须运行。

## 9. 质量自检清单

- [ ] 每个 FEA-XXX 可追溯到 ≥1 个 ST-XXX，边界 in/out 清晰，优先级带理由
- [ ] 功能描述含「用户痛点/业务目标」连接，非纯功能名列表
- [ ] 可测试表述已量化（数字+期限），无「体验流畅」类模糊词
- [ ] 涉及的指标有定义与口径，反向/护栏指标已考虑
- [ ] 覆盖主路径 + 分支/异常/空状态/权限的声明（链接下游 skill）
- [ ] 接口/配置类信息仅给建议并标「待研发确认」
- [ ] 未出现 API 路径/HTTP 方法/异常码/DB 结构/字段类型
- [ ] 对照反模式 8 条无命中；稀疏输入已走降级流程
