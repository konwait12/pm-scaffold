# 功能停止条件技法（Kill Criteria）

> 来源吸收：work buddy `product-management` skill 的 Kill Criteria 模板（Usage Threshold 用量阈值 / Cost Ceiling 成本上限 / Time Limit 时间上限 / Metric Guardrail 指标护栏 / Qualitative Signal 定性信号）、SKILL.md「Prioritization & Saying No」的每功能应预设停止条件（"every feature should have a pre-defined stop condition"）、「What to Stop Doing」季度停做四问（<5% 用量→移除 / 无可测结果→停或转向 / 成本超值→下架 / "一直这样做"→质疑）、以及 Bridge Migration 桥接替代规则（吸收率 ≥80% 维持 14 天 + 无留存回退才可下线旧功能），作为 feature-list 的可选落地能力。
> 定位：feature-list 现状只定"做哪些、什么优先级"；本文档补"何时停止做"——给每个 FEA-XXX 附加「触发即降级/移出」的停止条件，让功能清单带自毁预案，防止"做完才发现不该做"与"不敢砍"。
> 触发：功能清单生成后需要给 FEA 定停止条件时；范围收口争议（砍不掉/全要保留）时；评审阶段需回答"什么证据出现就该停"时。**按需加载，不设全局闸门**。

## 1. 输入映射（pm-scaffold 语境）

| 外部 skill 输入 | pm-scaffold 对应产物 | 说明 |
|---|---|---|
| Kill Criteria 模板（用量/成本/时间/护栏/定性） | feature-list.md 每个 FEA-XXX 的"停止条件"标注 | 停止条件四类 + 定性信号，落地为 FEA 表附加列或补充表 |
| 季度"停做"四问（What to Stop Doing） | 功能清单评审（Audit / Human Gate 前） | 对存量功能做"该不该继续"审查的四个问题 |
| Bridge Migration 桥接替代规则 | 被替代功能的移除决策 | 新旧功能并行期以"吸收率 + 时长 + 无回退"三条件决定何时下线旧功能 |
| 事前验尸（Pre-Mortem，kill-criteria-template §Pre-Mortem） | FEA 停止条件的最可能失败原因 | 先写"最可能失败原因"再写停止条件，停止条件才有依据 |

> **停止条件是"结果判据"不是"功能方案"**：每条停止条件必须可测量（有数值/时间/事件），写"用户不满意就停"不算停止条件。

## 2. Kill Criteria 四类 + 定性信号（吸收 kill-criteria-template）

给每个 FEA-XXX 从以下五类中选填适用的停止条件（不必五类全填，但至少 1 条可测）：

| 类别 | 模板句式 | 示例（to B） |
|---|---|---|
| **用量阈值 Usage Threshold** | 上线后 X 周内，目标用户采用率 < Y% → 停止/降级 | 上线 6 周后周活客户数 < 30 → 降级 P1 |
| **成本上限 Cost Ceiling** | 研发投入超过 X 人周 / Y 元，或上线后维护超过 Z 小时/月 → 暂停重评 | 超过 12 人周仍未提测 → 强制范围瘦身 |
| **时间上限 Time Limit** | 未在 X 日期前上线 → 砍或大幅降级；若延期必须先做范围复审 | 未在 Q2 末上线 → 移出本期范围 |
| **指标护栏 Metric Guardrail** | [护栏指标] 劣化超过 X% → 回滚/暂停 | 审批通过率较基线下降 > 5% → 暂停放量 |
| **定性信号 Qualitative Signal** | 反馈访谈中 X/Y 个用户表示无价值，或困惑/投诉工单每周 > Z 条 | 5 个试用客户中 3 个表示"没有解决任何问题" |

- 停止条件里的**数字必须写死目标值**（30 客户 / 12 人周 / 5% / 3 个），空模板数字 = 没写。
- 每条停止条件给**测量方法**：数据从哪来（埋点/工单/访谈）、谁负责采集、何时复查（对应评审时点）。

## 3. 每 FEA 附加「触发即降级/移出」停止条件

落地方式二选一（推荐 B，不破坏 FEA 主表结构）：
- **A. FEA 表附加列**：在功能清单表加"停止条件（Kill-if）"列，每行一句话。
- **B. 补充停止条件表**（推荐）：FEA 主表保持不动，另建"FEA 停止条件表"：

| FEA | 停止条件类别 | 触发判据（可测） | 触发后的动作 | 测量方法 | 复查时点 |
|---|---|---|---|---|---|
| FEA-001 客户名单导入 | 用量阈值 | 6 周后周活 < 30 客户 | 降级 P1，暂缓迭代 | 埋点周活 | 上线第 6 周 |
| FEA-005 超额折扣审批流 | 指标护栏 | 审批通过率较基线降 > 5% | 暂停放量、回滚 | 审批流埋点 | 每周 |
| FEA-008 操作日志审计 | 时间上限 | 未在 Q2 末上线 | 移出本期范围 | 排期表 | Q2 末 |

**触发后的动作三选一**：`降级`（P0→P1/P2，暂缓投入）/ `移出`（移出本期范围，进 backlog）/ `回滚`（功能已上线则撤回/关停）。写清触发动作，避免触发时再开会决定。

> 每个 FEA 至少 1 条停止条件；写不出的 FEA = 该功能的价值假设未想清，标 `待确认` 进 Clarify。

## 4. 季度"停做"四问（What to Stop Doing Quarterly Review）

功能清单评审（Audit / Human Gate 前）对**存量/拟保留功能**逐条过四问（吸收 product-management「What to Stop Doing」）：

1. **用量问**：哪些功能使用率 < 5%？→ 移除候选。
2. **结果问**：哪些投入没有产生可测量的业务结果？→ 停或转向。
3. **成本问**：哪些持续成本（维护/支持）超过其创造的价值？→ 下架。
4. **惯性问**：哪些是在做"因为一直这么做"、并没有人真正要求的功能？→ 质疑其存在。

四问输出：保留 / 降级 / 停做（附一句理由）。**停做不等于删需求**——停做的功能记录去向（backlog / 二期 / 彻底废弃），防止反复争论（呼应 feature-priority-quant.md §3 Won't 写原因）。

## 5. 桥接替代规则（Bridge Migration，可选）

当新功能替代旧功能时，不硬砍旧功能，用桥接迁移保护用户（吸收 product-management Bridge Migration）：

1. **并行期**：新旧功能同时存在，默认导向新体验，旧路径可回退。
2. **吸收指标**：旧功能用户中改用新功能完成同一任务的比例。
3. **下线三条件**：吸收率 ≥80% + 该比例维持 14 天 + 无留存回退。三条件全满足才下线旧功能。
4. **免桥接场景**：安全漏洞 / 合规要求 / 用量近零（<1% MAU）的功能可直接下线并公告。

## 6. 完整示例：to B 后台 8 个功能的停止条件

**背景**：企业客户管理系统后台迭代（与 feature-priority-quant.md §6 同一场景，8 个 FEA）。角色：销售、销售主管、财务、系统管理员。

| FEA | 功能 | 优先级 | 停止条件（Kill-if） | 触发动作 |
|---|---|---|---|---|
| FEA-001 | 客户名单批量导入 | P0 | 上线 6 周后周活 < 30 客户 | 降级 P1 |
| FEA-002 | 销售跟进记录 | P0 | 录入日活 < 20 人 | 降级 P1 |
| FEA-003 | 角色权限管理 | P0 | 审计抽查发现 1 例越权（合规红线） | 立即修复，不降级 |
| FEA-004 | 销售漏斗报表 | P1 | 上线 8 周后月打开客户 < 10 家 | 移出本期范围 |
| FEA-005 | 审批流（超额度折扣） | P1 | 审批通过率较基线降 > 5% | 暂停放量 |
| FEA-006 | 企微消息推送 | P2 | 渠道方案 4 周内未定 | 移出本期范围 |
| FEA-007 | 数据导出（CSV） | P2 | 上线 4 周后导出请求 < 5 次/周 | 移出本期范围 |
| FEA-008 | 操作日志审计 | P1 | 未在 Q2 末上线 | 移出本期范围 |

**评审对照**：
- P0 也有停止条件（FEA-001/002 用量、FEA-003 合规红线）——P0 ≠ 无限投入。
- 触发动作明确（降级/移出/立即修复），无"到时候再说"。
- 季度四问覆盖：FEA-004/007 属"用量问"候选，FEA-006 属"结果问"（渠道未定 = 无明确结果）。

## 7. 工作流程

1. **先写失败原因（Pre-Mortem）**：对每个 FEA 先答"最可能失败原因是什么"，再据此写停止条件。
2. **定停止条件**：按 §2 五类选 ≥1 条，数字写死、给测量方法与复查时点。
3. **落表**：按 §3 方式 B 建"FEA 停止条件表"，触发动作三选一写清。
4. **季度四问**：评审时对存量/拟保留功能过四问，输出 保留/降级/停做 + 理由。
5. **桥接评估**（有替代场景时）：按 §5 三条件决定旧功能下线时点。
6. **输出**：停止条件表并入 feature-list.md；停做项记录去向。

## 8. 核心硬规则

1. **每 FEA 至少 1 条可测停止条件**：数字写死、给测量方法；写不出 = 价值假设未想清。
2. **触发动作三选一**：降级/移出/回滚，写清触发时怎么做，不临时开会决定。
3. **P0 也有停止条件**：优先级高 ≠ 无限投入，合规/安全红线类停止条件优先级最高。
4. **停做要写去向**：停做的功能记录进 backlog/二期/废弃，防止反复争论。
5. **护栏指标必须不劣化**：指标护栏触发即暂停放量/回滚，不靠"再观察观察"拖延。
6. **桥接三条件全满足才下线**：吸收率 + 时长 + 无回退缺一不可（免桥接场景除外）。

## 9. 边界（Do Not）

- 不替代优先级定档（feature-priority-quant.md）——停止条件与优先级并存，不是二选一。
- 不写研发排期/资源分配细节（→ 超出 PRD-only 范围）——停止条件只定判据与触发动作。
- 不替业务方做"砍不砍"决策——AI 产出停止条件与四问结果，最终取舍由产品/业务负责人裁决。
- 不把停止条件写成功能需求——"用户不用就停"是结果判据，不是要加的功能。
- 不为凑条件编造不可测信号——数据不可得时标 `待确认`，不填空模板数字。
