# 规则决策表技法参考（Rule Decision Table）

> 来源吸收：`research-to-prd`（juloko__skillhub）的 references/rule-modeling.md「规则梳理 → 决策表建模」+ references/rule-modeling.md 完备性检查，作为 business-rules 的可选落地能力。
> 定位：business-rules 产出的 BR-XXX 规则文本是权威；本文档提供"把多条件判定结构化为决策表并做完备性检查"的技法，用于逼出组合穷尽、边界含糊、规则冲突三类人工书写时必然出现的漏洞。
> 触发：当一条业务判定存在 2 个及以上条件（各含多态），或业务方给了规则梳理类素材（Excel/条文/零散听记）需建模时使用。**按需加载，不设全局闸门**。

## 2. 决策表结构（吸收自 rule-modeling.md）

### 2.1 为什么必须用决策表

自然语言规则（"金额大于 1000 要审批，但 VIP 不用"）存在三大陷阱：

- **组合爆炸被省略**：2 个条件各 2 态 = 4 种组合，人常只写其中 2 种。
- **边界含糊**：">1000" 还是 "≥1000"？1000 本身走哪条？
- **冲突未消解**：同一条件两个规则给出不同动作，谁优先？

决策表把"条件桩 + 动作桩 + 规则列"摊开，一眼就能看出漏洞。

### 2.2 决策表结构示例（吸收自 rule-modeling.md，BR-01 工单审批路由）

```
规则编号：BR-01  名称：工单审批路由
条件桩            | 规则1 | 规则2 | 规则3 | 规则4 | 规则5(默认)
-----------------------------------------------------------
金额 ≥ 1000      |  Y   |  Y   |  N   |  N   |  -   (任意)
提交人 = VIP     |  Y   |  N   |  Y   |  N   |  -   (任意)
-----------------------------------------------------------
动作：转主管审批  |  X   |  X   |  -   |  -   |  -   (任意)
动作：自动通过   |  -   |  -   |  X   |  -   |  -   (任意)
动作：转财务复核 |  -   |  -   |  -   |  X   |  -   (任意)
动作：走默认流程 |  -   |  -   |  -   |  -   |  X
```

单元格约定：

- `Y` = 条件成立，`N` = 不成立，`-` = 不关心（任意）
- `X` = 该规则触发此动作
- 最后一列通常是"兜底/默认动作"列，覆盖所有没被显式命中的组合

### 2.3 完备性 6 项检查（★ 必做，吸收自 rule-modeling.md）

把每个规则梳理转完决策表后，逐条过下面 6 项。**每命中一项漏洞，生成一条清单项（问题或待确认），交 Clarify 或问题清单。** 经验数据：业务方手写的规则约 70% 至少命中其中 1 项——这些正是"上线后第一周就出 bug"的高发区。

| # | 检查项 | 漏洞信号 | 处置 |
|---|--------|---------|------|
| 1 | **组合穷尽** | 实际规则列数 < 条件状态笛卡尔积（且无常量默认列兜底） | → 提问：请补充缺失组合的动作 |
| 2 | **规则冲突** | 同一条件组合，两条规则给出不同动作 | → 冲突清单：需仲裁优先级/优先级规则 |
| 3 | **空规则** | 存在条件组合没有任何动作命中（含默认列） | → 提问：该组合（如金额=0）系统应如何处理？ |
| 4 | **边界归属** | 条件用 ">" 或 "<" 但未定义等于时归属；或区间有缝/重叠 | → 待确认：阈值 1000 本身走哪条？ |
| 5 | **默认动作** | 没有兜底列，且组合未全覆盖 | → 提问：未命中任何规则的请求，默认怎么处理？ |
| 6 | **优先级/冲突消解** | 多条规则可同时命中（如 VIP 且 ≥1000），未说谁优先 | → 提问：同时命中多规则时，按什么优先级？ |

### 2.4 常见规则类型清单（吸收自 rule-modeling.md）

建模时顺手核对业务方是否覆盖了这些规则族，缺的进遗漏清单：

- 准入/资格规则（谁能发起）
- 路由/分配规则（给谁、去哪）
- 审批/授权规则（谁批、阈值）
- 计费/计价规则
- 时限/超时规则（SLA、提醒、升级）
- 校验/容错规则（非法输入怎么处理）
- 例外/白名单规则（特殊通道）

## 3. 工作流程

1. **定条件桩**：从 BR 候选提取所有参与判定的条件（金额/身份/时限…），每个条件列出全部取值状态。
2. **算笛卡尔积**：条件状态数相乘得理论组合总数，作为穷尽性基准。
3. **列规则列**：业务方明示的组合各占一列；未覆盖的组合暂不补，进检查项 1/5。
4. **填动作桩**：为每列写系统动作（X/-），含拒绝行为——规则不只要说"怎么通过"，还要说"怎么拒绝"。
5. **过 6 项检查**：逐项扫描，命中漏洞生成清单项（提问/待确认/冲突），不静默修正。
6. **编号溯源**：每条决策表编号 `BR-0X`，来源标记 `[S2 计费规则表 B 列]` 或 `[T1 23:10 张经理]`；听记随口一提的标 `待确认`。
7. **输出**：在 business-rules 产物中以决策表呈现，条件/动作可回指 BR-XXX 文本。

## 4. 核心硬规则

1. **6 项检查必做**：组合穷尽/规则冲突/空规则/边界归属/默认动作/优先级消解，逐项过，禁止凭感觉抽查；命中即产清单项。
2. **必须留兜底列**：默认动作列覆盖所有未显式命中的组合；无常量默认列即视为组合未穷尽。
3. **边界显式化**：条件用 >/< 时必须定义等于归属与区间无缝；"1000 本身走哪条"是必答问题。
4. **冲突不静默消解**：同组合不同动作的冲突进冲突清单，由人工仲裁优先级，不自行选一条。
5. **动作含拒绝行为**：动作桩必须有明确的拒绝/降级动作（转人工、拒绝并提示），不只在 X/- 之间二选一。
6. **规则可溯源**：每条 BR-0X 挂素材来源；听记随口一提的标 `待确认`，不当已确认规则。

## 5. 边界（Do Not）

- 不把决策表当数据库表/状态机设计（条件桩不是字段 schema，动作桩不是状态迁移）。
- 不替代 BR-XXX 文本——决策表是结构化视图，规则文本仍是权威，二者须一致。
- 不凭行业惯例补缺失组合——缺失即 `待确认`，交业务方回答。
- 不把 UI 交互（弹窗、按钮、校验提示）塞入动作桩（属 interaction-rules / validation-rules）。
- 不处理单条件判断——单条件用 EARS 句式直写即可，决策表只服务多条件组合判定。

## 6. 质量自检清单

- [ ] 决策表条件桩/动作桩均来自已确认的 BR 候选，无凭空发明
- [ ] 条件状态笛卡尔积已计算，实际规则列 + 兜底列 = 全覆盖
- [ ] 6 项检查逐条过完，命中项均生成清单项（提问/待确认/冲突）
- [ ] 存在默认动作列，未命中任何规则的请求有定义
- [ ] >/< 边界定义了等于归属，区间无缝隙无重叠
- [ ] 规则冲突已进冲突清单，未自行消解
- [ ] 每条 BR-0X 有来源标记，听记规则标 `待确认`
- [ ] 决策表与 BR-XXX 文本一致，无遗漏动作
