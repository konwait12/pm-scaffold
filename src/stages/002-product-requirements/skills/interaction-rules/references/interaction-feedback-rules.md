# 交互反馈规范技法参考（Interaction Feedback Rules）

> 来源吸收：`incremental-prd-collaboration` 的高频遗漏检查（页面标题/按钮文案/倒计时重试文案/成功失败异常状态/自动处理与强拦截/阻断报错文案/成功后去向）+ `product-copywriting` 的 9 场景检查清单（错误提示/表单/按钮/弹窗/空状态/加载/成功反馈/权限请求/破坏性操作）+ `product-spec-generator` 的 `prd-selfcheck-consistency` 权限一致性（角色与操作可见性一致），作为 interaction-rules 的可选落地能力。
> 定位：把 IX-XXX 的反馈从"提示一下"升级为"四态完备、防重、分级确认、权限可解释"——每个操作的反馈（加载中/成功/失败/空状态）与特殊场景（防重复提交/破坏性确认/权限不足）都有必备要素、文案原则与边界。
> 触发：Generate IX-XXX 反馈类规则时；交互规则涉及提交/删除/权限类操作时；Audit 前检查反馈完备性时。**按需加载，不设全局闸门**。

## 2. 操作 → 反馈四态（每态必备要素）

吸收 `product-copywriting` 加载/成功/空状态/错误场景清单与 `incremental` 高频遗漏（成功/失败/异常状态）。每个可交互操作必须声明覆盖的四态（不适用时显式声明"不适用"）。

| 态 | 必备要素 | ❌ 反例 | ✅ 正确示例（吸收 copywriting） |
|---|---|---|---|
| **加载中** | 告知在等什么、预期时长（如可行）、是否可中断 | `加载中...` | `正在获取你的订单…` / `正在提交，预计几秒完成…` |
| **成功** | 结果意味着什么、接下来会发生什么（去向/状态变化） | `操作成功` | `密码已修改，下次登录请使用新密码` / `申请已提交，预计 1-3 个工作日审核` |
| **失败** | 发生了什么（说人话）、原因（如有）、明确恢复动作 | `提交失败，请重试`（无边界） | `网络连接不稳定，请检查后重试` + 保留输入 + 按钮可恢复 |
| **空状态** | 引导用户下一步行动，不只写"暂无数据" | `暂无订单` | `还没有订单，去逛逛？` → 按钮：`去逛逛` |

补充要素：
- **加载中**：长耗时操作必须给中间态反馈（吸收 flow-five-stage.md 执行中段），不得无反馈阻塞。
- **失败**：失败模式必须枚举（网络/校验/权限/冲突等），每条带恢复路径；可恢复与不可恢复措辞区分（追溯 EX-XXX）。
- **空状态**：含"因权限/筛选/数据未生成"三类原因区分，避免所有空态同一句文案。

## 3. 防重复提交

吸收 `product-copywriting` 按钮场景（动词开头、具体动作）与 `incremental` 高频遗漏（自动处理条件和强拦截条件）。

| 要素 | 内容 | 示例 |
|---|---|---|
| **按钮置灰 + 进行中文案** | 提交后到响应前按钮 disabled，文案变具体动作 | 点击`提交订单`后 → 按钮变`提交中…`并置灰 |
| **幂等标识** | 产品级声明"同一请求重复触发不产生副作用"（不写实现级幂等键，脚手架边界） | 网络重试/用户连点均不产生第二笔订单 |
| **双击/连点处理** | 响应到达前忽略后续触发，或给出明确反馈 | 连点支付按钮 → 只产生一次支付请求 |
| **恢复路径** | 提交失败后按钮恢复可点，输入保留 | 失败提示后按钮恢复`重新提交`，表单数据不丢 |

反例：`提交订单` 按钮无 loading、可反复点击生成多笔订单——不合格。

## 4. 破坏性操作确认（软确认 vs 强拦截两档）

吸收 `product-copywriting` 破坏性操作场景（说明后果、警示措辞按钮、次要按钮退出路径）与 `incremental` 高频遗漏（强拦截条件）。

| 档位 | 适用 | 必备要素 | 文案示例 |
|---|---|---|---|
| **软确认** | 可恢复/可撤销（如删除草稿、关闭弹窗） | 一句话说明后果 + 主次按钮 | `是否删除草稿？草稿可从回收站恢复` → 按钮：`删除` / `取消` |
| **强拦截** | 不可逆/高影响（删除账户、批量清空、提交不可撤回的审批） | 说明后果（尤其不可逆）+ 警示措辞主按钮 + 退出路径；高影响可加输入确认词 | `删除账户后，所有数据将无法恢复` → 按钮：`仍要删除` / `再想想`（吸收 copywriting 示例） |

判定规则：
- 不可逆（数据无法恢复、操作无法撤回）→ **强拦截**。
- 可恢复但有损失（有回收站、可重做）→ **软确认**。
- 涉及资金/合规/批量影响 → 强拦截，必要时升级为"输入确认词"或二次验证。
- 弹窗标题说结论、正文说原因，不用`系统提示`（copywriting 弹窗场景）。

## 5. 权限不足反馈（缺什么权限 / 谁能给）

吸收 `incremental` 高频遗漏（账号限制与边界规则）与 `prd-selfcheck-consistency` 权限一致性（E 检查），参照 `ui-copywriting-rules.md` 权限请求场景原则（不拒绝，给出路）。

**必备信息模板**（三问成对）：
1. **缺什么权限**：具体到动作或模块（`导出客户名单`），不写笼统"无权限"。
2. **谁能给**：指明申请对象（`管理员` / `销售主管` / `系统管理员`）。
3. **怎么联系**：给申请入口或指引（`前往权限申请页`）。

| ❌ 不合格 | ✅ 合格 | 三要素对照 |
|---|---|---|
| `无权限` + 按钮：`确定` | `导出客户名单需要「导出」权限，请向系统管理员申请开通` → 按钮：`去申请` / `关闭` | 缺什么✅ 谁能给✅ 下一步✅ |
| `你不是管理员` | `审批功能仅对审批经理开放，可联系管理员为你开通对应角色` | 不说"你不行"，给出路（copywriting 原则 3） |

规则：**权限不足提示不得只报"无权限"三个字**；角色与操作可见性不一致时，须回查 business-rules 权限规则（BR-XXX）确认，缺失标 `待确认`。

## 6. 完整示例：to B 表单提交交互 5 态

**场景**：销售在后台提交"折扣审批申请"表单（含客户、折扣率、理由字段）。追溯：VL-XXX（字段校验）、BR-XXX（折扣上限规则）、EX-XXX（网络异常兜底）。

### 6.1 提交中（加载态）

- **触发**：点击`提交申请`按钮后。
- **状态**：按钮置灰为`提交中…`，禁止重复点击；页面锁定滚动（如有长表单）。
- **文案**：`正在提交审批申请，预计几秒完成…`（copywriting 加载场景）。
- **边界**：超过 15 秒无响应 → 转入失败态（网络失败），不无限转圈（追溯 EX-XXX）。

### 6.2 提交成功（成功态）

- **触发**：审批流创建成功。
- **状态**：按钮恢复；跳转或驻留展示结果。
- **文案**：`申请已提交，预计 1-3 个工作日审核，可在「我的申请」查看进度` → 按钮：`查看申请` / `继续提交`（copywriting 成功场景——告知去向）。
- **去向**：状态转「待审批」（追溯 STATE-XXX），提交列表刷新。

### 6.3 字段校验失败（失败态 · 局部）

- **触发**：折扣率超上限（BR-XXX 定义）或必填缺失（VL-XXX 定义）。
- **状态**：表单驻留，出错字段高亮，按钮恢复为`提交申请`。
- **文案**：字段级提示 `折扣率不能超过 20%`；页级提示 `请修正标红字段后重新提交` → 按钮：`知道了`。
- **边界**：校验属 validation-rules/business-rules 判定，交互侧只反馈结果，不重写校验规则（脚手架边界）。

### 6.4 网络失败（失败态 · 全局）

- **触发**：提交请求超时/断网。
- **状态**：表单驻留，已填内容全部保留，按钮恢复为`重新提交`。
- **文案**：`网络连接不稳定，申请未提交成功，已为你保留填写内容` → 按钮：`重新提交` / `保存草稿`（copywriting 错误场景——现状+下一步）。
- **恢复**：追溯 EX-XXX 重试边界（次数/间隔/幂等），不写"系统异常，请稍后重试"式无边界文案。

### 6.5 权限不足（权限反馈）

- **触发**：当前账号无"提交折扣审批"权限（BR-XXX 权限规则）。
- **状态**：提交按钮置灰不可点（可见但禁用），或点击后弹权限提示。
- **文案**：`提交折扣审批需要「审批申请」权限，请向系统管理员申请开通` → 按钮：`去申请` / `关闭`。
- **边界**：与权限请求场景区分——这是"已登录但权限不足"而非"未登录请先登录"；两者都不得只报"无权限"。

## 7. 工作流程

1. **枚举交互点**：从 page-design 可交互元素摘出所有需要反馈的操作（提交/删除/权限/加载类优先）。
2. **补四态**：每个操作声明加载中/成功/失败/空状态（不适用显式声明），逐项对照 product-copywriting 9 场景清单。
3. **套特殊规则**：提交类加防重复提交；删除/批量类按 §4 判定软确认或强拦截；权限类按 §5 三问模板写反馈。
4. **写文案**：按 ui-copywriting-rules.md 5 原则逐条改写，按钮动词开头 2-6 字。
5. **追溯**：失败态追 EX-XXX、状态变化追 STATE-XXX、校验判定追 VL/BR，缺失标 `待确认`。
6. **收口**：Audit 前逐态核对必备要素与反例，全部通过后进入 Human Gate。

## 8. 核心硬规则

1. **四态缺一不可**：加载中/成功/失败/空状态必须逐操作声明；不适用须显式声明，不允许静默缺失（高频遗漏核验项）。
2. **失败态必须枚举模式并带恢复**：每条失败模式有可判定触发与恢复动作，追溯 EX-XXX；无"系统异常，请稍后重试"式无边界文案。
3. **成功态必须告知去向**：结果意味着什么 + 接下来发生什么（跳转/状态/数据刷新），无悬空成功反馈。
4. **提交必须防重**：按钮置灰 + 进行中文案 + 产品级幂等声明；响应前忽略重复触发。
5. **破坏性操作按后果分档**：不可逆 → 强拦截（警示措辞 + 退出路径），可恢复 → 软确认；涉及资金/合规/批量 → 强拦截。
6. **权限不足三问成对**：缺什么权限 + 谁能给 + 怎么申请；不得只报"无权限"。
7. **文案符合 UI 规范**：说人话、现状+下一步、不拒绝给出路、按钮具体动作；不暴露错误码/内部术语。

## 9. 边界（Do Not）

- 不重写字段校验与业务规则——判定归 VL-XXX/BR-XXX，交互侧只反馈结果。
- 不写权限规则本身——权限归属与角色定义归 business-rules，此处只写"缺什么/谁能给"的反馈。
- 不写技术实现（幂等键、防抖节流、重试机制的具体实现）——只做产品级行为声明。
- 不设计视觉样式（颜色/字号/图标）——属 page-design 视觉层。
- 不替代 exception-handling——失败恢复路径追溯 EX-XXX，不在交互层发明恢复逻辑。
- 不因规范而加戏——四态仅在真实可能发生的操作上声明，不编造不存在的交互场景。

## 10. 质量自检清单

- [ ] 每个 P0 可交互操作已声明四态（加载/成功/失败/空），不适用项已显式声明
- [ ] 失败态每条模式带恢复路径并追溯 EX-XXX，无"系统异常请稍后"式文案
- [ ] 成功态告知结果意义与去向（STATE-XXX / 跳转 / 刷新）
- [ ] 提交类操作有防重复提交（置灰 + 进行中文案 + 幂等声明）
- [ ] 破坏性操作已按软确认/强拦截分档，不可逆项有后果说明与警示按钮
- [ ] 权限不足反馈含"缺什么权限 / 谁能给 / 怎么申请"三要素
- [ ] 文案对照 ui-copywriting-rules.md 5 原则 + 9 场景清单，无错误码/内部术语
- [ ] 未越界写校验规则、权限规则、技术实现、视觉样式
- [ ] 反馈规则可被开发直接实现、测试可复现
