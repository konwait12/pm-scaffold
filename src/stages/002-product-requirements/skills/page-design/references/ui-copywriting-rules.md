# UI 文案规范技法参考（UI Copywriting Rules）

> 来源吸收：`copywriting`（product-copywriting__skillhub）SKILL.md 全文：5 条核心原则 + 9 场景检查清单 + 最终自检 5 问，作为 page-design 的可选落地能力。
> 定位：page-design 产出的页面骨架中，按钮、提示、空状态、弹窗等所有面向用户文案的措辞规范——确保没有技术背景的用户一眼看懂、知道下一步该做什么。
> 触发：在 page-design 中写页面操作、提示语、按钮文案，或评审既有文案是否"说人话"时使用。**按需加载，不设全局闸门**。

## 2. UI 文案 5 原则（吸收自 copywriting，按优先级排序）

### 原则 1：说人话，不说机器话

用户不关心技术细节，只关心「发生了什么」和「我该怎么办」。

- ❌ `鉴权失败` → ✅ `登录已过期，请重新登录`
- ❌ `API Error: 402 insufficient_user_quota` → ✅ `今日额度已用完（已用 $19.84 / 上限 $10.00），额度每天北京时间 0 点刷新。如需调整额度，请前往……`
- ❌ `无效的令牌` → ✅ `无效的令牌，请前往 www.onehub.com/token 查看你的令牌是否正确`

### 原则 2：现状 + 下一步

每条提示回答两个问题：怎么了？→ 怎么办？

- ❌ `订单支付失败，错误 123` → 按钮：`确定`
- ✅ `支付失败，账户余额不足` → 按钮：`去充值` / `以后再说`

### 原则 3：不拒绝，给出路

不要告诉用户"你不行"，要告诉用户"你可以怎样"。

- ❌ `你还不是我们的会员，不能参与此活动` → 按钮：`我知道了`
- ✅ `开通会员即可参与活动，期待你的加入` → 按钮：`开通会员` / `等会再来`

### 原则 4：简洁

能少一个字就少一个字。

- ❌ `你确定要删除这个好友吗？` → ✅ `是否删除好友？`
- ❌ `请输入收货人` → ✅ `名字`

### 原则 5：格式规范

- 中英文之间加空格：`你本次阅读了 30 分钟`
- 数字用阿拉伯数字：`8 件商品`（不写「八件商品」）
- 专有名词拼写正确：`iOS` / `WhatsApp` / `App Store`
- 人称代词全篇统一用 `你`（除非产品调性要求用 `您`）

## 3. 9 场景检查清单（吸收自 copywriting）

### 3.1 错误 / 异常提示

1. 用用户能理解的语言描述发生了什么（不暴露错误码、技术术语）
2. 说明原因（如果有）
3. 给出明确的解决方案或下一步操作
4. 按钮要是具体动作（`去充值` `重新登录`），不要用 `确定` `我知道了`

### 3.2 表单 / 输入项

1. 用 placeholder 提示预期格式（`名字`，而不是 `请输入收货人`）
2. 行动点具体明确，让用户知道该填什么

### 3.3 按钮 / 行动点

1. 动词开头，简短有力（2-6 个字）
2. 正向引导优先（`续费享特权` 而不是 `立即续费`）
3. 次要按钮提供退出路径（`以后再说` `等会再来`）

### 3.4 弹窗 / 对话框

1. 标题说结论，正文说原因
2. 不要用 `系统提示` 这种无意义的标题
3. 按钮区分主次操作，主操作在右侧

### 3.5 空状态

1. 不要只写 `暂无数据`，要引导用户下一步行动
2. ❌ `暂无订单` → ✅ `还没有订单，去逛逛？` → 按钮：`去逛逛`
3. ❌ `暂无搜索结果` → ✅ `没有找到相关内容，换个关键词试试？`

### 3.6 加载 / 等待状态

1. 告诉用户在等什么，而不是只写 `加载中...`
2. ❌ `加载中...` → ✅ `正在获取你的订单…`
3. ❌ `请稍候` → ✅ `正在提交，预计几秒完成…`

### 3.7 成功反馈

1. 不要只写 `操作成功`，要告诉用户结果意味着什么、接下来会发生什么
2. ❌ `操作成功` → ✅ `密码已修改，下次登录请使用新密码`
3. ❌ `提交成功` → ✅ `申请已提交，预计 1-3 个工作日审核`

### 3.8 权限请求

1. 先说明为什么需要这个权限，再请求授权
2. 按钮用具体动作，不要只写 `允许` / `拒绝`
3. ❌ `请允许访问相机` → ✅ `需要使用相机拍摄凭证照片` → 按钮：`允许拍照` / `暂不需要`

### 3.9 破坏性操作确认

1. 必须说明操作后果，尤其是不可逆的操作
2. 主按钮用警示措辞，次要按钮提供退出路径
3. ❌ `是否删除此账户？` → ✅ `删除账户后，所有数据将无法恢复` → 按钮：`仍要删除` / `再想想`

## 4. 工作流程

1. **摘文案点**：从 page-design 页面表的内容区块与操作列摘出所有面向用户文案点（按钮、提示、空态、弹窗、placeholder）。
2. **按原则过一遍**：说人话 → 现状+下一步 → 不拒绝给出路 → 简洁 → 格式规范，逐条改写。
3. **按场景套清单**：对照 9 场景检查清单逐点核验；写不出对照场景的按错误/异常处理默认项。
4. **自检 5 问**：见下方清单，全部通过才写入 page-design/interaction-rules 产物。
5. **输出**：文案落在页面操作/内容/反馈对应位置，保持"页面上有什么"层面。

## 5. 核心硬规则

1. **说人话是底线**：不暴露错误码、技术术语、内部字段名；`鉴权失败`/`API Error` 一票否决。
2. **现状 + 下一步成对出现**：每条提示必须回答"怎么了 + 怎么办"；只有结论没有出路 = 不完整。
3. **不拒绝，给出路**：禁止"你不能/你不是/你没有资格"式措辞；改写为正向导引 + 退出路径。
4. **按钮是具体动作**：禁止 `确定`/`我知道了`/`允许` 这类泛化按钮；动词开头 2-6 字。
5. **破坏性操作必须警示**：不可逆操作必须说明后果，主按钮警示措辞（`仍要删除`），次按钮给退路。
6. **格式统一**：中英文空格、阿拉伯数字、专有名词拼写、人称统一（`你`/`您` 全篇一致）。

## 6. 边界（Do Not）

- 不设计视觉样式（颜色/字号/按钮外观）——文案规范只限措辞与结构。
- 不替 interaction-rules 决定反馈时机与展示方式——只规范文案本身。
- 不写面向内部的口径（错误码、调试信息）进用户可见文案。
- 不因追求简洁牺牲信息——"简洁"是在信息完整前提下的少字，不删掉下一步动作。
- 不跨页面统一改写已确认文案——每处文案改动须可追溯，改动走 page-design 正常流程。

## 7. 质量自检清单

- [ ] 完全不懂技术的人能一眼看懂每句文案
- [ ] 用户看完知道下一步该做什么（现状+下一步成对）
- [ ] 无拒绝式措辞，均改为正向引导 + 出路
- [ ] 已按"能再短一点吗"过一遍
- [ ] 格式规范（中英文空格、数字、专有名词、人称一致性）
- [ ] 9 场景（错误/表单/按钮/弹窗/空态/加载/成功/权限/破坏性）逐项对照
- [ ] 破坏性操作有后果说明 + 警示措辞 + 退出路径
- [ ] 无错误码/技术术语/内部字段名泄漏
