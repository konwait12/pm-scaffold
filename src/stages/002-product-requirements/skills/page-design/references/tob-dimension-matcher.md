# ToB 维度匹配技法参考（ToB Dimension Matcher）

> 来源吸收：`product-spec-generator`（product-spec-generator__skillhub）阶段 0.5 三步编排（事实提取 prd-fact-extractor → ToB 维度匹配 prd-dimension-matcher → 大纲推导 prd-outline-builder 需用户确认），作为 page-design 的可选 to B 落地能力。
> 定位：在进入页面设计前，先把需求事实提炼成"产品类型 + 平台 + 受众"基线，再匹配 ToB 四类维度库（RBAC/多租户/审批流/审计等），确保页面骨架覆盖必写维度而不遗漏。
> 触发：当页面设计对象是内部后台、管理后台、数据看板或表单流程等 to B 产品时使用。**按需加载，不设全局闸门**。

## 1. 输入映射（pm-scaffold 语境）

| 外部 skill 输入 | pm-scaffold 对应产物 | 说明 |
|---|---|---|
| 用户需求描述/澄清结果 | functional-flow 已确认流程 + feature-list 的 FEA-XXX | 事实提取基线 |
| 事实清单（产品类型/平台/受众/阶段/用户故事） | page-design 的页面清单入口 | 维度匹配依据 |
| 关注维度建议 | page-design 页面骨架的内容区块/操作列 | 页面要素来源 |
| PRD 大纲（待确认） | page-design 的页面层级/信息架构 | 页面覆盖范围契约 |

> **上游未 confirmed，不启动维度匹配**：以已确认的功能流程与 FEA-XXX 为准；产品类型不明标 `待确认`，先澄清再匹配。

## 2. ToB 维度库四类映射（吸收自 prd-dimension-matcher.md）

### 2.1 维度库（仅 ToB 四类）

| 产品类型 | 自动匹配维度 |
|---------|------------|
| 内部后台（PC） | RBAC 权限（页面/按钮/数据级）、批量操作、导入导出、表单校验、操作留痕 |
| ToB 管理后台 | 多租户隔离、数据权限、审批流、审计日志、大数据量性能 |
| 数据看板 | 实时性、图表响应式、下钻联动、数据权限、查询性能 |
| 表单流程 | 草稿保存、流程状态机、审批链路、留痕审计、驳回/撤回 |

> 当前版本**不支持 ToC / 移动端 C 端 / 消费者**场景。若产品类型为 ToC，返回终止提示："维度库仅覆盖 ToB 类型，请联系 PM 补充维度库后再生成。"——不硬套 to B 维度。

### 2.2 维度 → 页面要素映射（适配 page-design 语境）

匹配到的每个维度必须能在页面骨架中找到落点：

| 维度 | 在 page-design 中的落点 |
|---|---|
| RBAC 权限 | 页面入口前置条件（角色）、操作列可见性、按钮级权限区块 |
| 多租户隔离 | 页面顶部租户切换器、数据范围提示、隔离边界标注 |
| 审批流 | 审批表单页、审批记录区块、状态流转展示 |
| 审计日志 | 操作留痕区块、详情页审计 tab |
| 批量操作 | 列表页批量操作区、导入导出入口 |
| 下钻联动 | 看板点击事件 → 详情页导航关系 |

## 3. 阶段 0.5 三步编排（吸收自 product-spec-generator）

进入页面设计正文前依次执行三步，产物作为后续推导基线：

### 步骤一：事实提取（吸收自 prd-fact-extractor.md）

把已澄清需求提炼成结构化事实清单，作为一切推导的引用依据：

```
## 事实清单
- 产品类型：[ToB管理后台 / 内部后台 / 数据看板 / 表单流程 / 其他（含 ToC 则照实标注）]
- 平台：[PC 管理后台 / 移动端 H5 / App / 小程序 / …]
- 受众：[用户角色、使用频次、专业背景]
- 项目阶段：[MVP / 迭代优化 / 重构迁移]
- 核心用户故事：
  - US-01：[角色] 在 [场景] 为了 [目标] 做 [动作]
  - US-02：[角色] 在 [场景] 为了 [目标] 做 [动作]
```

规则：缺失项标注 `TBD`，不编造；用户故事使用 Who / When / What / Why 结构；产品类型含 ToC 照实标注，是否终止由主流程判断。

### 步骤二：ToB 维度匹配（吸收自 prd-dimension-matcher.md）

基于事实清单的产品类型 + 平台，从四类维度库匹配本 PRD 必须覆盖的维度，输出：

```
## 关注维度建议
基于「{产品类型}」识别到以下必写维度：
- [维度1]：说明（如：RBAC 权限需区分页面级/按钮级/数据级）
- [维度2]：说明
```

### 步骤三：大纲/页面范围推导（吸收自 prd-outline-builder.md）

基于事实清单 + 关注维度推导页面设计覆盖范围，作为"合同"输出，**必须等待用户确认（回复「确认」或「调整：xxx」）后方可进入正文**：

```
## 页面范围（待确认）
| 页面/分区 | 覆盖范围 | 必填产出 | 关联维度 |
| 列表页 | 筛选/表格列/批量操作/导入导出 | 筛选项表+列定义 | RBAC、批量 |
| 详情页 | 字段展示/操作/审计 tab | 字段表+操作列 | 数据权限、审计 |
| 表单页 | 字段/校验/审批流/草稿 | 表单字段表+提交动作 | 表单校验、审批流 |
| 看板页 | 指标卡/下钻/联动 | 指标定义+点击事件 | 实时性、下钻 |

是否按此范围生成？回复「确认」或「调整：xxx」。
```

## 4. 工作流程

1. **事实提取**：从已确认流程/FEA 提炼事实清单（产品类型/平台/受众/阶段/用户故事），缺失标 `TBD`。
2. **匹配维度**：按产品类型从四类维度库选必写维度，写说明与落点。
3. **推导页面范围**：输出页面/分区覆盖表（页面 + 必填产出 + 关联维度）。
4. **用户确认**：拦截等待用户回复「确认」或「调整：xxx」，未确认不进入正文。
5. **落位页面骨架**：按确认后的页面范围生成 page-design 页面表，每页覆盖关联维度要素。
6. **复核遗漏**：维度匹配到的要素在页面表中全部有落点，无"匹配了但页面没体现"。

## 5. 核心硬规则

1. **三步顺序不可跳**：事实提取 → 维度匹配 → 范围推导，产物逐级引用；跳步即失去推导基线。
2. **维度必须有页面落点**：匹配到的维度在页面骨架中必须有对应内容/操作；"匹配了但页面没体现" = 遗漏。
3. **ToC 不硬套**：产品类型为 ToC/移动端 C 端 → 返回终止提示，不把内部后台的 RBAC/审批流硬塞给 C 端页面。
4. **范围推导必须人工确认**：页面范围即"合同"，未获确认不生成页面正文；用户可合并/拆分/增减。
5. **事实不编造**：产品类型/平台/受众缺失标 `待确认`/`TBD`，不凭需求一句话猜出完整产品画像。
6. **用户故事可溯源**：US-0X 用 Who/When/What/Why 结构，是页面入口与前置条件的推导来源。

## 6. 边界（Do Not）

- 不替代 page-design 页面表——维度匹配是前置分析，页面骨架是正式产物。
- 不做 ToC 场景硬匹配——维度库仅覆盖 ToB 四类，其他类型照实标注后由人工决定。
- 不把技术实现（多租户中间件、RBAC 框架、审批引擎）写进页面设计。
- 不在未确认范围前生成页面正文——范围是合同，跳过确认即违背协作纪律。
- 不把性能指标（并发数、响应时间）塞进页面要素（属非功能需求/AC）。

## 7. 质量自检清单

- [ ] 事实清单完成（产品类型/平台/受众/阶段/用户故事），缺失标 `TBD`
- [ ] 产品类型匹配到四类维度库，或 ToC 场景已返回终止提示
- [ ] 匹配维度均说明页面落点，无"匹配了但页面没体现"
- [ ] 页面范围表已输出并经用户确认（「确认」或「调整」）
- [ ] 页面/分区表含必填产出与关联维度列
- [ ] 用户故事为 Who/When/What/Why 结构，可溯源
- [ ] 无技术实现/性能指标越界内容
