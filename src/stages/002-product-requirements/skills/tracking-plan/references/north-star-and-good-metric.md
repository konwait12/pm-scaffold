# 北极星指标与好指标框架（North Star & Good Metric）

> 来源吸收：`pmaster__skillhub` 的 §11.2 OKR vs KPI vs 北极星指标、§14.1 北极星指标框架、§14.2 好指标 4 标准、§14.3 AARRR 海盗指标、§14.4 指标看板定义模板；补充 `pm-master-prosl` 的 `metrics-and-okr.md` 指标分层与北极星六要求，作为 tracking-plan 指标/目标设计能力的参考。
> 定位：帮 tracking-plan 判断「这个事件支撑的指标到底是不是好指标」——先定北极星，再拆输入/健康/业务/过程指标，每类有反向护栏；避免把事件挂到一堆无法指导行动的指标上。
> 触发：Generate 事件表时确定 metric/goal 字段、覆盖矩阵需要把 EV-XXX 映射到 G-X 时；或指标口径模糊需澄清时。**按需加载，不设全局闸门。**

## 1. 输入映射

| 外部 skill 输入 | pm-scaffold 对应产物 | 说明 |
|---|---|---|
| 北极星指标框架（输入/健康/业务指标） | background-goal 的 G-X 目标 + tracking-plan 指标映射 | 事件必须支撑某层指标 |
| 好指标 4 标准 | EV-XXX 的 metric 字段 | 过滤「无法指导行动」的指标 |
| AARRR 海盗指标 | 用户生命周期阶段定位 | 判断事件属于获取/激活/留存/推荐/收入哪段 |
| 指标看板定义模板（含口径） | tracking-plan 指标映射表 | 口径字段补全，避免数据团队反复确认 |
| 指标分层（北极星/过程/反向护栏） | tracking-plan 覆盖矩阵 | 确保每个 P0 功能至少挂到有意义的指标 |

## 2. 北极星指标框架

```
北极星指标（North Star）
├── 输入指标（3-5个）
│   ├── 输入指标1
│   └── 输入指标2
├── 健康指标
│   ├── 延迟
│   ├── 错误率
│   └── NPS
└── 业务指标
    ├── MRR
    ├── CAC
    ├── LTV
    └── 流失率
```

### 北极星指标的合格要求（6 条）

1. 代表真实用户价值。
2. 能被团队行动影响。
3. 与长期业务结果正相关。
4. 不容易被刷量。
5. 足够稳定，不频繁更换。
6. 能拆解为输入指标。

## 3. 指标分层（分级：北极星 / 过程 / 反向）

| 类型 | 作用 | 示例 |
|---|---|---|
| 北极星指标 | 衡量用户价值和业务增长的核心结果 | 周活跃有效协作团队数 |
| 输入指标 | 团队可以直接推动的领先指标 | 新建项目数、邀请成员数 |
| 健康指标 | 防止增长牺牲质量（= 护栏/反向） | 留存率、投诉率、延迟、成本 |
| 业务指标 | 连接商业结果 | 付费转化、ARPU、续费率 |
| 过程指标 | 观察漏斗和执行过程 | 点击率、激活率、完成率 |

### 反向指标（护栏）要点

- 反向指标是「赢了指标害了用户」的守门员：追北极星时必须同时设质量/风险约束。
- 例：会员活动不能只看新增会员数，还要看 30 日复购率、客单价、毛利、优惠券核销率、投诉率和低价值用户占比。
- tracking-plan 的每个事件在映射指标时应能回答：这个事件挂的指标变好时，产品一定更健康吗？有没有副作用？

### OKR vs KPI vs 北极星指标

| 概念 | 说明 |
|---|---|
| OKR | 鼓舞人心的目标 + 可衡量的关键成果 |
| KPI | 长期跟踪的核心量化指标 |
| 北极星指标 | 单一、以客户为中心、成功领先指标 |

关系：关键成果可以是 KPI；OKR 的 KR 可以表达北极星指标的变化。

## 4. 好指标的 4 个标准

1. **易理解** — 形成共同语言，不用解释口径。
2. **可比较** — 随时间变化可比（同口径跨期/跨群）。
3. **是比率** — 比绝对数字更具洞察力（如转化率 vs 转化数）。
4. **能改变行为** — 「如果一个指标不会改变你的行为，它就是一个糟糕的指标」。

## 5. AARRR 海盗指标

| 阶段 | 指标 | 说明 |
|---|---|---|
| **A**cquisition | 获取 | 用户如何发现你？ |
| **A**ctivation | 激活 | 用户第一次体验好吗？ |
| **R**etention | 留存 | 用户会回来吗？ |
| **R**eferral | 推荐 | 用户会推荐别人吗？ |
| **R**evenue | 收入 | 你如何盈利？ |

应用：tracking-plan 判定事件阶段归属，覆盖矩阵确保漏斗关键段无盲区。

## 7. 指标常见反模式（对照自检）

1. 只看增长，不看质量。
2. 只看平均数，不看分布。
3. 把收入结果指标当作用户价值领先指标。
4. 北极星指标过多（北极星必须单一）。
5. 指标不可被团队行动影响。
6. 看板没有口径，会议反复争论数据含义。
7. 只追转化率，忽略用户质量和长期留存。

## 8. 工作流程

1. 从 background-goal 确认北极星指标与 G-X 目标层级（北极星 / 过程 / 反向）。
2. 对每个候选事件，用 AARRR 定位它属于用户生命周期哪一段。
3. 用「好指标 4 标准」过滤：挂不上可行动指标的候选事件降级或删除。
4. 用指标口径模板补全每个 metric 的口径字段（公式/窗口/对象/排除条件/告警）。
5. 用指标分层核对覆盖矩阵：北极星有输入支撑、有反向护栏，不裸奔。
6. 对口径模糊或反向护栏缺失的，走 Clarify 批量提问（metric_owner 判定）。
7. 将指标映射写入 tracking-plan，随 Human Gate 呈现给 metric_owner / data_owner。

## 9. 核心硬规则

1. 北极星指标必须单一、代表用户价值、可被行动影响。
2. 每个指标必须能改变行为——不能指导动作的指标不挂事件。
3. 指标必须是比率优先，绝对数要能拆出分母口径。
4. 追北极星必须配反向护栏（健康/质量指标），防赢了指标害了用户。
5. 每个指标必须有明确口径（公式/窗口/对象/排除条件），无口径不上看板。
6. 事件与指标映射必须可追溯（EV-XXX → G-X），覆盖矩阵每个 P0 功能 ≥1 个 must_track。

## 10. 边界（Do Not）

1. 不设定具体数值目标——那是 background-goal 的 G-X 职责，tracking-plan 只做映射。
2. 不写 SQL、不建数仓表、不设计 BI 看板。
3. 不把结果收入指标当作用户价值领先指标来设计事件。
4. 不用平均数掩盖分布——分布类指标（p95 延迟等）要显式。
5. 不因「好指标」框架而删掉必要的 nice_to_track 事件——分级由 metric_owner 定。
6. 不在 tracking-plan 中重新发明北极星——以上游 G-X 为唯一事实来源。

## 11. 质量自检清单

- [ ] 北极星指标已从上游 G-X 确认，单一且能拆解为输入指标
- [ ] 每个事件的 metric 能通过好指标 4 标准（易理解/可比较/比率/改行为）
- [ ] 覆盖矩阵含反向护栏（健康/质量指标），非裸奔北极星
- [ ] 事件已用 AARRR 定位生命周期阶段，漏斗关键段无盲区
- [ ] 每个指标口径已补全（公式/时间窗口/统计对象/排除条件）
- [ ] 指标映射可追溯（EV-XXX → G-X），无孤立事件
- [ ] 未写 SQL / 数仓表 / BI 看板；未设定具体数值目标
- [ ] 指标口径模糊项已交 Clarify 或由 metric_owner 判定
