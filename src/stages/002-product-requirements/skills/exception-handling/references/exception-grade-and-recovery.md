# 异常分级与恢复策略技法参考（Exception Grade & Recovery Strategy）

> 来源吸收：`pm-master-prosl` 的「异常降级与安全边界」（§7 研发评审版 PRD 硬标准第 11 项 + §10 高风险决策给风险分级/验证计划/回滚方案）+ `product-spec-generator` 的 `prd-selfcheck-consistency`（P0/P1/P2 严重级别定义与处理 + 状态机三元一致性 D 检查）+ `product-copywriting` 提示文案原则（说人话/现状+下一步/不拒绝给出路），作为 exception-handling 的可选落地能力。
> 定位：给每条 EX-XXX 行统一「异常分级（CRITICAL/HIGH/MEDIUM/LOW）+ 恢复策略（重试/回滚/降级/兜底/人工介入）」两把尺子，并做异常↔状态机↔规则三元一致性扫描——让严重程度与恢复路径可判定、可验收、可被下游 AC-XXX 消费。
> 触发：Generate EX-XXX 需判定严重级别或选择恢复策略时；多条 EX 无法裁决阻断优先级时；Audit 前做分级与三元一致性扫描时。**按需加载，不设全局闸门**。

## 2. 异常四级分级（CRITICAL / HIGH / MEDIUM / LOW）

吸收自 `prd-selfcheck-consistency` 的 P0/P1/P2 严重级别（阻断性矛盾/明显不一致/轻微不一致）与 `pm-master-prosl` 高风险决策分级思想，映射为异常处理侧的 4 级。**每条 EX-XXX 必带分级，不允许无级行**。

| 级别 | 判定标准 | 是否阻断 | 阻断/放行示例 |
|---|---|---|---|
| **CRITICAL** | 涉及资金错乱、合规红线、数据完整性被破坏；或主流程完全中断且无自动恢复路径；恢复后必须人工核验 | 阻断——Human Gate 前必须清零，不修复不输出 | 重复扣款 / 金额写错 / 数据被覆盖不可恢复 → 阻断该功能确认 |
| **HIGH** | 主流程局部中断但可恢复；影响多个用户或关键任务；缺兜底会静默失败 | 阻断该功能确认，须交 Human Gate 明确裁决 | 支付超时 / 回调丢失 / 外部依赖不可用 → 阻断该 EX 的 confirmed |
| **MEDIUM** | 单个用户局部体验受损；有兜底但兜底降级了能力 | 不阻断，须在 EX 行标注并登记 | 余额查询延迟 / 附件上传重试后成功 → 放行但记录 |
| **LOW** | 偶发、非关键、有默认值兜底，不影响业务正确性 | 不阻断，可延后处理 | 展示层小瑕疵 / 日志字段缺失 → 放行，登记 backlog |

判定顺序（逐条判断，命中即定级）：
1. 是否触碰资金 / 合规 / 数据不可逆？→ CRITICAL。
2. 是否中断主流程或依赖关键外部系统？→ HIGH。
3. 是否只影响单用户局部且已有兜底？→ MEDIUM。
4. 其余偶发小问题 → LOW。

## 3. 恢复策略矩阵（5 策略）

吸收自 `pm-master-prosl` 研发评审硬标准「异常降级」与 §10「验证计划和回滚方案」、`prd-selfcheck-consistency` 异常覆盖要求。每个策略给适用场景、必须写明的边界、EX 写法片段。

| 策略 | 适用场景 | 必须写明的边界 | EX 写法片段 |
|---|---|---|---|
| **重试** | 瞬时性失败（网络超时、锁冲突、外部抖动） | 重试次数、间隔、幂等提交；耗尽后去向 | `EX-XX: 支付请求超时 → 自动重试最多 3 次、间隔 30s、幂等提交 → 耗尽转人工介入` |
| **回滚** | 数据一致性被破坏（部分成功、跨系统写一半） | 回滚范围、补偿动作、补偿失败兜底 | `EX-XX: 扣款成功但订单创建失败 → 自动原路退款 → 退款失败转人工工单` |
| **降级** | 依赖不可用但主流程可继续 | 降级后哪些能力缺失、何时恢复全量、是否标记 | `EX-XX: 风控服务不可用 → 降级为白名单放行 + 标记人工复核 → 服务恢复后补跑风控` |
| **兜底** | 输出不可靠（AI 输出、解析失败、枚举不匹配） | 兜底触发条件可判定、默认值来源、需否用户确认 | `EX-XX: AI 摘要置信度 < 0.9 → 用默认值填充并标注"AI 推断，请确认" → 人工确认前不计入` |
| **人工介入** | 不可自动恢复、需要业务判断、涉及资金核验 | 转人工触发条件、责任人、处理时限 | `EX-XX: 退款金额与账单不一致 → 转人工工单，财务 T+1 处理，处理前状态冻结` |

选型规则：先判可自动恢复性——瞬时性 → 重试；数据受损 → 回滚；依赖缺失 → 降级；输出不可靠 → 兜底；判断型/资金型 → 人工介入。**CRITICAL 级必须含「人工介入」或「回滚」，不允许只靠重试**。

## 4. 用户可见提示规范（三要素）

异常提示必须同时回答三问（吸收 `product-copywriting`「说人话 + 现状+下一步」与脚手架 `ui-copywriting-rules.md` 5 原则）：

1. **发生了什么**：用用户能理解的语言描述，不暴露错误码/技术术语/内部字段。
2. **影响什么**：后果要透明——哪些没成功、数据是否安全、状态是什么。
3. **下一步能做什么**：给具体动作按钮（`重试` `去充值` `联系客服`），不给裸 `确定`。

| ❌ 不合格 | ✅ 合格 | 三要素对照 |
|---|---|---|
| `支付失败，错误 123` | `支付未完成，你的账户未被扣款` → 按钮：`重新支付` / `查看订单` | 发生了什么✅ 影响✅ 下一步✅ |
| `系统异常，请稍后重试` | `网络连接不稳定，订单已保存为草稿，可稍后继续提交` → 按钮：`查看草稿` | 三要素齐，且不写"系统异常" |
| `鉴权失败` | `登录已过期，请重新登录` → 按钮：`重新登录` | 说人话 |

规则：**无下一步动作的异常提示不成立**；可恢复与不可恢复的提示措辞必须区分（可恢复给动作，不可恢复说明去向 + 联系方式）。

## 5. 异常 ↔ 状态机 ↔ 规则三元一致性

引用脚手架 `state-machine/references/state-machine-completeness.md` §3（吸收自 prd-selfcheck-consistency D 检查）。对每个被异常影响的实体跑三方核对，**任一缺口即冲突，按严重级别处理**。

| 核对项 | 状态机（STATE-XXX） | 异常兜底（EX-XXX） | 规则触发（BR-XXX） | 缺口 → 级别 |
|---|---|---|---|---|
| 状态存在 | 状态机中有该状态 | 该状态「卡住/失败」有 EX 方案 | 进入该状态有条件规则 | 缺异常兜底 → **CRITICAL/HIGH**（P0） |
| 迁移触发 | 转移表有该事件 | 失败时有恢复异常 | 触发守卫有规则 | 迁移无规则支撑 → HIGH（P1） |
| 命名一致 | 状态名 | 异常描述状态名 | 规则状态名 | 三者写法不一致 → MEDIUM（P2） |
| 引用存在 | 引用 STATE-XXX 编号 | 引用 EX-XXX 编号 | 引用 BR-XXX 编号 | 引用悬空 → CRITICAL（P0） |

输出格式（吸收 prd-selfcheck-consistency）：

```markdown
- [!][CRITICAL] 状态机缺口：状态「已取消」在 STATE-008 存在，EX 层未覆盖其卡住场景 → 补 EX-XXX
- [!][HIGH] 规则缺口：STATE-011「超时自动关闭」无 BR-XXX 支撑 → 补 BR 或降级标记
- [!][MEDIUM] 命名口径：异常层称「支付失败」，规则层称「交易失败」→ 统一
```

## 6. 完整示例：to B 支付异常 4 例

**场景**：企业客户在后台提交订单并在线支付。角色：提交人、财务、风控管理员、客服。每例给「判定 → 分级 → 恢复策略 → 用户提示 → 三元一致性」。

### 6.1 网络超时

- **判定**：提交支付请求后 15 秒无响应（BR-XXX 定义超时阈值）。
- **分级**：HIGH——主流程中断但可恢复。
- **恢复策略**：重试（最多 3 次 / 间隔 30s / 幂等提交）→ 重试耗尽转人工介入（客服核查支付状态）。
- **用户提示**：`支付未完成，订单已保存，正在为你重试`；耗尽后 `网络不稳定，请稍后重新支付` → 按钮：`重新支付` / `联系客服`。
- **三元一致性**：状态机「支付中 → 支付失败 → 重试 → 支付成功」；EX-XXX 覆盖超时恢复；BR-XXX 定义 15s 阈值与幂等提交。

### 6.2 余额不足

- **判定**：账户余额 < 应付金额（BR-XXX 扣款前校验）。
- **分级**：MEDIUM——非系统故障，用户可自行解决。
- **恢复策略**：阻断本次支付（不自动重试）+ 引导充值后用户重新发起；充值动作属用户侧操作，非系统恢复。
- **用户提示**：`支付失败，账户余额不足` → 按钮：`去充值` / `以后再说`（吸收 product-copywriting 原则 2 示例）。
- **三元一致性**：状态机「支付中 → 支付失败 → 用户充值 → 重新支付」；EX 覆盖扣款拒绝；BR 定义余额校验规则与最低充值额。

### 6.3 重复支付

- **判定**：同一订单号收到第二次支付成功回调（幂等冲突，BR-XXX 幂等规则）。
- **分级**：CRITICAL——资金错乱，触碰钱即最高级。
- **恢复策略**：回滚（重复款项自动原路退款）+ 人工核验（财务确认退款到账）+ 审计留痕。
- **用户提示**：`检测到你重复支付了 ¥X，多余的款项将在 1-3 个工作日内原路退回` → 按钮：`查看退款进度` / `联系客服`。
- **三元一致性**：状态机「支付成功 → 退款中 → 已退款」；EX 覆盖重复支付补偿；BR 定义幂等键与退款规则；不写实现级幂等键（脚手架边界）。

### 6.4 风控拦截

- **判定**：命中风控规则（BR-XXX 风控条件，如异地大额、频次异常）。
- **分级**：HIGH——涉及合规安全，须人工判断。
- **恢复策略**：阻断 + 人工介入（转风控管理员审核）+ 兜底（用户可提交申诉材料）。
- **用户提示**：不暴露"风控"内部术语，写 `本次支付未通过安全校验，为保障资金安全已暂停处理` → 按钮：`提交申诉` / `联系客服`。
- **三元一致性**：状态机「支付中 → 待风控审核 → 通过/拒绝」；EX 覆盖拦截与申诉路径；BR 定义风控触发条件与申诉时限。

## 7. 工作流程

1. **逐条定级**：按 §2 判定顺序给每条 EX-XXX 标 CRITICAL/HIGH/MEDIUM/LOW；写不出判据的 EX 标 `待确认`。
2. **选恢复策略**：按 §3 五策略矩阵选型；CRITICAL 必须含回滚或人工介入。
3. **写用户提示**：按 §4 三要素写提示，逐条对照 ui-copywriting-rules.md 5 原则。
4. **跑三元一致性**：引用 state-machine-completeness.md §3，输出 P0/P1/P2 冲突清单。
5. **收口**：CRITICAL/HIGH 阻断项清零；MEDIUM 登记说明；LOW 进 backlog。全部通过后进入 Audit。

## 8. 核心硬规则

1. **每条 EX 必带分级**：无级行不成立；分级锚点缺失标 `待确认`，不臆断。
2. **分级判定可复核**：CRITICAL/HIGH 的判定要能说清"碰没碰钱/合规/数据不可逆"，遮住结论别人能复核。
3. **恢复策略带边界**：重试次数/间隔/幂等、回滚范围/补偿、降级缺失项、人工介入责任人与时限必须写明；"稍后重试"式无边界恢复不合格。
4. **CRITICAL 必须人工核验**：资金/合规/数据完整性异常，恢复后必须有人工核验环节，不可纯自动闭环。
5. **提示三要素齐**：发生了什么 + 影响什么 + 下一步能做什么；无下一步动作的提示不成立。
6. **三元一致性是硬闸**：状态机卡住状态无异常兜底、迁移无规则支撑、引用悬空——P0 级必须修复后才能进入 Human Gate。
7. **不暴露内部**：提示不得出现错误码、风控/幂等/回调等技术术语，按 UI 文案规范改写。

## 9. 边界（Do Not）

- 不定义技术实现（try-catch、异常类型、幂等键实现、消息队列）——只做产品级分级与恢复行为。
- 不重写业务规则——分级阈值、幂等规则、风控条件属 business-rules，EX 引用而非重写。
- 不替代状态机——恢复迁移落点引 STATE-XXX，异常侧不重新定义状态流转。
- 不写交互时机与展示方式（弹窗/toast/时长）——属 interaction-rules。
- 不把 CRITICAL 级当普通行处理——资金/合规异常必须走人工核验路径。
- 不做假检查——上游未确认的失败来源只登记 `待确认`，不编造分级。
