# 功能说明五要素技法参考（Functional Spec Five Elements）

> 来源吸收：Trae `prd-development` skill 阶段五「功能说明」的完整结构（功能描述 + 业务说明四项），作为 functional-flow 的可选落地能力。
> 定位：functional-flow 产出的功能流程文本（主流程/分支流程/异常流程）是权威；本文档提供"把每个功能拆解为五要素结构化规格"的技法，使开发可直接消费、字段状态生命周期可见。
> 触发：当功能流程涉及多角色、状态流转、字段校验或需要开发可直接消费时使用。**按需加载，不设全局闸门**。

## 1. 输入映射（pm-scaffold 语境）

| 外部 skill 输入 | pm-scaffold 对应产物 | 说明 |
|---|---|---|
| 功能要点 | functional-flow 的 FEA-XXX | 五要素挂接对象 |
| 交互流程 | functional-flow §主流程/分支/异常 | 实现逻辑来源 |
| 核心字段 | validation-rules 的 VL-XXX | 核心字段说明（含状态生命周期） |
| 业务规则 | business-rules 的 BR-XXX | 数据校验规则来源 |
| 用户故事 | user-stories 的 ST-XXX | 功能动机与目标用户 |

> **上游未 confirmed，不启动五要素拆解**：以 functional-flow 已确认的 FEA-XXX 为准；缺失标 `待确认`，不编造。

## 2. 五要素结构（吸收自 prd-development 阶段五）

每个功能（FEA-XXX）拆解为以下五要素：

| # | 要素 | 内容 | 必填 |
|---|---|---|---|
| 1 | **功能描述** | 这个功能要实现什么，核心逻辑是什么。用一段话说清核心逻辑，不涉及 UI 细节 | ✅ |
| 2 | **前置条件** | 功能使用前需满足的条件（用户权限要求、必须依赖的系统模块等） | ✅ |
| 3 | **功能实现逻辑** | 系统处理业务的主要逻辑：数据来源、处理流程、能力边界 | ✅ |
| 4 | **核心字段说明** | 页面呈现的字段及含义；若存在多种状态，明确描述**状态生命周期**（经历哪些状态、什么条件下从一状态变为另一状态） | ✅ |
| 5 | **数据校验规则** | 系统对输入数据的合法性和唯一性校验 | ✅ |

## 3. 完整示例（吸收自 prd-development，评论功能）

### FEA-XXX：评论功能

**① 功能描述**：支持用户对内容发表评论，并支持富文本编辑与多级回复，权限按角色差异化控制。

**② 前置条件**：用户已登录；目标内容处于可评论状态。

**③ 功能实现逻辑**：

1. 内容输入 — 支持三种形式：
   - 纯文本
   - 图片（限制 JPG/PNG 格式和大小）
   - 文件上传（限制格式和大小）
2. 富文本编辑 — 支持文字样式（字号、字重、字体颜色）和段落样式（段落间距、对齐方式）编辑
3. 回复功能 — 支持对一级评论回复形成二级评论，但不支持三级及以上嵌套
4. 权限控制（追溯 BR-XXX / RBAC 矩阵）：

| 操作 | 普通用户 | 管理员 |
|---|---|---|
| 删除评论 | 仅限自己的评论 | 任意评论 |
| 修改评论 | 仅限自己的评论 | 仅限自己的评论 |

**④ 核心字段说明**（含状态生命周期）：

- 评论 ID：评论唯一标识
- 评论内容：用户输入的文本/图片/文件
- 评论状态：包括 **待审核 → 已发布 → 已隐藏**，由管理员用户审核/操作切换
- 父评论 ID：回复关系标识（一级为空，二级为父评论 ID）

**⑤ 数据校验规则**：

- 评论内容非空校验（纯文本/图片/文件至少一项）
- 图片格式 JPG/PNG、大小 ≤5MB
- 文件格式限制、大小 ≤20MB
- 回复层级校验：父评论必须为一级，禁止三级及以上嵌套（追溯 BR-XXX）

### 另一示例：核心字段状态生命周期（吸收自 prd-development 告警功能）

- 告警 ID：告警唯一标识
- 告警名称：恶意软件家族
- 影响资产：触发告警的资产 IP
- 告警状态：**未处置 → 处置中 → 已完成**，由管理员用户手动切换告警状态（追溯 STATE-XXX）

## 4. 工作流程

1. **读功能流程**：从 functional-flow 提取 FEA-XXX 的主流程/分支/异常步骤。
2. **写功能描述**：一段话核心逻辑，不涉及 UI。
3. **拆前置/实现逻辑**：从流程入口边与处理步骤推导；未明示标 `AI_INFERENCE` 交人工。
4. **抽核心字段**：从流程节点涉及的数据对象提取字段；状态字段列出值序列（如 待审核→已发布→已隐藏），与 state-machine 的 STATE-XXX 一致；不一致标 `CONFLICT`。
5. **挂数据校验**：每条校验追溯 BR-XXX / VL-XXX；缺失标 `待确认`。
6. **输出五要素**：在 functional-flow 产物功能详述段以结构化呈现。

## 5. 核心硬规则

1. **忠于流程，不发明步骤**：实现逻辑每步可追溯 functional-flow 节点；不得新增流程外步骤。
2. **状态生命周期显式化**：核心字段若参与状态流转，必须列出值序列（如 未处置→处置中→已完成），并与 state-machine 的 STATE-XXX 一致；不一致即 `CONFLICT`。**这是 to B 流程系统的核心**——告警单/审批单/质检单/工资单等业务对象的状态流转必须显式。
3. **权限差异按操作粒度拆行**：同资源不同角色的"部分允许"（如"仅限自己的评论"vs"任意评论"）必须拆行，追溯 BR-XXX / RBAC 矩阵，不合并表述。
4. **校验不空挂**：每条数据校验追溯 BR-XXX / VL-XXX；无上游规则标 `待确认`，不自行编规则。
5. **to B 前置含权限**：前置条件须显式校验权限角色（RBAC）；多租户场景标注租户隔离边界。

## 6. 边界（Do Not）

- 不设计数据库表结构或 API 接口（超出 PRD-only）。
- 不替代 functional-flow §主流程文本——五要素是结构化增强，流程文本是权威。
- 不替业务方决定字段状态——状态生命周期以 STATE-XXX 为准，存疑标 `待确认`。
- 不把视觉/交互微细节塞入实现逻辑（属 interaction-rules / page-design）。
- 不写测试用例/断言脚本（属测试，超出 PRD-only）。

- [ ] 核心字段的状态生命周期与 STATE-XXX 一致（无 CONFLICT），值序列显式
- [ ] 权限差异按操作粒度拆行，追溯 BR-XXX / RBAC
