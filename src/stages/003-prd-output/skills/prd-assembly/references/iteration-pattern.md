# 迭代变更模式（Iteration Pattern）

> 来源吸收：`product-spec-generator` 的 `iteration-prd-generator` 子技能（SKILL.md + references/methodology.md + templates/case1-change.md + templates/case2-change.md），作为 prd-assembly 迭代/增量场景的可选落地能力。
> 定位：当 prd.md 已有基线（或老系统无基线）要做增量变更时，产出轻量「变更文档（delta）」而不是重跑完整汇总——只写差异、带 chg 日志块、可测试可追溯，避免大炮打蚊子。
> 触发：迭代/增量意图（改字段、改规则、加功能、调权限），或 prd.md 定稿后收到上游变更需生成变更记录时。**按需加载，不设全局闸门。**

## 1. 输入映射

| 外部 skill 输入 | pm-scaffold 对应产物 | 说明 |
|---|---|---|
| 已有可 diff 的 PRD 基线（本地 prd.md / 外部文档） | 已 confirmed 的 prd.md + 上游基线 | 走 **Case 1 有基线 delta**：粘贴补丁式变更文档 |
| 无基线的老系统 + 本次迭代 | 上游原始材料（无 prd.md） | 走 **Case 2 无基线自包含**：现状 + 变更 + 验收 |
| 全新模块 / 改状态机 / 改关键字段枚举口径 / 范围大幅扩张 | 视为新需求而非迭代 | 不写变更文档，回完整流水线重建基线 |
| 一次迭代涉及多个模块 | prd.md 多个章节 | 单文档、双 `modules` 标签，正文按模块分段 |

## 2. 场景判定：Case 1 vs Case 2

两种场景的本质差异只有一点：**是否已有可 diff 的书面基线 PRD**。其余治理完全一致。

| 维度 | Case 1 有基线 | Case 2 无基线 |
|---|---|---|
| 文档形态 | 粘贴补丁式（引用章节，只写 delta） | 自包含（现状 + 变更 + 验收） |
| 是否写现状 | 否（基线即现状） | 是（从老系统反向观察） |
| 基线维护者 | 已有 PRD，持续更新 | 由变更文档逐步合成 |
| 何时跑完整汇总 | 改结构时重建 v2 | 累积到节点时 collapse 成基线 |
| 核心纪律 | 不重写基线内容，只给「替换/新增/删除」指令 | 每份文档不依赖外部文档即可读 |

## 3. Case 1 · 有基线 PRD（增量迭代）

### 3.1 特征

- 已有一份产品文档，两种常见形态：(a) 本地结构化 PRD（prd.md）；(b) 外部协作工具（钉钉/飞书/Confluence/Word）里的历史文档——**这是更常见的真实形态**。
- 本次迭代是局部优化：加字段、改规则、调权限、补文案等。
- 基线文档是**唯一事实来源**，仍在持续维护。

### 3.2 做法：粘贴补丁式变更文档

- 文档形态：「在『XX 章节』修改为……」/「在文档中新增『YY』章节」。
- 引用基线：开头写明目标文档路径/链接 + 涉及模块。
- 不重写基线内容，只给「替换/新增/删除」指令。
- 文末追加变更记录日志块（chg-XXX）。

### 3.3 变更详情（delta）模板——字段级变更

#### 新增字段

| 序号 | 字段名 | 所属位置 | 控件类型 | 必填 | 取值/枚举 | 说明 |
|---|---|---|---|---|---|---|
| 1 | [fieldName] | [表格/筛选/表单] | [Input/Select/…] | 是/否 | [枚举值] | [说明] |

#### 修改字段

| 序号 | 字段名 | 原定义 | 新定义 | 说明 |
|---|---|---|---|---|
| 1 | [fieldName] | [原控件/枚举/校验] | [新控件/枚举/校验] | [说明] |

#### 删除字段

| 序号 | 字段名 | 原所属位置 | 删除原因 |
|---|---|---|---|
| 1 | [fieldName] | [表格/筛选/表单] | [原因] |

#### 规则级变更

| 序号 | 规则编号 | 变更类型 | 原规则 | 新规则 | 实现方 |
|---|---|---|---|---|---|
| 1 | BR-0N / 新增 | 新增/修改/删除 | [原规则描述] | [新规则描述] | 前端/后端 |

> 纯非功能迭代（性能/安全/兼容性）可留空字段表，但验收标准须含可量化指标（如「响应 ≤2s → ≤1s」）。

## 4. Case 2 · 无基线老系统（补 PRD）

### 4.1 特征

- 系统已上线运行，但没有任何符合规范的 PRD 文档；现在被要求「做迭代也要出 PRD」。
- 没有可 diff 的基线，但有**可观察的现状**（界面、数据库、接口、代码）。

### 4.2 做法：自包含变更文档（现状 + 变更 + 验收）

1. **现状梳理（Before）**：从老系统反向观察当前行为，作为本次变更基准。
2. **变更内容（After）**：直接描述变更后目标状态，不依赖外部文档。
3. **验收标准 + chg 日志块**：逐条可测，并方便日后合并重建基线。

### 4.3 关键纪律

- 现状梳理要「轻但准」：只覆盖本次受影响的页面/字段/规则，不必全量盘点老系统。
- 多迭代累积后**定期 collapse**：每 3~5 次迭代或到大版本节点，把历次变更合并成一份「当前状态 PRD」——这次合并产物就是你系统真正的基线 PRD。

### 4.4 现状梳理模板（Before）

| 序号 | 页面 / 功能 | 当前行为简述 |
|---|---|---|
| 1 | [页面/功能名] | [现状描述] |

| 序号 | 字段名 | 当前控件/类型 | 当前规则 | 数据来源 |
|---|---|---|---|---|
| 1 | [fieldName] | [Input/Select/…] | [当前校验/默认值] | [字典/接口/手动] |

### 4.5 变更内容模板（After，多个独立变更用「变更一 / 变更二」分隔）

```
### 变更一：{变更标题}
- 影响范围：[页面 / 字段 / 规则 / 流程]
- 现状 → 目标：
| 维度 | 变更前 | 变更后 |
|---|---|---|
| [字段/规则/文案] | [原样] | [新样] |
- 详细说明：
  - [规则要点 1，含枚举值/边界/实现方（前端/后端）]
  - [规则要点 2]
```

## 5. 变更记录日志块（chg 格式，两种场景共用）

```
rev: chg-NNN
summary: {一句话汇总本次所有变更}
modules: [模块A, 模块B]
status: active          # active / superseded / reverted
comments: []
actor: {姓名/工号}
ts: {YYYY-MM-DDTHH:MM:SS+08:00}
```

**编号规则**：`chg-NNN` 按变更次数递增，永不回退、不重号；取现有最大号 +1。无则 `chg-001`。

**回滚**：若本次变更后续被撤销，新增一条 `chg` 并置 `status: reverted`，**不删除**原记录（保留审计链）。

## 6. 验收标准纪律（两种场景共用）

- 验收标准必须**可测试**、标注类型（功能/性能/异常）。

| 序号 | 所属变更 | 验收项 | 验收标准 | 类型（功能/性能/异常） |
|---|---|---|---|---|
| AC-01 | [变更项] | [场景] | [可测试条件] | 功能 |
| AC-02 | [变更项] | [异常场景] | [可测试条件] | 异常 |

- 只列本次变更相关项，不复制基线已有验收。

## 7. 何时升级为完整汇总（不写变更文档）

当本次变更**改动了基线结构**时，应升级而非打补丁：

- 新增 FR（功能需求编号）
- 修改状态机 / 核心流转
- 修改关键字段表的枚举口径
- 模块范围大幅扩张

→ 此时回完整流水线重建 v2，或在基线变更记录处追加大版本说明。

## 8. 共同治理规则

### 8.1 何时合并 / 重建基线

| 触发条件 | 动作 |
|---|---|
| Case 1 打了多次补丁 | 补丁已并入基线，无需额外合并 |
| Case 2 累积 3~5 次变更 | 合并为 `baseline` 文档 |
| 任一场景遇到大版本 | 重新跑完整汇总（v2）作为新基线 |
| 字段/枚举口径出现漂移 | 立即 re-baseline，避免分叉放大 |

### 8.2 版本号与 chg 编号的关系

- `chg-001…` 按变更次数递增，永不回退、不重号。
- PRD `v1.0 / v2.0` 仅在**基线重建 / collapse / 大版本**时 bump，日常补丁不 bump。
- 即：多个 `chg` 可落在同一个 `v` 之下；一次 `v` bump 可能消化多个 `chg`。

### 8.3 澄清门禁（迭代版）

- 变更文档动笔前，若变更点无法写成可测试验收项（如「优化列表体验」），先用业务语言澄清（每次 ≤3 问），确认后才写入。
- 「模糊即问」的纪律必须保留，否则变更文档会产出垃圾 delta。

## 9. 工作流程

1. **定位基线**：确认本次迭代归属的基线文档（prd.md 或外部链接），确认它仍是当前事实来源。
2. **判定场景**：有可 diff 基线 → Case 1；无基线 → Case 2；改结构 → 升级回完整汇总。
3. **取号**：查已有最大 `chg` 编号，本次取「最大 + 1」。
4. **澄清（如需）**：变更点无法写成可测试验收项时，先业务澄清再动笔。
5. **写变更文档**：Case 1 写 delta（引用章节）；Case 2 写现状 + 变更 + 验收（自包含）。
6. **追加 chg 日志块**：`status` 默认 `active`。
7. **收口**：验收标准逐条可测、标注类型；文档随评审呈现，PM/TL 轻量确认后再流转。

## 10. 核心硬规则

1. 迭代不重复跑完整汇总——只写 delta，不复制未变更章节。
2. 每份变更文档都有 `chg` 日志块——这是跨迭代追溯、未来合并成基线的事实索引。
3. `chg-NNN` 永不回退、不重号；回滚新增一条 `status: reverted` 记录，不删除原记录。
4. 验收标准必须可测试且标注类型，只列本次变更相关项。
5. 改结构（新增 FR / 改状态机 / 改枚举口径 / 范围大扩）必须升级为完整汇总，不打补丁。
6. 模糊变更点先澄清（≤3 问）再动笔，禁止吞咽「优化体验」类垃圾 delta。

## 11. 边界（Do Not）

1. 不用变更文档替代完整 PRD 汇总——它是 delta，不是基线重建。
2. 不复制基线未变更章节进变更文档。
3. 不删除被回滚的 `chg` 记录，审计链必须保留。
4. 不把下游代码生成/接口合并契约纳入本技法（交接细节另见 downstream-handoff）。
5. 不因迭代而跳过人工确认——定稿后仍需 PM/TL 轻量闸门。

## 12. 质量自检清单

- [ ] 已定位基线并判定场景（Case 1 / Case 2 / 升级完整汇总）
- [ ] `chg` 编号取最大号 +1，未重号
- [ ] Case 1 只写 delta，未复制基线章节；Case 2 自包含（现状+变更+验收）
- [ ] 变更详情表格完整（新增/修改/删除字段、规则级、流程级、权限）
- [ ] 验收标准每条可测试且标注类型，未复制基线验收
- [ ] `chg` 日志块含 `status` 字段，回滚走新增记录
- [ ] 模糊变更点已在动笔前澄清
- [ ] 涉及结构变更的已升级为完整汇总，未打补丁
