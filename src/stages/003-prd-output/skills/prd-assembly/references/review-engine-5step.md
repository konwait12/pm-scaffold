# 统一评分引擎 5 步流水线（Review Engine 5-Step）

> 来源吸收：`incremental-prd-collaboration` 的 `prd-output-review-rubric.md`（统一评分引擎）+ `ai-prd-review-rubric.md` + `company-requirement-review-rubric.md`（两类规则集），作为 prd-assembly Human Gate 前的可选量化自检能力。
> 定位：把「评审 PRD 质量」从凭感觉变成固定 5 步流水线——`fetch / inspect / deep_check / scoring / decision`，并按输入来源切换规则集，保证结论可追溯、不跳步。
> 触发：prd.md 汇总完成、Human Gate 前需要结构化自评结论（pass/revise/reject），或上游原始材料（公司需求/字段化内容）混入待审时。**按需加载，不设全局闸门，advisory 级——不改状态机、不阻断 gate，最终以 review-taxonomy 裁决与 authorized-reviewers 人工批准为准。**

## 1. 输入映射

| 外部 skill 输入 | pm-scaffold 对应产物 | 说明 |
|---|---|---|
| 完整 PRD / AI 生成 PRD / 项目交付版 PRD | `prd.md`（§0–§12 已聚合，draft/ready_for_human_review） | 走 **AI PRD 规则集**，关注结构完整性与流程闭环 |
| 公司内部需求文档 / 禅道字段化导出 / 纯文本需求正文 | 上游原始材料（background-goal.md / requirement-restate.md 等，未经 PRD 化） | 走 **公司需求规则集**，关注章节完备度与模板适配度 |
| 来源混合（既有 PRD 又混字段化输入） | 先判 `input_type` 再选规则集 | 优先按公司需求规则集保证「来源兼容」，再补一轮 PRD 完整性视角 |
| 无需评分的输入（单条事实、一句话需求） | 不进入本引擎 | 不套 5 步流水线，避免过度工程 |

## 2. 引擎总览：固定 5 步流水线

流程固定为 `fetch → inspect → deep_check → scoring → decision`，**禁止跳步，禁止只检查部分模块**。

| 步骤 | 目标 | 至少输出 |
|---|---|---|
| 1. fetch | 确认文档已被完整读取，明确评审对象/范围/版本/来源 | 文档名或路径、`fetch_status`、是否完整读取成功、`input_type`、`active_rubric` |
| 2. inspect | 对全部模块做覆盖式巡检 | 每模块：模块名称、状态（`complete/partial/missing/n_a`）、原文依据 |
| 3. deep_check | 对已读内容做深层质量检查，找出矛盾/缺口/失配/不可执行点 | 表格：id、module、severity、finding、evidence |
| 4. scoring | 基于检查结果给出数值评分（总分 100） | 每维度：维度名称、得分、扣分原因、原文依据 |
| 5. decision | 根据总分与严重问题给出最终判定 | `total_score`、`critical_issue_count`、`decision`、`decision_reason` |

### 2.1 决策规则

- `score >= 90` 且无严重问题 → `pass`（可进入评审/下游协作）
- `60–89` → `revise`（主体可用，但必须先修补缺口）
- `< 60` → `reject`（结构或内容缺陷过大，不适合继续流转）

### 2.2 规则集切换（按输入来源）

| 判定结果 | 激活规则集 | inspect 覆盖 |
|---|---|---|
| AI 生成 PRD、正式 PRD、项目交付版 PRD | AI PRD 规则集 | 14 个模块 |
| 公司内部需求文档、禅道需求、字段化导出、纯文本正文 | 公司需求规则集 | 11 个必查模块 + 扩展模块 |
| 来源混合 | 先公司需求规则集兼容，再补 PRD 完整性 | 两套依次 |

某模块本阶段确实不适用时，也必须明确标记 `n_a` + 说明原因 + 给出原文依据。**不允许跳过任何一个模块不写。**

## 3. AI PRD / 正式 PRD 规则集（14 模块 + 5 维评分）

### 3.1 inspect 覆盖模块（status 只能是 complete/partial/missing/n_a）

1. 需求背景与目标
2. 目标用户 / 角色
3. 核心场景
4. 功能流程
5. 页面 / 模块方案
6. 页面流转与状态变化
7. 功能规则
8. 输入与输出
9. 文案与提示
10. 验收标准
11. 异常与边界处理
12. 最小可用版
13. 待确认清单
14. 可选附录 / 下游协作输入

### 3.2 deep_check 重点

1. 目标、用户、场景是否彼此一致
2. 功能主流程、关键分支和异常流程是否闭环
3. 页面职责、状态变化和主流程是否重复或冲突
4. 规则、异常、拦截、提示文案是否对齐
5. 输入项、输出项、结果页、埋点或上报项是否支撑验收
6. 最小可用版是否真实收敛（而不是重复正文目录）
7. 待确认项是否集中管理（而不是散落打断正文）
8. 下游协作附录是否足够支撑设计、研发、测试开工

### 3.3 scoring 维度（总分 100，每维 20 分）

| 维度 | 分值 |
|---|---|
| 背景、目标、用户、场景清晰度 | 20 |
| 功能流程与页面状态闭环度 | 20 |
| 规则、边界、异常严谨度 | 20 |
| 页面、文案、验收可执行度 | 20 |
| 范围收敛与整体交付质量 | 20 |

## 4. 公司需求 / 禅道需求规则集（11 模块 + 5 维评分）

### 4.1 inspect 必查模块（即使原文没有单独成章，也要按内容归类检查）

1. 需求背景 / 场景
2. 需求期望 / 目标
3. 功能流程 / 逻辑 / 规则
4. 产品实现方案 / 功能节点
5. 异常场景
6. 原型 / 设计稿信息
7. 灰度计划 / 上线安排
8. 权限配置
9. 新旧规则兼容 / 历史数据兼容
10. 与外部关联系统
11. 业务数据量 / 性能量级

原文若有以下扩展模块，一并检查：埋点需求、兼容性要求、安全要求、跨端/跨系统说明。

### 4.2 deep_check 重点

1. 背景是否说明「为什么做、解决什么问题、业务价值是什么」
2. 目标或期望是否可验证（而非方向性口号）
3. 功能流程、节点动作、完成条件是否清楚
4. 规则、异常、权限、兼容是否互相一致
5. 原型、设计稿、链接、关键页面入口是否足够支撑理解
6. 灰度计划、上线范围、外部系统、数据量是否可落地
7. 字段化抓取输入中，字段之间是否存在缺口、冲突或明显断层

### 4.3 输入形态补充规则

| 输入形态 | 处理规则 |
|---|---|
| 禅道字段化输入 | 先把字段映射到上述模块；没命中的模块标 missing/n_a；字段值冲突必须在 deep_check 标出证据 |
| 纯文本正文粘贴 | 先按段落语义归类；不要求原文按模板编号；最终输出仍必须覆盖全部检查模块 |

### 4.4 scoring 维度（总分 100，每维 20 分）

| 维度 | 分值 |
|---|---|
| 背景、目标、业务价值清晰度 | 20 |
| 功能流程、节点规则、完成条件闭环度 | 20 |
| 异常、权限、兼容、边界严谨度 | 20 |
| 原型、灰度、外部依赖、数据量可执行度 | 20 |
| 整体文档完整性与交付可用性 | 20 |

## 5. deep_check 纪律（只输出问题 + 严重度 + 证据）

`deep_check` 只允许输出：**问题是什么、严重度是什么、对应证据是什么**。

不允许在 deep_check 阶段输出：修改建议、优化建议、推荐写法、「可以补充」「建议增加」这类话术。

输出格式建议为表格，每条问题至少包含：

| 字段 | 说明 |
|---|---|
| `id` | 如 F-001 |
| `module` | 所属模块 |
| `severity` | `critical / major / minor` |
| `finding` | 只能描述问题，不得带建议 |
| `evidence` | 可追溯到章节或原文片段 |

## 6. 严重问题定义（可判定 critical 的情形）

1. 核心模块整段缺失，导致主流程无法理解
2. 规则集要求的关键模块明显缺失
3. 功能流程、节点规则或字段逻辑互相矛盾
4. 规则与验收标准或上线要求明显冲突
5. 主流程无法闭环
6. 关键异常场景缺失，导致结果不可判断
7. 下游协作、灰度、权限、兼容或外部依赖信息不足以支撑继续流转
8. 问题结论无法追溯到原文

## 7. 工作流程

1. 确定评审对象与输入来源，判定 `input_type`，选择激活规则集。
2. `fetch`：完整读取待审文档；读取失败立即终止并输出 `decision = terminate`。
3. `inspect`：按激活规则集对全部模块巡检，逐模块给 `status` 与原文依据。
4. `deep_check`：按规则集的 deep_check 重点逐条核对，输出问题表（只含问题/严重度/证据）。
5. `scoring`：按规则集的评分维度打分，逐维度给得分、扣分原因、原文依据。
6. `decision`：汇总总分与 critical 数，输出 pass / revise / reject 及理由。
7. 将评分结论作为 Human Gate 参考材料提交，最终批准权仍在 authorized-reviewers。

## 9. 核心硬规则

1. **禁跳步**：5 步流水线顺序执行，跳过任何一步即无效评审。
2. **fetch 必须成功**：未完整读取文档不得进入 inspect/deep_check/scoring。
3. **inspect 必须全覆盖**：任何模块不得跳过不写；不适用也必须标 `n_a` + 原因 + 依据。
4. **deep_check 禁建议**：只输出问题 + 严重度 + 证据，出现任何「建议补充」即违规。
5. **输出必须结构化**：禁止散文式、随意段落式结论。
6. **所有问题必须可追溯原文**：无原文依据不下结论。

## 10. 边界（Do Not）

1. 不改变 prd.md 产物状态机，不接入 validate_artifact.py，不产生 blocking 闸门。
2. 不在评分中引入 prd-scoring-rubric 之外的跨模块抵扣或总分封顶逻辑。
3. 不用 AI PRD 规则集去评纯公司需求正文（先切规则集，再评分）。
4. 不因某维度 0 分而连带拉低其他独立维度（模块间独立评分）。
5. 不把 `pass` 当作人工批准的替代品——最终由 authorized-reviewers 拍板。

## 11. 质量自检清单

- [ ] 已按 `fetch → inspect → deep_check → scoring → decision` 全流程执行，无跳步
- [ ] `input_type` 与 `active_rubric` 已明确，规则集选择有依据
- [ ] inspect 覆盖激活规则集全部模块，无跳过、不适用项已标 `n_a` 并给原因
- [ ] deep_check 每条问题含 id/module/severity/finding/evidence，且不含任何建议性表述
- [ ] 每个扣分/问题都能追溯到原文章节或片段
- [ ] scoring 各维度独立计分，输出得分、扣分原因、原文依据
- [ ] decision 结论（pass/revise/reject）与总分、critical 计数一致
- [ ] 本评审结论仅作 Human Gate 参考，未替代人工批准
