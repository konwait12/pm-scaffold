# PRD 结构 9 问最小判断（Structure 9Q）

> 来源吸收：`incremental-prd-collaboration` 的 `prd-structure-checklist.md`（PRD 结构检查清单），作为 prd-assembly Generate 阶段的结构自查能力。
> 定位：用 9 个最小问题判断一份 PRD 结构是否可评审，并用「章节职责 + 快速判断规则」决定某段内容该放哪——避免把次要部分写厚而主缺口未补。
> 触发：prd.md 聚合完成、Generate 前后不确定结构是否完整时；或 review 中发现「缺了某一层」时。**按需加载，不设全局闸门。**

## 1. 输入映射

| 外部 skill 输入 | pm-scaffold 对应产物 | 说明 |
|---|---|---|
| 已有一版 PRD，不确定结构是否完整 | prd.md 已聚合 §0–§12 草稿 | 9 问逐一对照，找缺口 |
| 「是不是还缺某一层」的疑问 | Generate 阶段章节草案 | 用章节职责对照定位缺失层 |
| 「某段内容该放哪」的犹豫 | 12 个上游产物中的片段 | 用快速判断规则路由到正确章节 |

## 2. 最小结构判断：9 问

一份可评审的 PRD，通常至少要能回答下面这些问题：

| # | 问题 | 对应 prd-assembly 章节 |
|---|---|---|
| 1 | 为什么做这件事 | §1 项目背景与目标 |
| 2 | 给谁用 | §2 用户旅程 / 用户角色 |
| 3 | 在什么场景下用 | §2 用户旅程 / 场景 |
| 4 | 主流程怎么走 | §5 功能流程 |
| 5 | 关键分支和异常流程怎么处理 | §5 功能流程 + §11 异常处理 |
| 6 | 页面本身承载什么信息和状态 | §6 页面设计 |
| 7 | 系统按什么规则判断 | §8 业务规则 + §9 校验规则 |
| 8 | 成功、失败、异常时分别怎样处理 | §7 交互规则 + §11 异常处理 |
| 9 | 怎么验收 | §12 验收依据 |

**修订优先级**：如果上述问题有明显空缺，优先补齐，而不是继续扩写次要部分。缺项时按以下顺序补：

1. 功能目标和核心场景
2. 功能流程
3. 页面 / 模块方案与状态变化
4. 关键规则
5. 异常与边界处理
6. 验收标准
7. 最小可用版、待确认清单和下游交接

## 3. 常见章节职责（每节回答什么问题）

### 3.1 需求背景与目标（§1）

用于说明：为什么现在做、目标用户是谁、核心场景是什么、不做会有什么问题。

**不要在这里堆页面细节或接口字段。**

### 3.2 功能流程（§5）

用于说明整个执行链路：从哪里触发、用户怎么进入、系统做什么、流程在哪里分支、异常在哪里中断、结束后流向哪里。

> 功能流程回答的是「这件事整体怎么走、哪里会分叉、失败后怎么办」。

### 3.3 页面 / 模块方案（§6）

用于说明每个页面或模块自身的静态要求：页面目标、核心信息、核心模块、主操作/次操作、Loading/空态/错误态/无权限态。

> 页面 / 模块方案回答的是「这个页面本身该承载什么内容和动作」。

### 3.4 页面流转与状态变化（§6/§10）

用于补充跨页面状态差异：哪些状态下按钮可点或不可点、成功和失败时停留在哪、同一页面在不同状态下展示差异是什么。

> 这一节回答的是「页面状态怎么变」，**不应该再重复完整主流程**。

### 3.5 功能规则表（§8 业务规则）

用于说明判断逻辑：什么条件命中什么规则、系统如何判断、系统动作是什么、哪些是硬约束。

> 规则表回答的是「系统按什么口径作出判断」。

### 3.6 异常与边界处理（§11）

用于说明逆向路径：输入异常、流程异常、回退和重试、人工接管。

> 异常章节回答的是「主流程走不通时怎么办」。

### 3.7 最小可用版与待确认清单（§3 范围 + 附录）

用于收敛范围和留口：本期必须做什么、本期明确不做什么、哪些放后续迭代、哪些暂时未确认但会影响后续评审或落地。

> **不要把未确认项零散插入正文主干**——集中管理，散落即失口径。

### 3.8 下游协作附录（§12 附录）

用于把 PRD 转成交接清单：设计先看什么还缺什么、研发先看什么要冻结什么、测试先看什么要重点覆盖什么。

> 不要把它写成正文目录复读机（详见 `downstream-handoff.md`）。

## 4. 快速判断规则（内容归属路由）

如果你在犹豫某段内容该放哪，按下面判断：

| 内容讲的是… | 放哪 |
|---|---|
| 主链路、关键分支、异常中断 | 功能流程 |
| 页面职责、内容、静态状态 | 页面 / 模块方案 |
| 跨页面状态差异和跳转结果 | 页面流转与状态变化 |
| 条件判断和系统动作 | 规则表（业务规则） |
| 失败、回退、补偿 | 异常与边界处理 |
| 给设计 / 研发 / 测试怎么接手 | 下游协作附录 |

## 5. 工作流程

1. 对 prd.md 草稿跑一遍 9 问：逐问找原文依据，无依据即缺口。
2. 将缺口按修订优先级排序（目标场景 → 流程 → 页面状态 → 规则 → 异常 → 验收 → 附录）。
3. 用快速判断规则处理「内容放哪」的犹豫，避免错位堆叠。
4. 对照章节职责确认：背景节没有堆页面细节、页面状态节没有重复主流程、未确认项没有散落正文。
5. 缺口存在时：能由上游确认的（如规则缺失）路由回对应 work item，不能确认的登记 issue-record。
6. 结构补齐后，再进入 Audit 阶段结构校验（`validate_artifact.py`）。

## 6. 核心硬规则

1. 9 问任一有明显空缺，优先补齐而不是扩写次要部分。
2. 背景 / 目标节不得堆页面细节或接口字段。
3. 页面流转与状态变化节不得重复完整主流程。
4. 未确认项集中管理，不零散插入正文主干。
5. 下游协作附录不写成目录复读机。
6. 结构缺口路由回原 work item，不在 prd-assembly 内自答新业务问题。

## 7. 边界（Do Not）

1. 不用 9 问替代机器校验（`validate_artifact.py` 结构校验仍必须运行）。
2. 不因 9 问通过就跳过追溯审计——结构完整 ≠ 链完整。
3. 不为凑结构而捏造内容，稀疏输入时宁可标记缺口。
4. 不把「该放哪」的判断变成新增章节的借口，12 节结构是基线。
5. 不在本技法中回答新的业务问题，缺口一律路由或登记。

- [ ] 页面状态节未重复完整主流程
- [ ] 未确认项集中管理，无散落正文
