# 对抗式复审与自检三维（Grill-Me & Selfcheck 3D）

> 来源吸收：`product-spec-generator` 的 `grill-me.md`（对抗式人工复审）、`prd-section-grill.md`（四阶段对抗自检）、`prd-selfcheck-structure.md` / `prd-selfcheck-consistency.md` / `prd-selfcheck-hallucination.md`（结构/一致性/幻觉三维收口），作为 prd-assembly Human Gate 与 Audit 前的可选对抗能力。
> 定位：机器审计管「结构/追溯/边界」，这套技法管「业务层对抗」——签发前用人工一道 grill-me 做业务判断层复审，过程中用四阶段 grill 逼出漏洞，收口前用三维自检清零占位与幻觉。
> 触发：Human Gate 前由 PM 主动发起「签发前复审」；Generate/Audit 阶段发现跨模块疑点需对抗核验时。**按需加载，不设全局闸门；不接入 validate_artifact.py、不改状态机。**

## 1. 输入映射

| 外部 skill 输入 | pm-scaffold 对应产物 | 说明 |
|---|---|---|
| 待签发 PRD（grill-me 对象） | prd.md（ready_for_human_review 候选） | 人工一道，业务层对抗复审 |
| 每节/每模块写完即 grill | 12 个上游产物聚合过程中的各节草稿 | 过程内增量早筛，不等收口 |
| 结构三维评分 + 模板完整性 | prd.md §0–§12 结构 | 收口前检查结构完整与模板一致 |
| 一致性冲突扫描 P0/P1/P2 | 跨章节引用/口径核对 | 冲突清单喂给 review-taxonomy 的 [Contradiction] 扫描 |
| 幻觉清除 + 待澄清项 | 无来源的事实性陈述 | 待澄清项喂给 Clarify / issue-record |

## 2. grill-me：签发前人工一道（受控触发）

### 2.1 触发（仅显式）

| 触发方式 | 示例 |
|---|---|
| 关键词 | `grill-me`、`对抗复审`、`挑战我的PRD`、`签发前复审` |
| @ 提及 | `@grill-me` |
| 脚手架引导 | prd-assembly Human Gate 前由 PM 主动发起 |

### 2.2 执行循环（沿用原版 grilling 指令）

> Interview me relentlessly about every aspect of this until we reach a shared understanding. Walk down each branch of the decision tree, resolving dependencies between decisions one-by-one. For each question, provide your recommended answer.

- 一次只问一个问题，等待反馈后再继续；一次多问只会让人困惑。
- 能从环境（文件/工具）查到的**事实**直接查，不要拿去问用户；**决策**才是用户的——逐个抛出并等待回答。
- 未确认「达成共识」前，不替用户做任何改动。

### 2.3 在 prd-assembly 中的定位

- **不进入** Audit 的机器自检链（避免每发现一处就打断聚合）。
- 机器链已覆盖：`validate_artifact.py` + traceability + branch_validator + review-taxonomy 扫描。grill-me 补**人工这一道**——业务判断层。
- 典型问法（针对 prd.md）：「这个 MVP 范围砍得对吗？」「≥50% 目标有依据吗？」「状态机 cancelled 终态会不会漏审计？」「P0 功能 FEA-002 的验收真能证明 G-001 达成吗？」

### 2.4 纪律

- 每次只问一个问题，附推荐答案，等用户反馈后再下一题。
- 事实直接查、决策才问。
- 未确认达成共识前，不替用户做任何改动。

## 3. section-grill：四阶段过程内对抗自检（G1→G4）

### 3.1 G1 · 静默重读（Silent Re-read）

先不质疑，把上下文读全：
- 重读刚写完的这一节（或模块）全文。
- 重读它引用/被引用的依赖：上游定义（BR-XXX / SM-XXX / 字段表）、下游将消费它的模块。
- 在心里建立「这一节声称了什么」的清单，**不要边读边问**。

### 3.2 G2 · 风险挖掘（按负载分级）

从 G1 清单里挑出**负载决策**——错了会拖垮下游的，按强度分级挑战：

| 强度 | 触发信号 | 是否必须 grill |
|---|---|---|
| 🔴 高 | 涉及钱/积分/权限/数据正确性/跨模块字段定义 | 必须 |
| 🟡 中 | 业务规则边界、状态流转、异常兜底 | 必须 |
| 🟢 低 | 纯展示文案、UI 提示语、非关键排序 | 可跳过 |

对每个高/中负载决策，形成**一个尖锐的 grill 问题**（一次只问一个）：
- 字段类：「customerStatus 在关键字段表定义了吗？下游 FR 的筛选项和表格列枚举和它一致吗？」
- 规则类：「超量你说『提示用户』，但没说上限是多少、超限后能否提交——这是硬约束还是软提示？」
- 状态类：「状态『已取消』在状态机里有，但异常处理没覆盖它卡住的情况——失败模式是什么、谁来处理？」
- 边界类：「时间范围筛选含不含当天？空数据和『0 条』的展示区分了吗？」

### 3.3 G3 · 逐项 Grill（一次一问）

| 判定 | 含义 | 动作 |
|---|---|---|
| ✅ PASS | 本节已给出具体、可辩护的答案（有数值/有规则/有来源/有兜底） | 通过 |
| ⚠️ 待澄清项 | 出现「适当」「支持」「可再细化」「等」「相关」等模糊词，或数值缺失 | 未防御决策，升级为待澄清项 |
| ❌ 一致性冲突 | 本节内部或与上游矛盾（同字段两处枚举不同、状态机与异常缺口） | 升级为一致性冲突项（P0/P1） |

### 3.4 G4 · 判定（Verdict）

- 全部 PASS → 通过，继续下一节。
- 存在待澄清项 → **必须**交 Clarify 机制补齐具体值后替换正文，重新 grill 至全 PASS。
- 存在一致性冲突 → 记录到不一致报告，路由回最早受影响的 work item；闭环前不进输出。

### 3.5 输出格式（写在该节/模块末尾）

```markdown
> 🔥 Grill 自检（小节 FEA-003 / 大节 模块五）
> - [x] 字段 customerStatus：上游已定义，枚举与 FEA-003 筛选项/表格列一致 → PASS
> - [x] 规则 BR-004 超量：明确上限 100 条、超限拦截提交 → PASS
> - [!] 边界：时间范围是否含当天未写清 → 待澄清项（已交 Clarify）
> 结论：1 项待澄清，补齐后通过
```

## 4. 自检三维（收口总检，Audit 前跑）

### 4.1 维度一：结构自检（三维评分 + 模板完整性）

| 分 | 含义 |
|---|---|
| 5 | 完整且无缺口，可直接进入下一阶段 |
| 4 | 基本完整，仅极轻微可优化点（不阻塞） |
| 3 | 主体齐全，但有明显缺口需补写 |
| 2 | 关键部分缺失或错误 |
| 1 | 严重缺失，几乎不可用 |

| 维度 | 打分锚点 |
|---|---|
| 方向 | 5=目标+量化指标齐全且可衡量；3=有目标但缺量化；1=目标与需求脱节 |
| 结构 | 5=§0–§12 齐全顺序对；3=缺 1-2 个非核心节；1=缺核心节 |
| 细节 | 5=字段枚举全、规则有实现方、验收可测；3=有占位或边界不清；1=大量 TBD 倾向 |

模板完整性硬指标（任一项不达标即「结构」维度不得给 5）：FR 编号连续无跳号；验收条目数 ≥ 预估；BR 编号连续且标注实现方；名词/字段均被下游引用且一致。**任何 <3 分必须列出具体待补项。**

### 4.2 维度二：一致性自检（冲突扫描 P0/P1/P2）

| 检查项 | 内容 |
|---|---|
| 字段三元组 | 每个关键字段（出现在 ≥2 处）核对：定义位置 ✓ 使用位置 ✓ 枚举一致性 ✓，任一处缺失即冲突 |
| 引用完整性 | 每处 BR-XX / AC-XX / EX-XX / FR-XX 引用，对应定义处必须存在该编号 |
| 状态机三元 | 状态机状态全集 ↔ 异常覆盖 ↔ 业务规则触发条件；任一状态无异常兜底即冲突 |
| 权限一致性 | 权限矩阵与操作/角色可见性一致 |
| 术语一致性 | 同一概念全篇用词统一 |

| 级别 | 定义 | 处理 |
|---|---|---|
| P0 | 阻断性矛盾：字段无定义却被引用 / 状态机与异常缺口 / 引用悬空 | 必须修复后才能输出 |
| P1 | 明显不一致：枚举取值不符 / 角色与权限错位 | 必须修复，可批注后让用户确认 |
| P2 | 轻微不一致：命名口径差异 / 描述冗余 | 建议修复，不阻塞 |

### 4.3 维度三：幻觉清除（事实溯源 + 待澄清项）

凡属事实性陈述都必须可追溯到来源，范围包括但不限于：具体数字（用户量/百分比/性能阈值/金额）、归因结论（「因为 X 所以提升 Y」）、范围声明（「覆盖 N 个角色」「全部渠道」）、角色/权限断言（「仅管理员可」）、业务目标量化指标。

| 来源类型 | 处理 |
|---|---|
| 上游已确认产物 / 用户输入 / 澄清结果 | 标记 PASS |
| 模板基线值（如通用性能阈值） | 标记「基线·待评审」——不算幻觉，但需人工最终拍板 |
| 无任何来源、且非基线 | 标记「待澄清项」，附推测依据与建议提问，交 Clarify / 登记 issue-record |

**红线**：`待确认` / `TBD` 是「需澄清」的信号，不是「可定稿」的内容。PRD 正文不得保留待确认占位。

## 5. 工作流程

1. Generate 每节完成后：跑 G1–G4 小节 grill，产出 🔥 自检块。
2. 每模块收尾：跑大节 grill，串联上下游，重点查跨模块口径。
3. Audit 前：跑结构三维评分 + 模板完整性检查。
4. Audit 中：跑一致性冲突扫描，P0/P1 写入不一致报告并路由。
5. 输出前：跑幻觉清除，所有事实溯源，待澄清项清零。
6. Human Gate 前：PM 主动触发 grill-me 人工一道，逐问达成共识后才放行。

## 6. 核心硬规则

1. 一次一问：grill 问题逐个抛出，禁止一次性倾倒全部问题。
2. 拒绝含糊：凡答案含「适当/支持/等/相关/可再细化」，一律判未防御，不得放行。
3. 专挑负载：低影响项直接跳过，火力集中在高/中负载决策（🔴/🟡）。
4. 要具体辩护：每个放行的决策，正文里必须能找到具体数值/明确规则/来源标注。
5. 不自行脑补：grill 发现缺口交 Clarify，绝不自己编一个值填上。
6. P0 冲突与待澄清项闭环前，PRD 不得进入输出/批准。

## 7. 边界（Do Not）

1. 不把 grill-me 接入机器自检链——它是人工一道，只在签发前或用户主动触发时跑。
2. 不用自检三维替代 `validate_artifact.py` / traceability_check / branch_validator 机器审计。
3. 不在一致性扫描中直接删改内容——发现冲突必须带严重级别与修复建议再路由。
4. 不把「模板基线值」当幻觉清除——需标注待评审而非静默删除。
5. 不让待澄清项以 `待确认`/`TBD` 占位残留在正文。
6. 不在 grill 结论中替用户做最终取舍——决策权归人工。
