# 下游交接三视角（Downstream Handoff）

> 来源吸收：`incremental-prd-collaboration` 的 `downstream-handoff.md`（下游协作交接清单）+ SKILL.md 产品边界，作为 prd-assembly 附录 §12 的落地能力。
> 定位：把已聚合的 prd.md 转成给设计 / 研发 / 测试的可执行交接清单——不是重复正文目录，而是告诉每个角色「先看什么 / 产出什么 / 缺什么会阻塞开工」。
> 触发：prd.md 接近定稿、准备交下游开工时；或 Human Gate 呈现「这份 PRD 能不能开工」时。**按需加载，不设全局闸门。**

## 1. 输入映射

| 外部 skill 输入 | pm-scaffold 对应产物 | 说明 |
|---|---|---|
| PRD 正文各章节（流程/页面/规则/异常/验收） | prd.md §1–§11 各节 | 交接清单只引用、不重写正文 |
| 待确认项 / 未决风险 | prd.md 附录 + issue-record / UNK-XXX | 「缺什么」必须指向明确缺口而非泛泛而谈 |
| 上游基线（user-journey / functional-flow / business-rules 等） | 12 个上游 confirmed 产物 | 交接时标注优先级阅读顺序 |
| 无交接价值的纯目录 | 不生成 | 下游附录不允许复读章节标题 |

## 2. 核心原则

下游协作附录不是把正文标题重新抄一遍。它的价值是告诉不同角色三件事：

1. **先看什么**——该角色开工前优先阅读的章节。
2. **继续产出什么**——该角色需要基于 PRD 继续产出的交付物。
3. **当前还缺什么**——哪些信息缺口会阻塞该角色开工。

一句话模板（时间紧时最少也要让每个角色看到这三类信息）：

> 先看什么 / 要产出什么 / 当前缺什么

## 3. 给设计（Design）

### 3.1 设计真正关心的通常是

- 功能主流程和关键页面状态
- 页面目标和状态
- 异常态和风险提示
- 关键文案和按钮文案

### 3.2 设计附录建议写

| 栏目 | 内容 |
|---|---|
| 优先阅读章节 | 功能流程、页面设计、交互规则、异常处理 |
| 需要继续补的设计产物 | 页面稿、空态/错误态/无权限态视觉、关键文案确认 |
| 当前阻塞设计定稿的信息 | 未决的文案口径、未定的页面状态清单 |

## 4. 给研发（Engineering）

### 4.1 研发真正关心的通常是

- 哪些规则已经冻结
- 页面如何流转
- 输入输出口径是什么
- 异常分支和权限边界是什么

### 4.2 研发附录建议写

| 栏目 | 内容 |
|---|---|
| 优先阅读章节 | 业务规则、校验规则、状态变化、异常处理 |
| 需要继续拆出的研发产物 | 接口方案、数据模型、状态机落地、异常码映射 |
| 当前阻塞研发落地的信息 | 未冻结的规则、冲突的枚举口径、缺位的权限矩阵 |
| 建议先冻结的核心口径 | 关键字段定义、状态集合、输入输出边界 |

## 5. 给测试（QA）

### 5.1 测试真正关心的通常是

- 主流程和逆向流程
- 关键规则和验收口径
- 模式差异、状态差异、权限差异
- 哪些地方风险最大、最容易漏测

### 5.2 测试附录建议写

| 栏目 | 内容 |
|---|---|
| 优先阅读章节 | 验收依据、异常处理、状态变化、校验规则 |
| 优先覆盖的用例范围 | 主路径 + 关键分支 + 高负载异常 |
| 当前需要重点关注的风险 | 跨状态流转、权限边界、历史数据兼容 |

## 6. 常见低价值写法（对照自检）

| 低价值写法 | 正确做法 |
|---|---|
| 只列「需求背景 / 流程图 / 规则表 / 异常场景」 | 按角色给差异化阅读顺序与缺口清单 |
| 不区分设计、研发、测试的差异 | 三个角色分别给「先看/产出/缺口」 |
| 不说明当前缺什么 | 每个角色明确列出阻塞开工的缺口 |
| 不说明谁应该先看什么 | 优先阅读章节指向明确 ID（FEA-XXX / BR-XXX / AC-XXX） |

## 7. 产品边界红线（源自 incremental-prd-collaboration 产品边界）

PRD 用**产品语言**描述数据需求，只说明：输入项、输出项、业务含义、使用位置。

**不要默认展开成**以下实现细节：

| ❌ 不写 | 说明 |
|---|---|
| API 路径 | 如 `/api/v1/order` |
| HTTP 方法 | GET/POST/PUT/DELETE |
| 异常码 | 如 `40001` |
| 数据库结构 | 表结构、索引、SQL |
| 字段类型 | `string`、`enum`、`text`、`object` 这类类型标注 |

用户明确要求技术设计时，把它当作 **PRD 之后的另一层工作**来处理（如 domain-mapping-hint / ADR 交接），而不是提前滑入实现细节。交接清单中如出现「接口配置建议」类内容，仅写建议与业务约束，具体接口方案由研发产出。

## 8. 工作流程

1. 确认 prd.md 各节已聚合、正文不再变化。
2. 对设计 / 研发 / 测试三个角色，分别提取「先看什么」：列出优先阅读章节与关键 ID。
3. 分别提取「产出什么」：该角色基于 PRD 需继续交付的产物清单。
4. 汇总「缺什么」：从 issue-record、UNK-XXX、待确认项中筛选每个角色的阻塞缺口。
5. 检查是否落入低价值写法：若只是目录复读，重写为差异化信息。
6. 对照产品边界红线：确认交接清单未滑入 API/HTTP/异常码/DB 结构/字段类型。
7. 将交接清单作为 prd.md 附录（或 99-review 交接材料）随 Human Gate 一并呈现。

## 9. 核心硬规则

1. 每个角色必须有三类信息：先看什么 / 产出什么 / 缺什么。
2. 交接清单只引用正文，不重写正文内容。
3. 所有「缺什么」必须可追溯到具体缺口（UNK-XXX / issue-record / 待确认项）。
4. 三个角色差异不抹平：设计、研发、测试的阅读顺序与缺口不得混写。
5. 产品边界红线六不写：API 路径、HTTP 方法、异常码、DB 结构、字段类型、SQL。
6. 技术设计请求路由到 PRD 之后的另一层工作，不在交接清单内展开。

## 10. 边界（Do Not）

1. 不把附录写成正文目录复读机。
2. 不替设计/研发/测试产出他们的交付物，只列「该产出什么」。
3. 不把「缺什么」写成模糊描述（如「待补充」），必须指向缺口 ID。
4. 不默认展开技术实现细节，除非用户明确要求技术设计层。
5. 不把下游交接当作新增需求的入口——发现缺口先路由回原 work item。

## 11. 质量自检清单

- [ ] 设计 / 研发 / 测试三个角色各有独立的「先看什么 / 产出什么 / 缺什么」
- [ ] 每个角色的优先阅读章节指向具体节或 ID，不是整篇 PRD
- [ ] 「缺什么」全部可追溯到 UNK-XXX / issue-record / 待确认项
- [ ] 正文未被重写，附录仅引用
- [ ] 未出现 API 路径、HTTP 方法、异常码、DB 结构、字段类型、SQL
- [ ] 无「只列章节标题不区分角色」的低价值写法
- [ ] 交接清单随 Human Gate 材料一并呈现，可支撑「这份 PRD 能不能开工」的判断
