# 访谈信息提炼技法（Interview Synthesis）

> 来源吸收：`incremental-prd-collaboration` skill 的 `references/interview-synthesis.md`（访谈五步提炼法）+ `juloko` skill 的 `references/question-crafting.md`（问题措辞 5 铁律），作为 requirement-restate 的可选落地能力。
> 定位：把"大量口语化描述/会议纪要/访谈原话"从聊天记录提炼成可写进 PRD 的结构化需求，避免"原话堆叠"和"方案当需求"两种失真。
> 触发：Intake 阶段面对大量访谈原话、聊天记录、会议纪要而写不成需求时；Clarify 阶段需要把缺口翻译成业务方能答的问题时。**按需加载，不设全局闸门**。

## 1. 输入映射（pm-scaffold 语境）

| 外部 skill 输入 | pm-scaffold 对应产物 | 说明 |
|---|---|---|
| 访谈原话/聊天记录 | requirement-restate 的 SRC-* 来源 | 提炼对象 |
| 五步提炼结果 | RR-NNN 重述行 + user-journey / user-stories | 目标→背景、角色→用户、场景→旅程 |
| 规则与风险 | business-rules 的 BR-XXX / issue-record Q-XXX | 允许/不允许/成功条件/失败处理 |
| 待确认口径 | issue-record 的 Q-XXX（INF） | 口径未定项路由澄清 |

> 访谈原话适合保留在需求访谈记录，**不要直接搬进正式 PRD**——PRD 需要可执行表达，不是聊天记录。

## 2. 先分"事实"和"方案"（搬入自 interview-synthesis）

访谈里经常混在一起的两类内容：

- **事实**：现在怎么做、谁在用、哪里痛、什么规则已确定
- **方案**：想做什么页面、想加什么按钮、觉得应该怎么实现

先把事实抽出来，再决定方案怎么写进 PRD。看到方案型表述，必须向上追问一层"为什么"，这是 PM 与传声筒的分界线。

## 3. 访谈五步提炼法（搬入自 interview-synthesis）

### 第 1 步：提炼目标
把原话改写成一句"为什么做"：
- 当前有什么问题
- 想改善什么结果

### 第 2 步：提炼角色
明确：
- 谁是直接使用者
- 谁是协作方
- 谁提供输入或消费输出

### 第 3 步：提炼场景
把口语化描述改成结构化场景：
- 在什么情况下触发
- 用户要完成什么动作
- 系统要承接什么

### 第 4 步：提炼功能点
把"零散动作"整理成功能项，而不是原话堆叠。

例如**不要写**：
- 要有按钮
- 点进去再跳一个页
- 最后给个结果

**要整理成**：
- 入口展示
- 场景说明页
- 模式进入
- 结果展示

### 第 5 步：提炼规则与风险
从原话里找这些内容：
- 什么情况下允许
- 什么情况下不允许
- 成功条件是什么
- 失败时怎么办
- 哪些口径还没定

## 4. 一份原话通常落到这些 PRD 位置（搬入自 interview-synthesis）

| 提炼内容 | PRD 落位 |
|---|---|
| 为什么做 | 背景 / 目标 |
| 谁在用 | 用户 / 角色 |
| 在哪用 | 核心场景 |
| 要承接什么 | 功能清单 |
| 怎么判断 | 规则表 |
| 失败怎么办 | 异常场景 |
| 哪些还没定 | 待确认事项 |

## 5. 问题措辞 5 铁律（搬入自 juloko question-crafting）

差的提问 = 业务方看不懂 → 不回 → 调研卡死。写问题必须遵守 5 条铁律：

1. **用业务语言，不用黑话。** ❌"请明确状态机终态定义" ✅"这张单子办完之后，还会不会再被打开改动？"
2. **给选项，降低回答成本。** ✅"历史工单是（A）全迁（B）只迁近 1 年（C）不迁？" 比开放问句回收率高 3 倍。
3. **先说影响，再问。** 业务方愿意答"不答会怎样"的问题。✅"如果不定超时时长，系统不知道什么时候升级催办，可能又出现漏办超期——您看超时按几小时算？"
4. **一次问一类，不堆叠。** ❌"权限、接口、迁移都怎么弄？" ✅ 拆成 3 条独立问题，分别标建议问谁。
5. **追问"为什么"挖真需求。** 业务方给方案时，问题要逼出动机：✅"您想要自动提醒，是因为出现过漏办的情况吗？大概多久一次？"

### 四类问题的写法模板（搬入自 juloko question-crafting §2）

| 类型 | 模板 | 示例 |
|------|------|------|
| 缺失事实 | "关于【X】，目前是按【选项】哪种处理？" | "关于工单撤回，目前是允许随时撤，还是审批后就不能撤？" |
| 边界确认 | "【阈值】本身是走【A】还是【B】？" | "金额 1000 元整，算大额要审批，还是算小额自动过？" |
| 假设确认 | "我按行业惯例先假设【假设】，可以吗？若有不同请告诉我。" | "我假设默认审批人是直属主管，可以吗？" |
| 冲突仲裁 | "文档说【A】，您会上说【B】，以哪个为准？" | "规则表写超时 24h，您说 48h，以哪个为准？" |

### 问题清单字段规范（搬入自 juloko question-crafting §3）

| 字段 | 填写要求 |
|---|---|
| 编号 | Q-01 递增（冲突用 C-01，假设用 A-01，便于回查） |
| 优先级 | P0/P1/P2（按 gap-checklist-14d 定级） |
| 问题（业务语言） | 按 5 铁律写，这是最关键的一列 |
| 为什么要问 | 一句话，帮 PM 判断紧迫度 |
| 不答的后果 | 最严重会怎样（卡开工/返工/合规风险） |
| 建议问谁 | 具体角色（王经理/张总/IT），不写"业务方" |
| 状态 | 未答 / 已答 / 已确认 / 已否决 |

## 6. 工作流程

1. **分事实/方案**：先把事实抽出来，方案型表述单独标记待追问。
2. **五步提炼**：目标 → 角色 → 场景 → 功能点 → 规则与风险，逐段输出结构化条目。
3. **落位映射**：按"一份原话 → PRD 位置"表把条目分配到对应模块。
4. **登记待确认**：口径未定项落 issue-record Q-XXX；冲突落 CONFLICT（CLS）。
5. **生成问题清单**：对缺口按 5 铁律翻译成业务语言问题，附建议问谁。

## 7. 核心硬规则

1. **不搬原话进 PRD**：保留原意，改写为产品语言、结构化表达、可评审的规则；原话留在访谈记录。
2. **先事实后方案**：功能点提炼以"用户要完成什么动作/系统承接什么"为准，不写"要有按钮"式原话堆叠。
3. **方案必追"为什么"**：任何方案型表述必须向上追问一层动机，追问不到进问题清单。
4. **问题用业务语言**：禁止状态机/接口/字段等黑话；先给选项、先说影响、一次问一类。
5. **每条有来源与去向**：提炼结果挂 SRC-*，并指明落位模块，防止悬空。
6. **口径未定不静默**：所有"还没定"进待确认清单，不自行假设。

## 8. 边界（Do Not）

- 不把访谈记录当 PRD 正文——只作提炼输入。
- 不替业务方定义规则——允许/不允许/成功条件以业务方为准，未明示进清单。
- 不一次堆叠多个独立问题——拆成单类问题并标注建议问谁。
- 不把"想要什么功能"直接当需求——先追动机再落位。
- 不用技术黑话提问（状态机/接口/幂等）——一律翻译成业务语言。

## 9. 质量自检清单

- [ ] 五步提炼（目标/角色/场景/功能点/规则风险）每步都有产出
- [ ] 功能点是结构化表达，无"要有按钮"式原话堆叠
- [ ] 规则与风险覆盖：允许/不允许/成功条件/失败处理/未定口径
- [ ] 提炼条目挂 SRC-* 并注明 PRD 落位模块
- [ ] 问题按 5 铁律书写，无黑话、带选项、先说影响、一次一类
- [ ] 方案型表述均已追问"为什么"
- [ ] 未定口径全部进待确认清单，无静默假设
