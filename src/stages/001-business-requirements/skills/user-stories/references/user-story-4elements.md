# 用户故事四要素模板（User Story 4 Elements）

> 来源吸收：work-buddy `prd-development` skill 阶段三「用户故事」的统一编号 US-XX 四要素模板（角色/场景/意图/动机）。作为 user-stories 产出 ST-XXX 时的可选增强写法。
> 定位：本脚手架 ST-XXX 已用 As a / I want / so that 范式；本文档把「四要素」补充为更具体的结构化模板，强化**场景**与**动机**两个常被一句话故事省略的高价值字段，让验收条件与优先级更有据可依。
> 触发：Generate 故事卡片时，为 ST-XXX 补齐四要素而非常规一句话；尤其用于动机与验收条件易混淆的故事。**按需加载，不设全局闸门**。

## 1. 四要素模板

每条用户故事统一编号 `ST-XX`，含四个字段——角色 / 场景 / 意图 / 动机：

```
ST-0X：[故事标题]
- 角色：作为 [具体角色]（"安全分析师"而非"用户"）
- 场景：当 [触发条件/情境]（何时、何地、何种状态触发）
- 意图：希望 [达成的结果，动词开头]（想完成的可观察动作）
- 动机：以便 [背后的目标]（达成意图后兑现的业务/用户价值）
```

| 要素 | 一句话引导 | 失败写法 | 达标写法 |
|---|---|---|---|
| 角色 | 谁来做 | "用户" | "运营人员" |
| 场景 | 何条件触发 | 缺省（默认"打开页面"） | "当有 3 条以上待审批工单时" |
| 意图 | 想做成什么（动词开头） | "系统显示列表" | "我能够批量审批相似工单" |
| 动机 | 为什么值得做 | "……的功能" | "以便我在 5 分钟内清空积压而非逐条处理" |

## 2. 核心硬规则

1. **四要素缺一不可**；「动机」必须落到可衡量的用户/业务价值，不允许写成功能堆砌；确无法回答的字段标 `待确认`，不硬编。
2. **角色要具体可识别**；禁止"用户/管理员/前端"这类合并表述（对齐 `job-story-and-moat.md` 的角色具体化）。
3. **意图以动词开头、描述用户可观察的结果**；严格区分"要什么"与"怎么做"——做法归 `feature-list`，不混入故事。
4. **"和/并且"出现即拆故事**：每个故事只承载一个可独立交付与验证的用户结果（与 `scenario-5elements.md` 的痛点/机会承接一致）。
5. **保留上溯**：每个故事仍标注来源旅程节点，与 SKILL.md 的 ST-XXX→旅程覆盖矩阵保持一致；无来源机会不编故事。
