# 情景五要素（Scenario Five Elements）

> 来源吸收：`pmskills`（网龙产品设计方法论）的「六、情景分析」模块——情景分析五要素（罗列要素/情景标题/情景描述/痛点和快点/功能启发）+ 情景驱动用户故事写法示例，作为 user-stories 的可选落地能力。
> 定位：用户故事常从功能倒推，缺少"在什么情景下用"的上下文——本技法把情景分析作为故事的上游：先罗列使用情景要素，再推导功能启发，让故事有场景依据而非凭空设计。
> 触发：当用户故事需要场景上下文支撑、或新功能缺乏明确使用场景（尤其 to B 复杂流程、跨角色协作场景）时使用。**按需加载，不设全局闸门**。

## 1. 输入映射

| 外部 skill 输入 | pm-scaffold 对应产物 | 说明 |
|---|---|---|
| 情景（使用情况） | user-journey 的旅程阶段/触点 | 情景 = 故事的上游场景 |
| 情景五要素 | user-stories 的故事候选 | 从要素推导故事 |
| 痛点/快点 | 故事承接的痛点/机会 | 用户情绪证据 |
| 功能启发 | ST-XXX 的功能范围 | 故事的 In/Out 依据 |
| 情景驱动写法 | As a / I want / so that 的故事 | 故事表达范式 |

> **先情景后故事**：情景分析先行，功能启发从情景推导——不跳过情景直接列故事。

## 2. 情景定义与五要素（吸收自网龙方法论）

**情景**：用户使用我们设计的产品或服务的具体使用情况。

> **例子（设计付费软件）**：用户排队去买东西的时候，没带现金，附近又没取款机。这个情景揭示了移动支付的痛点和需求。

**情景分析五要素**：

| # | 要素 | 内容 | 作用 |
|---|---|---|---|
| 1 | **罗列要素** | 任务、时间、地点、起因、经过、条件、道具 | 明确使用场景的基本信息 |
| 2 | **情景标题** | 简洁描述场景 | 给场景命名，便于索引 |
| 3 | **情景描述** | 具体的故事情节 | 还原真实使用过程 |
| 4 | **痛点和快点** | 用户在过程中的挫败感与爽点 | 情绪证据，故事动机来源 |
| 5 | **功能启发** | 针对上述发现推导产品应具备的功能 | 从情景到功能的桥 |

### 2.1 罗列要素详解

| 要素 | 说明 | 示例 |
|---|---|---|
| 任务 | 用户要完成什么 | 排队购物付款 |
| 时间 | 什么时候发生 | 午休时间 |
| 地点 | 在哪里发生 | 便利店收银台 |
| 起因 | 为什么发生 | 没带现金 |
| 经过 | 过程如何 | 收银员无法找零，用户掏手机 |
| 条件 | 有什么前提 | 附近没有取款机 |
| 道具 | 涉及什么工具 | 手机、支付 App |

## 3. 情景五要素完整示例（付费软件 / 移动支付场景）

| 要素 | 内容 |
|---|---|
| **罗列要素** | 任务：购物付款；时间：午休；地点：便利店；起因：没带现金；经过：收银员无法找零，用户掏出手机；条件：附近无取款机；道具：手机 |
| **情景标题** | 没带现金的便利店结账 |
| **情景描述** | 用户午休去便利店买午餐，排到收银台才发现没带现金，附近没有取款机，收银员也找不开零钱，场面尴尬 |
| **痛点和快点** | 痛点：无法付款的窘迫、排队人群的注视；快点：掏出手机扫码即付的轻松感 |
| **功能启发** | 移动扫码支付、余额不足时的替代支付方式（信用付/绑卡兜底）、免密小额支付 |

## 4. 情景驱动用户故事写法示例

从五要素的"功能启发"推导故事，痛点/快点为故事的 so that 动机：

**示例 1（移动支付）**：

- As a 便利店顾客，我想要 扫码即可支付，以便 没带现金也能快速结账、不尴尬。
- As a 便利店顾客，我想要 余额不足时自动切换绑卡支付，以便 结账不中断、不收银员找零为难。

**示例 2（to B 审批场景）**：

| 要素 | 内容 |
|---|---|
| **罗列要素** | 任务：提交费用报销；时间：月末集中报销期；地点：移动端；起因：出差垫资需报销；经过：填单→贴票→领导审批→财务打款；条件：审批人出差中；道具：手机 |
| **情景标题** | 审批人出差途中的紧急报销 |
| **情景描述** | 员工月底提交报销单，审批领导正在外地出差，电脑不在身边，报销流程卡在"待审批"一周 |
| **痛点和快点** | 痛点：垫资周期长、员工催问；快点：手机一键审批、流程即时推进 |
| **功能启发** | 移动端审批、审批超时提醒、自动转派审批人 |

**驱动故事**：

- As a 审批领导，我想要 手机端一键审批报销单，以便 出差在外也不阻塞流程。
- As a 报销员工，我想要 审批超时自动提醒/转派，以便 垫资不被拖太久。

> **对应 pm-scaffold 的位置**：五要素产出的功能启发进入 user-stories 的故事候选，痛点/快点映射为旅程节点，故事回溯该节点。

## 5. 工作流程

1. **罗列要素**：任务/时间/地点/起因/经过/条件/道具——明确场景基本信息。
2. **起情景标题**：简洁命名，便于索引。
3. **写情景描述**：还原具体故事情节（真实、可想象）。
4. **标痛点与快点**：挫败感 + 爽点，记录情绪证据。
5. **推导功能启发**：针对痛点/快点推导产品应具备的功能。
6. **驱动故事**：功能启发落成 As a / I want / so that，so that 引用痛点/快点。
7. **映射旅程**：故事回溯 user-journey 节点，进 Audit/Human Gate。

## 6. 核心硬规则

1. **五要素顺序不可跳**：罗列→标题→描述→痛点/快点→功能启发，逐层推导。
2. **情景描述要具体**：必须有起因、经过、条件——"用户想付钱"不算情景，"排队到收银台才发现没带现金"才算。
3. **功能启发必须来自痛点/快点**：启发是从情景推导的，不从产品功能倒推。
4. **故事 so that 引用痛点/快点**：故事的"以便"用情绪证据（不尴尬/不阻塞），不用功能描述。
5. **痛点与快点都要标**：只写痛点不写快点，会漏掉爽点价值。
6. **先情景后故事**：情景不清晰时标 `待确认` 进 Clarify，不为凑故事编造场景。

## 7. 边界（Do Not）

- 不替代 user-journey——情景是旅程中一个具体的切片，旅程权威仍在其产物。
- 不把情景写成功能列表——情景是"使用情况"，功能启发是推导产物。
- 不为凑五要素编造场景——信息不足标 `待确认`，不虚构起因/经过。
- 不跳过"快点"——爽点是情感价值的来源，漏掉会失去故事的情感层。
- 不用情景分析替代 JTBD——情景回答"什么时候用"，JTBD 回答"为什么雇佣"。
