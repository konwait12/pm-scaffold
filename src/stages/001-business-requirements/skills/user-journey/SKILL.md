# 用户旅程

## 作用与边界

这个 skill 描述角色为了完成业务目标，实际经历了哪些生命周期阶段、行为、触点、分支、阻碍和结果。它产出：

- `user-journey.md`：人和 AI 都能直接阅读的旅程基线候选；
- `user-journey.governance.md`：来源、知识状态、澄清、审计和主文档哈希；
- 默认输出 `user-journey.board.html`：本 skill 默认生成 Figma 风审阅板（触发条件见 §5 Generate「HTML 审阅板触发条件」段），用于人审的单文件可交互旅程审阅板，不是页面原型。

不写用户故事卡片、范围基线、功能清单、页面、字段、接口、业务规则、状态机或验收标准。出现这些内容时，保留到角色行为和业务结果层，并路由到下游 skill。

## 输入边界

优先输入是已确认的 `project-background-goal` 产物，以及 PM 在本次任务提供的原始旅程材料（会议、PPT、PDF、图片、口述、邮件、流程草图或现状说明）。只能使用本次任务中的这些材料和 PM 的明确回复。

材料边界与执行协议：

- **只认本次原始材料**：不得用联网搜索、通用行业知识、模型记忆、其他项目文件、既有 PRD 或产物、计划、案例、交接文档或 skill 自带示例来补充、校正、推断或验证旅程事实；它们也不能作为验证材料。
- **推断与事实分离**：AI 可以归纳材料、还原行为链、识别缺口并提出问题；所有推断必须与来源事实分开标识，不能自行升级为业务事实或决定。材料不足或互相冲突时，保留原意并向 PM 提问。
- **示例不是默认输入**：任何说明性示例、演示旅程或参考案例都不是默认输入，也不是 skill 的内置测试夹具。PM 若要用它们测试，必须在本轮明确指定原文材料、范围和测试目的；否则不得带入当前旅程、问题选项或验证结论。
- **从角色和业务结果出发**：先说清业务本质、旅程起点与终点、主题与框架，再逐步完善场景；不要把第一次输出当成最终答案，也不要从页面或功能清单倒推旅程。
- **单点可用**：本 skill 必须能独立使用，拥有清楚的原始输入和独立输出，不依赖 pipeline、registry、下游产物、其他 skill，也不依赖任何外部工具或指定文档源。
- **验证以原始材料为输入**：用具体原始材料跑 skill，并拿人工期望或独立参照比对结果；验证不能拿最终 PRD、已确认产物或示例替代原始材料。

## 对话流程

### 1. Preflight：确认输入是否足够

从上游和本次材料提取：

- 每个角色要完成的生命周期目标；
- 已明确的阶段、触发事件、行为和触点；
- 已明确的正常、备选、异常、失败、交接和恢复路径；
- 能观察到的情绪线索或痛点证据。

评估成熟度：

- `L0`：没有角色或目标；
- `L1`：只有一个角色或一个阶段线索；
- `L2`：有多个角色但阶段/触点不完整；
- `L3`：角色、阶段、触点和部分分支清楚；
- `L4`：上游已确认且旅程材料充分。

先给 PM 一段材料解读，区分“材料明确说了什么”“AI 对高层行为链的理解”“材料无法证明什么”。先确认旅程要完成的业务事件、起点和终点；若起点或终点不清楚，先给出 A/B/C 三选一澄清，不要先画一条完整的理想路径。本步输出作为 §3.5 粒度决策的输入材料，但粒度本身在 Intake 之后才正式决定。

### 2. Intake：按角色还原实际行为

对每个角色单独记录：目标、触发、可观察动作、触点、决策点、交接、异常退出、恢复动作和情绪证据。材料若只给功能或页面，改写为角色行为；例如“进入列表页”应还原为“查找自己的产品记录”。

保留来源位置和原意。禁止把“系统展示了某页面”自动写成用户痛点，也禁止把“方案列了某功能”自动写成业务目标。

### 3. Think：使用必要透镜（筛选用，不是展示性罗列）

**总原则**：以下六个透镜是"找出会改变产物的发现"的工具，不是必填字段。任何透镜若产出会改变旅程结构、路径覆盖、澄清问题或落产物的事实，就记下来；否则跳过——不把完整思考过程倾倒到主文档。

| 透镜 | 何时启用（产物会变） |
|---|---|
| 第一性原理 | 去掉方案名称后，根问题/业务结果是否仍成立（决定是否要重写目标） |
| 系统思维 | 触点是否跨角色/系统/渠道/外部依赖（决定约束/依赖/不可变项） |
| 同理心/角色视角 | 角色承担的成本/卡点/不确定性，无证据则标 UNKNOWN（决定情绪与痛点表达） |
| 对抗性审视 | 是否存在反例/失败前提使当前旅程不成立（决定是否需新澄清） |
| 逆向验证 | 哪些阶段/交接不可缺；成功前提是否有负责人（决定是否增加前置澄清） |
| 知识边界 | 事实/决定/假设/AI 推断/未知/冲突 分开保存（决定主张来源与知识状态登记） |

**只在以下情况把透镜结论写入产物**：

1. 改变了旅程结构（阶段切分、合并、拆分）
2. 增加了路径类型覆盖（normal/alternative/exception/failure/handoff/recovery）
3. 触发了新的澄清问题（影响 Q 表）
4. 影响了产物待确认与风险条目

否则仅在治理伴随文件中简记，不进主文档。

### 3.5 粒度决策：先选业务层还是产品层，再动笔

用户旅程拆成两段粒度，必须在 Intake 之后、Generate 之前先决定。不能在模糊状态下"先画一条完整的理想路径"。

#### 两段粒度的边界

| 维度 | 业务层（business-level journey） | 产品层（product-level / UX journey） |
|---|---|---|
| 起点 / 终点 | 一个具体业务事件的生命周期（例如：某凭证创建前 → 创建过程中 → 创建完成后） | 完成该业务事件的系统交互步骤（例如：客人收到短信 → 点链接 → 进入过渡页 → 落到小程序） |
| 阶段粒度 | 3–6 段高层阶段，每段对应一个完整业务子事件 | 每个业务阶段可下钻为多步 UI 步骤；同阶段的不同路径（如短信进入 vs 邮件进入）需并列 |
| 行为描述 | 角色在该业务事件中的目标、触发、决策、交接 | 角色在具体界面/通道中的动作、跳转、反馈、异常处理 |
| 触点 | 业务级别的入口与通知（短信 / 邮件 / 服务号推送 / 站内提醒） | 页面 / 弹窗 / 浏览器过渡页 / 小程序启动动画 / 标签 / 红点 |
| 不应出现的产物 | 页面名称、字段、接口、跳转 URL | 用户故事卡（"作为…我希望…"）、功能清单、验收标准 |

#### 决策顺序（强制）

1. AI 先给出粒度判断 + 证据（引自 PM 原始材料）。
2. 在 Clarify 阶段第一个澄清问题必须是粒度（`Q-GR-001`），给出 A/B/C 选项：
   - A. 只做业务层：画清生命周期阶段、角色行为、交接和异常。
   - B. 只做产品层：把已知业务事件直接展开为 UI 步骤与跳转（前提是业务层已在前置产物确认）。
   - C. 都要：业务层为主，产品层作为"业务阶段 X 的展开"附在每个阶段之后。
3. 若 PM 选择 B 但上游业务层尚未确认，必须先停在 `needs_user_input`，让 PM 选择"先补业务层"或"用 AI 推断的业务层先展开产品层（标 AI_INFERENCE）"。
4. 主文档 frontmatter `granularity` 字段必须记录：`business` / `product` / `business+product`。

#### 何时回退到上游

- 业务层旅程的阶段划分不明确（缺起点或终点）→ 回到 §1 Preflight，要求 PM 给出起点事件和终点事件。
- 产品层旅程找不到对应的业务阶段 → 回到业务层补全，再展开。
- AI 写出"点击某按钮""进入某页面"且粒度声明是 `business` → 校验器视为 `uj.granularity_leak` 警告，必须改为业务事件表述。

#### 与下游 skill 的边界

- 业务层 → 可直接喂给 `user-stories`、`feature-list`、`functional-flow`。
- 产品层 → 可喂给 `page-design`、`interaction-rules`、`exception-handling`；不替它们生成页面或规则。
- 同一份主文档若同时含两种粒度，必须在 `角色旅程矩阵` 用子表分开。

### 4. Clarify：AI 判断后提问

每轮最多 5 个高影响问题；优先处理会改变角色、阶段、路径、触点、情绪判断或下游使用的问题。每个阻断问题都要给：AI 初步判断、材料证据、三个互斥选项（A/B/C，可加“其他”自由回答）、影响、负责人和是否阻断。

澄清按渐进顺序推进：先问业务目标、起点/终点和角色责任，再问主路径、分支、异常和交接，最后才讨论可能的实现方案。AI 可以列出通知或触达等可行选项供 PM 选择，但不能擅自把某个选项写成已决定的业务需求。

遇到以下情况必须停在 `needs_user_input`：角色责任冲突、主路径与备选路径无法判定、痛点/情绪只有 AI 猜测、交接归属不明、或旅程范围会随答案改变。不要通过行业常识“补齐”答案。

#### 待确认的两个来源（缺一不可）

**1. 材料显式未决项（优先，也最容易漏）**

全量扫描原材料中**作者自己已经提出、但尚未回答**的问题与待定判断，逐条进入待确认。识别特征包括：以「？」结尾的问句（尤其「是否……？」「……沿用吗？」这类悬空判断）、「待定 / TBD / 待确认 / 待讨论 / open / TODO」标记、以及用 `--` 或 `---` 引出的未结论判断。

扫描范围必须覆盖**全部材料载体**，不能只读结构化章节：

- 正文段落与列表项（含嵌套子项、表格单元格内的批注）；
- **图片的标题与说明文字（alt / 图注）**——旅程图、流程图的说明常含时间轴（如 m-1 / D-7 / D-1 / D）与分支信息，必须读取；
- 备注、callout、批注、脚注。

**典型失败模式（必须避免）**：材料中已存在结构化的「议题表 / 问题清单」时，只搬运那张表，而漏掉散落在正文、图片说明和备注里的问句。结构化清单只是来源之一，不是全部。

**2. AI 推导缺口**：材料未涵盖、但本 skill 的旅程产出要求必须回答的内容。

**视角约束**：本 skill 的待确认与风险必须聚焦**旅程视角**——角色责任、阶段完整性、路径/分支/异常/恢复、触点与情绪、时间节点、跨角色交接。上游（如背景目标）已列出的 TBD，只有**确实影响旅程结构**时才引用并注明来源，不允许整体照搬成同一份清单。两份产物对同一事项应各有侧重；冲突时以材料证据为准。

### 5. Generate：生成两份文档，HTML 按需

**提取护栏（强制）**：Generate 前必须按 `references/journey-extraction-guardrails.md` 逐条执行五条护栏——①多品类并列页强制分列成对照表、节点归并保留品类适用范围；②通知/提醒/提示独立形态枚举、流程图独立提示节点（如 Receive a reminder）单独登记并追问，不并入已知形态；③资产空态与身份×登录×资产状态分支骨架必检（TBC 也画骨架）；④图片/版式型线索（模板缩略图、并列方案图、图注）逐图文字化；⑤文案占位符登记动态变量与口径。未过护栏的自检清单不得进入 Audit。

主文档 `user-journey.md` 使用模板标题，至少包括：一句话旅程叙事、业务生命周期分解、角色旅程矩阵、路径与情绪、触点/痛点/机会、覆盖与边界、待确认与风险、参考资料。

每个角色至少有一条独立叙事；每个已确认阶段说明触发、行为、触点、结果和路径类型。痛点必须来自材料或明确标为 AI 推断/未知；机会写成可观察的改进结果，不写成按钮、页面或接口。

**时间维度**：若材料含相对时间标记（`D-7` / `D-1` / `D` / `m-1` /「活动前 N 天」等，常见于旅程图说明或备注），必须把时间钩子写进生命周期分解，不能只写阶段而丢掉时间。与时间绑定的通知、行程单等节点，即使其去留尚未决定，也要作为候选节点列出并挂到待确认，而不是整体省略。

**场景完整性**：材料给出的界面状态矩阵、弹窗清单、异常列表中的每一项，都要么落到某个旅程节点，要么在「材料明确但尚未纳入旅程」中显式说明不纳入的理由。不允许静默丢弃。

**表格输出校验**：生成 Markdown 表格时，同一张表的每一行列数必须一致；单元格内若含括号、书名号或引号，必须成对保留在同一单元格内，不得被分隔符截断；表头每一列都要有语义列名，禁止出现空列名或仅含 `<br />` 的列。

**产物可视化最小集（强制）**——禁止只交表格不交图，主文档至少含 2 张 mermaid：

1. **旅程总览图**（必画）：`flowchart LR`，把「业务生命周期分解」表转成图形——主路径实线、异常/失败虚线、决策分支用菱形节点；放「业务生命周期分解」节尾；
2. **情绪曲线图**（必画）：`journey` 图（mermaid 原生 journey 类型，满意度 1-10），按阶段 × 角色评分；材料无情绪证据时按路径类型推导并标 AI_INFERENCE（normal/alternative=7、handoff/exception/recovery=5、failure=3）；放「情绪与可观察信号」节尾；
3. **状态机图**（条件必画）：材料定义资产/账户/订单状态流转时，用 `stateDiagram-v2` 画状态机；放「旅程覆盖与边界」或独立小节；
4. 其余信息（品类对照 / 分支骨架 / 入口生命周期）用表格承载——表格适合精确对照，图形适合看流向，两者互补不互替。

**飞书画板与外部图形引用**：原始材料若含飞书画板（whiteboard）或外部图形链接，主文档「参考资料」登记链接与一句话摘要即可，**不复制画板内容**（材料隔离：画板是材料证据，不是产物）；产物自身的图形只由本 skill 的 mermaid 生成，保证可版本管理与 diff。

状态只能是 `draft`、`needs_user_input`、`conditional_review` 或 `ready_for_human_review`，AI 永远不能写 `confirmed`。

**HTML 审阅板触发条件（UJ 默认 / BG 不出）**：本 skill 默认生成 `user-journey.board.html`，仅当产物满足以下任一条件时跳过——① 单角色且单阶段且单路径（极简旅程无可视化收益）；② PM 显式说明本次不需要可视化产物；③ 产物处于 `draft` 之前的状态（预检阶段）。否则按下列规则生成：

- **UJ 默认**：角色数 ≥ 2 **或** 阶段数 ≥ 3 **或** 路径类型 ≥ 2 → 必出 board.html；
- **BG 默认不生成**：本 skill 不为 BG 产物生成 board.html；BG 模板的「可选审阅板」字段描述为「按需」，由 PM 在 BG Generate 时显式触发，且仅当产物含「角色 × 阶段 × 路径」任一维度 ≥ 2 项时才出。

`user-journey.board.html` 是单文件、零外部网络依赖、按角色/阶段/路径筛选并可展开证据和未知项的 Figma 风中性模板。它只呈现旅程材料，不新增页面、文案、功能或状态；具体契约见 `references/html-journey-board.md`。模板在 `assets/user-journey-board.html`，使用时**只替换 `DATA` 对象**（`meta` / `stages` / `roles` / `nodes` / `edges` + 5 段可选附录），不重写样式与交互层；未填附录会自动隐藏。

### 6. Audit：重新阅读并反证

检查：

- 每个已确认角色和已确认阶段都有覆盖；
- 主路径、备选路径、异常/失败、交接/恢复的缺口显式列出；
- 情绪来自可观察证据，缺证据不编造“满意/焦虑/惊喜”；
- 每个痛点都能追到来源或 AI 推断，每个机会都能追到痛点；
- 行为层没有泄漏成页面、功能或技术实现；
- 目标、前提、依赖和未知能被下游读取；
- HTML 与 Markdown 的角色、阶段、路径和状态一致。
- 本次验证是否只使用了 PM 指定的原始材料；没有把示例、旧产物或参考文档泄漏为答案。
- **待确认是否已扫全**：材料里作者自己提出的问句、待定标记、`--` 悬空判断是否都被提取？（见 §4「待确认的两个来源」）
- **时间维度是否丢失**：材料中的相对时间标记（`D-7` / `D-1` / `D` / `m-1` 等）是否已体现为生命周期中的时间钩子，而非只写阶段？
- **场景是否静默丢弃**：材料的界面状态矩阵、弹窗清单、异常列表中的每一项，是否都已落到旅程节点，或在「材料明确但尚未纳入旅程」中说明了不纳入理由？
- **表格是否合规**：每张表的各行��数一致、单元格内括号/引号成对且未被分隔符截断、表头无空列名或仅含 `<br />` 的列。
- **提取护栏是否已过**：多品类并列是否分列、提醒形态是否枚举、空态与身份分支是否画骨架、图片线索是否文字化、占位符是否登记（journey-extraction-guardrails.md 自检清单，未过项修复后再审计）；
- **活动/类型数量是否自洽**：文中数量表述（如「N 种活动类型」）与实际列举项数一致，且与上游背景目标产物不冲突。

运行 `scripts/validate_artifact.py <user-journey.md> --json`。修复阻断错误，并把非阻断未知写入治理文件。

### 7. Human Gate 与回流

向 PM 展示旅程摘要、角色与阶段覆盖、路径/情绪缺口、证据、待确认问题、HTML 审阅板（如有）和 Audit 结果。只有授权业务/产品负责人可以批准；机器校验不能确认。

已确认内容发生改变时，记录变更和下游影响，重新生成 Markdown/HTML、重跑 Audit，再回到人工评审。不要在下游 skill 中静默修补上游旅程。

## 完成标准

`user-journey.md` 与治理伴随文件同目录、同 artifact_id 和版本；主文档可独立阅读且不包含机器治理表；治理文件记录所有重要来源、知识状态、澄清、Audit 和哈希；所有角色旅程、阶段、路径和未知均可追溯；可选 HTML 审阅板无外部依赖且只呈现已确认或明确标记的旅程信息；状态等待授权人类确认。

## 独立运行

### 独立可用的边界声明

- **零外部依赖**：本 skill 不依赖 pipeline / orchestrator / registry / 其它 skill 的产物或历史 PRD / PM 在场；可被任何上层（独立对话、子能力调用、项目级集成）触发。

  - skill 不感知 001 项目、PM 角色、`pipeline.py review` 等项目层概念——这些由项目层 adapter 提供。

### 与项目级耦合的零依赖要求
