# 用其他 AI 验证与迭代 user-journey skill 的问法

> 本文件不是 SKILL 的一部分，是给 PM/AI 协作者使用的"反向检验 prompt 库"。
> 思路来自 2026-08-27 项目会议：把做好的 skill 拿到不同的外部 AI（Kimi / 千问 / 通义 / Claude / GPT）反复追问，
> 用多份独立回答互相校验，判断 skill 是否"真的有用"。

## 一、为什么要用外部 AI 反向检验

- 本地 skill 是工具,工具好坏要拿案例跑才知道。
- 同一个案例,多个 AI 独立回答,对比一致性,可以判断 skill 输出是否"AI 时代鲁棒"。
- leader 原话："随便做,它能帮我做的百分之五六十。但是我们现在做的是让每个 skill 它真正的能管用。"

## 二、检验的 5 个层级

| 层级 | 问题 | 期望 |
|---|---|---|
| L1 概念理解 | 这个 skill 在 PM 流程里是干什么的? | 任何 AI 都能讲清楚 |
| L2 输入输出 | 输入什么、输出什么?边界在哪? | 多个 AI 描述基本一致 |
| L3 案例跑通 | 给定真实材料,跑一遍能否产出可用产物? | 产物结构一致、字段完整 |
| L4 边界守住 | 给极端输入,是否会越界(泄漏到页面/功能/字段)? | 守住"不替下游定义" |
| L5 增量价值 | 产物比"不用 skill 直接问 AI"更好在哪? | 有可观察差异(粒度清晰、可追溯、有治理) |

## 三、可以复制的 prompt 模板

### 3.1 让 AI 当"产品经理导师"理解 skill 本质

```
我刚做了一个 PM 工具里的 "user-journey"(用户旅程)子工具。
我贴一下它的 SKILL.md,请你像一个资深产品经理一样回答:
1. 这个 skill 解决的是 PM 哪一类工作?
2. 输入和输出分别是什么?
3. 它和"用户故事""功能流程图""UX 流程图"的边界在哪?
4. 你觉得最容易踩坑的地方是什么?
```

### 3.2 让 AI 当"案例测试员"跑具体业务

```
我有一个原始业务材料(贴在下面)。请按 user-journey skill 的步骤帮我产出用户旅程:
材料:[这里贴原始材料]
请按以下顺序:
(a) 判断应该停在业务层还是产品层(粒度决策);
(b) 给出 3-6 个业务阶段;
(c) 对每个阶段填写 6 个维度(触发、行为、想法、触点、痛点、机会);
(d) 显式标出至少 1 个异常路径;
(e) 区分哪些是材料明确说的(FACT),哪些是你的推断(AI_INFERENCE)。
```

### 3.3 让 AI 当"边界守护者"挑刺

```
请检查下面这份 user-journey 产物:
[贴产物]
逐项判断:
1. 哪些地方泄漏到了"页面/按钮/字段/接口"?
2. 哪些痛点缺乏证据(没有可观察行为支撑)?
3. 哪些阶段缺少起点/终点/交接?
4. 是否能区分主路径 / 备选路径 / 异常路径?
5. 如果把粒度从 business 改成 product,产物是否要重写?哪些行能保留?
```

### 3.4 让 AI 当"产品新人"问基础问题

```
我是一个新入职的产品经理,刚拿到一份 user-journey 文档。
请你帮我理解:
1. 这份文档在讲谁的旅程?起点和终点是什么?
2. 一共分了几段?为什么这么分?
3. 每个阶段的关键行为是什么?我做开发时从哪里读懂角色要做什么?
4. 哪些是"已经决定"的、哪些是"待确认"的?
5. 我能拿这份文档去做下游的用户故事 / 功能流程 / 原型吗?还缺什么?
```

### 3.5 让 AI 当"skill 优化顾问"

```
我做了一个 user-journey skill,目标是:从原始业务材料出发,产出可追溯的角色×阶段旅程,
不要替下游定义页面/功能/字段。
请你:
1. 假设你是第一个使用者,把它读一遍;
2. 列出 5 条"用起来不顺"的地方;
3. 列出 5 条"想用它但不知道该传什么"的疑问;
4. 如果让你重写这一节,你会怎么改?
```

## 四、把多份回答横向比对

拿 2-3 个不同 AI(本地 Claude / Kimi / 千问)各跑一遍同一份材料,做对比表:

| 字段 | AI-A | AI-B | AI-C | 一致度 |
|---|---|---|---|---|
| 角色数 | | | | |
| 阶段数 | | | | |
| 粒度判断(business / product) | | | | |
| 异常路径数 | | | | |
| 痛点是否有证据 | | | | |
| 是否泄漏到功能/页面 | | | | |

如果三家 AI 给出的粒度、角色、阶段差距巨大,说明 skill 的输入/边界不够锋利;
如果产物都能区分业务层 vs 产品层、有显式异常路径、痛点带证据 → skill 算"管用"。

## 五、用 leader 思路反复追问的具体套路

会议里 leader 用过的几类追问,可直接复用:

| 套路 | 模板 |
|---|---|
| 反向追问 | "如果我把这一步去掉,你的产物还成立吗?" |
| 对抗反例 | "能不能想一个反例,让这个旅程不成立?" |
| 第一性原理 | "业务真正的目标是什么?方案只是手段。" |
| 知识边界 | "你说的这句话,是从材料里来的,还是你自己推断的?" |
| 迁移测试 | "下次换个项目,这个 skill 还能跑出一样质量的东西吗?" |
| 视角切换 | "假如你是开发 / 老板 / 客户 / 新人,你分别最想看到什么?" |
| 维度发散 | "这个 skill 一共要考虑多少种类型?每种分别怎么写?" |

## 六、迭代闭环

每次跑完外部 AI 验证,把发现写进 skill 的 issue-record:

```
ISS-XXX | user-journey skill 优化项
  触发:用 Kimi 跑了 DP 案例,产物粒度错位到产品层
  发现:Clarify 阶段没有强制问粒度
  修复:SKILL.md §3.5 加粒度决策段
  验证:再用两个 AI 跑同一案例,粒度一致
```

每次只改一个点,跑两个外部 AI 验证一致性,通过才提交。
