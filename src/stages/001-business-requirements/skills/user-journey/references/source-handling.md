# 来源处理（Source Handling）

## 来源登记（Source Register）

为每个来源分配一个稳定 ID 并记录：

```text
source_id
title_or_description
format
author_or_speaker
provided_by
created_at
retrieved_at
authority_scope
location_or_link
notes
```

使用 `SRC-001`、`SRC-002` 等。对于会议，区分会议纪要原文与 AI 生成的摘要。

## 材料元数据核对（Material Metadata Reconciliation）

扫描阶段开工前**先核对材料元数据**，登记到治理伴随文件的「材料元数据」段：

```text
## 材料元数据

- 总页数：<数值>
- 页码口径：<PDF 页序 / PPT 页脚自编号 / 章节序号 / 混合>——必须明确选择一种口径，下游所有页码引用统一按该口径
- 页码偏移：<如 PDF 页序与材料页脚自编号存在 N 页偏移，登记 N>
- 载体类型分布：<纯文本 X 页 / 图片 Y 页 / 混合 Z 页>
- 来源格式：<PDF / PPT / DOCX / SHEETS / TXT / ...>
- 文本化方式：<原生文本提取 / OCR / 手工转写 / 其他>
- 文字化覆盖：<如 36/40 张图片有文字描述，登记覆盖率>
```

> **必须先做元数据核对再开逐页台账**：台账首行即口径声明，下游所有页码引用必须统一按该口径——避免 DP 案例那种「PDF P26 页脚为 30，4-5 页偏移导致产物引用错位」的元数据 bug 重复发生。

## 逐页台账（Page-by-page Ledger）

含图片/混合载体的材料，**逐页登记**到治理伴随文件的「逐页台账」段：

```text
## 逐页台账

| 页码（按上方口径） | 载体（纯文本 / 图片 / 混合） | 解析状态（已文字化 / 不可解析） | 一句话摘要 | 证据状态 | 澄清问题 ID |
|---|---|---|---|---|---|
| 1 | 纯文本 | 已文字化 | <摘要> | FACT | — |
| 2 | 图片 | 已文字化（OCR / 视觉） | <摘要> | FACT / AI_INFERENCE | — |
| 3 | 混合 | 部分已文字化 | <摘要> | FACT | Q-UJ-001 |
| 4 | 图片 | 不可解析（已尝试 OCR / 视觉，仍无可读内容） | <附已尝试证明> | UNKNOWN | Q-UJ-002 |
```

### 硬约束

1. **逐页登记**——禁止把多页打包成一条「图片未解析」备注了事
2. **不可解析**必须附已尝试的证明（如「OCR 输出乱码；视觉解析后内容主体仍不可读」）
3. **每张不可解析的页必须生成一条澄清问题**——登记在台账的「澄清问题 ID」列
4. **图片页内容主体必须尝试视觉解析**——内容进入产物或升级为澄清问题，两者都必须在治理文件留记录（与护栏 ④ 联动）

### 与护栏 ④ 衔接

- 护栏 ④「图片/版式型线索文字化」+ 本节「逐页台账」共同保证：所有图片页要么文字化进产物，要么升级为单条澄清问题
- `audit-checklist.md` 新增对账项：「不可解析页数 = 0，或每页都有对应澄清问题 ID」（详见 audit-checklist.md）



## 项目级会议基线（可选，通用约定）

当 PM 或项目级集成方**显式指定**了一个会议基线（飞书 / 企微 / Notion / 录音转写 / 现场纪要等任意形态），在治理伴随文件 `*.governance.md` 中按以下格式登记一个 `## 项目级会议基线（可选）` H2 段（命名也可改为对应项目的习惯名称，但需在治理伴随文件 frontmatter 或正文中显式标注"基线来源"）；不向主文档注入业务事实。

> 通用模板：

```
## 项目级会议基线（可选）

- 原文来源：<会议名称 / 飞书 / Notion 等链接>
- 读取命令：<CLI 命令，如 lark-cli / notion-cli 等>
- 检索日期：YYYY-MM-DD
- 使用位置：<本产物在何处使用基线>
- 四类拆分（分别记录，不混写）：
  1. 会议明确决定：...
  2. 会议业务示例：...
  3. 会议讨论或建议：...
  4. AI 解读：...
```

> **不强制**：未指定会议基线的项目 / 独立对话使用场景不需要登记此段，skill 仍可独立产出。
> **校验契约**：若治理伴随文件存在此段，校验器会检查段内是否含原文链接、读取命令、四类拆分与使用位置（不校验链接是否有效、命令是否可执行——项目级真实性由集成方负责）。

001 项目当前指定的会议基线为 [2026-08-27 飞书会议原文](https://ccegroup.feishu.cn/docx/MDVkds3yJocDvGxSYCGceULBn8f?from=from_copylink)。通过飞书 CLI 读取时，必须保留原文位置；会议原文、会议纪要/摘要和 AI 解读分开登记，不能把摘要当作原始证据。

> 通用化说明（不绑定 001）：上面这条 001 项目基线是项目级示例。任意 skill 调用方（项目级集成 / 独立对话使用）若明确指定了会议基线（飞书、企微、Notion、会议纪要等），按下面的"## 项目级会议基线（可选）"段格式在治理伴随文件中登记；若未指定，本段可不创建，skill 仍可独立运行。

## 提取规则（Extraction Rules）

1. 在规范化之前先提取来源陈述。
2. 对实质性主张保留说话人或作者与位置。
3. 区分显式陈述与隐含含义。
4. 当被排除的内容看似承载需求但属于范围外或重复时，记录一条简短原因。
5. 绝不把"没有提及"当作需求不存在的证据。

## 权威性（Authority）与冲突

不要定义通用的来源类型优先级。用以下方式评估权威性：

1. 针对本项目是否有显式的人工确认；
2. 对特定业务事实或目标的决策权；
3. 来源的直接程度；
4. 时效性，以及后续陈述是否显式取代先前陈述；
5. 独立来源的相互佐证。

当陈述冲突时：

- 保留双方的陈述与来源 ID；
- 说明每种解读的影响；
- 识别可能的事实负责人或决策负责人；
- 当冲突改变实质性结论时，标记为 `conflict` 并停下；
- 绝不要悄悄选择更"方便"的陈述。

## 调研边界（Research Boundary）

对 001 项目，指定的飞书会议原文是必须读取的基线；除此之外，不要用联网搜索或外部案例填补旅程事实，除非 PM 在本轮明确授权并指定用途。任何获授权的外部资料都只能作为方法或待核实线索，不能确认内部角色、范围、目标或路径。调研不能确认内部业务意图、项目范围、业务归属或风险的可接受性，把这些提交给负责任的人类。

## 混合媒体（Mixed Media）

- 对于幻灯片与文档，保留幻灯片/页面/章节位置。
- 对于图片，转录可见的承载需求文本并注明不确定性。
- 对于会议记录，区分说话人陈述、决策、建议与未决讨论。
- 对于邮件线程，保留发件人、收件人上下文、日期，以及后续邮件是否取代先前邮件。

## 提取护栏的下游落点（与护栏 4 衔接）

来源扫描阶段识别到的图片/版式型线索（流程图节点、模板缩略图、并列方案图、图注/alt 等），落产物时按 `journey-extraction-guardrails.md` 护栏 4（版式线索文字化）执行：

- 逐图/逐列列举为枚举项（如三种模板图示），禁止以"XX 通知""若干模板"等一笔带过；
- 缩略图下的图注文字（含 TBC / pending / assumption / 仅模型示意等标注）随枚举结果同步进入产物待确认清单。

本文件管"扫描哪些载体 + 记录位置"，护栏 4 管"扫到后如何文字化落产物"——两层职责互补，本文件不重复枚举规则。
