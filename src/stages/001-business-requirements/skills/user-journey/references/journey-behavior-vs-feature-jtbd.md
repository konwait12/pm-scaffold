# 用户行为 ≠ 功能：旅程叙事与 JTBD 一句式（Journey Behavior vs Feature）

> 来源吸收：`user-story-mapping` skill（Jeff Patton 故事地图）的"行为轴线"概念——活动 backbone 描述的是**用户行为**而非产品功能、叙述（Narrative）是一句**结果导向**的 JTBD、纵向按优先级切 release 线；与 `brainstorming-v2` 的"先问题后方案、尽早成稿"配合，作为 user-journey 的旅程边界判定技法。
> 定位：user-journey 最常见的失真，是把"用户做什么"画成了"产品提供什么/某个页面"。本技法给出**行为判定测试**，让旅程每一格停在客观用户行为层，并为后续 `user-stories` / `feature-list` 留出干净的输入。
> 触发：Intake 判断某阶段该填"用户动作"还是"产品功能"拿不准时；Generate 前给旅程画"叙事主线"时；Audit 检查旅程是否有"功能泄漏"时。**按需加载，不设全局闸门**。

## 1. 行为判定测试（Activity Vs Feature Test）

旅程活动/步骤是**用户做什么**，不是产品提供什么。逐条过三问，答不上来先改写：

| 判定问法 | 通过标准 | 反例 → 正例 |
|---|---|---|
| 这是"用户做"，还是"产品提供"？ | 主语是角色行为动词 | 把“查看某界面”改写为“完成某业务观察” |
| 我能"看着某人执行"这一步吗？ | 可观察，不含系统内部动作 | 把“系统完成”改写为“角色完成动作并观察到结果” |
| 它讲的是"怎么达成目标"，不是"有什么页面"？ | 行为指向结果而非界面 | 把“进入某页面”改写成“完成某业务判断/结果” |

> 规则：主语一律是角色；动词是可观察行为；宾语是业务结果或实体，**不是页面/按钮/字段**。出现"看/进/打开 X 页""点按钮"即可判定为功能泄漏。

## 2. 一句话结果导向叙事（JTBD Narrative 一句式）

旅程主线 = 该角色在追求的一段生命周期的**目标结果**，不是"使用本产品"。按 user-story-mapping 的一句式测试：

- **一句写完**：超过一句说明主线拆过头，退回到"骨架活动"而非具体步骤。
- **结果导向**：写角色要完成的业务结果，而非“使用某工具”。
- **成功可判**：句子里能抽出可观察的完成标志（"收款到账""评审通过"），供下游旅程验收使用。

写不出结果导向的一句叙事，说明 Preflight 阶段"该角色要完成什么目标"还没立住——回到背景与目标，别硬画。

## 3. 骨架活动 3-5 条（顺序、互斥、用户动作）

- 主线用 **3-5 条高一层活动**（做骨架），再逐条拆步骤——超过 5 条多半是混入了次级步骤，需要合并；
- 活动按**叙事时序**排列，步骤才往下拆；
- 每条活动须过 §1 行为测试；活动是"用户行为轴"，功能清单留到 `feature-list` 从这些步骤里提炼（行为先于功能）。

## 4. 层层下钻，逐层留接口

```
叙事(一句结果导向 JTBD) → 骨架活动(3-5 行为) → 步骤(可观察动作) → 每个动作=下游故事/功能的输入
```

旅程只画**前三层**；`user-stories` 承接"每步背后的 so that 动机"（JTBD 三层属 `user-stories/references/job-story-and-moat.md`，本文件不重复展开），`feature-list` 承接"系统要为此做什么"。旅程里出现任何"系统怎么做"即是越界，路由给下游。

## 5. 硬规则

1. **旅程主语是用户**：任何格子的主语不是角色 → 重写。
2. **行为可观察**：讲不出"看着谁做什么"，先标缺失再进 Clarify，不空写。
3. **叙事一句且结果导向**：写不出就回 Preflight，不硬画。
4. **3-5 条骨架活动**：超过即合并，防止把功能当活动。
5. **不把功能下探进旅程**：页面/按钮/系统逻辑泄漏 → 路由 `feature-list`/`page-design`。

## 6. 质量自检

- [ ] 每一阶段/触点 / 行为 都以角色为主语、可观察、指向业务结果
- [ ] 没有“看某页面/点某按钮/进入某页面”类功能泄漏
- [ ] 角色旅程主线是一句结果导向叙述，且能抽出完成标志
- [ ] 骨架活动数量在 3-5 条，步骤只画用户动作
- [ ] 系统性/系统怎么做没有进入旅程（已路由下游）
