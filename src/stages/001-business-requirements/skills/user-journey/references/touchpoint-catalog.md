# 触点目录（Touchpoint Catalog）

> 本目录是 UJ 旅程生成时枚举触点的参考清单。每次 Generate 不强制加载；当材料含多触点描述或多入口对比需求时必读。AI 不得自创本目录外的触点——若有新材料中的触点不在本目录，需先在 governance 的「AI 推断」段登记，再建议加入本目录。

## 触点 ID 命名规范

`<触点分类>_<具体名称>`，全大写下划线分隔。例如 `SMS_3RD_PARTY`、`EMAIL_TRANS`、`PUSH_APP` 等。

## 选择触点的判断要点

- **触达即时性要求**：秒级（操作反馈）→ INAPP；分钟级（订单进度）→ PUSH_OS 或 INAPP_REMINDER_CENTER；小时级（活动通知）→ EMAIL_TRANS / WE_COM_ROBOT
- **用户是否在应用内**：在 → INAPP 系列；不在且为内部员工 → WE_COM；不在且为外部用户 → SMS / EMAIL / PUSH_OS
- **是否需要富媒体**：是 → EMAIL_TRANS / PUSH_OS / INAPP_BANNER；否 → SMS / INAPP_TOAST
- **是否需强提醒**：是 → INAPP_MODAL；否 → INAPP_RED_DOT / INAPP_BANNER
- **法规与授权**：SMS 需报备模板；EMAIL_MARKETING 需退订；CALL_VOICE_AI 需用户授权；MINI_PROGRAM_MSG 需用户主动订阅
- **成本**：SMS 按条计费、PUSH_OS 边际成本低、AI 语音按分钟计费

## 模板外的触点处理

若材料中出现本目录未列的触点（如传真、传真邮件、Slack 通知等）：

1. **AI 不得直接采用**，必须在 governance 的「AI 推断」段登记该触点及其来源材料；
2. 提示 PM：「检测到新触点 `<X>`，未在标准目录内。是否纳入本次旅程？纳入后建议加入本目录作为标准触点。」
3. 若 PM 选择纳入，按本目录的 ID 命名规范补一个新条目，并同步更新 touchpoint-coverage-matrix.md。

## 维护

- 本目录随 skill 演进；每次新增触点需要：① ID 与名称、② 载体分类、③ 推送方式与时效、④ 富媒体与链接支持、⑤ 法规/授权约束、⑥ 典型场景举例。
- 维护人：skill owner；评审：双周一次随 PM 用例回归。
