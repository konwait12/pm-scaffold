# 旅程错误恢复与指标技法（Journey Error Recovery & Metrics）

> 来源吸收：work buddy `user-journeys` skill 的 Journey Template（每步 Success Criteria / Potential Friction→缓解）、Error Scenarios（E1/E2 的 Trigger / User Sees / Recovery Path / Test）、Metrics to Track 与 Journey Metrics Dashboard（完成时长/各步流失/错误率/恢复率）、Recovery Journey 模式（识别回归用户→恢复状态→承认发生→给出前进路径→完成原目标）与 Anti-Patterns（仅 happy path / 忽略时间 / 不测错误恢复），作为 user-journey 的可选落地能力。
> 定位：`journey-matrix-and-mot.md` 把旅程"切矩阵、标 MOT、转机会"；本文档把每个触点与整条旅程的**可验证性**补齐——每步定义成功标准勾选、每个摩擦点给缓解、每条异常路径给 E1/E2 错误恢复四段式、整条旅程给可埋点的量化指标。两者互补，合起来才是一条"既能讲清故事、又能被验收"的旅程。
> 触发：旅程需被验收/可测试（下游 AC 依赖）、或旅程含高风险异常路径（支付/审批/数据迁移）、或需定义埋点指标时加载。**按需加载，不设全局闸门**。

## 1. 输入映射（pm-scaffold 语境）

| 外部 skill 输入 | pm-scaffold 对应产物 | 说明 |

## 2. 每步 Success Criteria 勾选（per-step Success Criteria）

对矩阵中**每个触点**补"成功标准"清单（至少 2 条可勾选项），标准必须可观察、可验证，禁止形容词：

```
### Step 2: [触点/阶段]
**用户动作：** 用户实际做什么
**系统响应：** 用户应看到/经历什么
**成功标准（Success Criteria）：**
- [ ] 页面加载 < 2 秒（性能基线）
- [ ] 主 CTA 首屏可见（布局基线）
- [ ] 用户知道下一步做什么（可测：下一步点击率 / 无求助行为）
```

- **每条成功标准必须可度量**（时长/百分比/点击率/可观察状态），"用户感觉良好"不算成功标准。
- **成功标准是下游 AC 的原料**：`acceptance-criteria` 产 AC 时直接引用这些勾选项作为 G/W/T 判据来源，避免重复调研。
- **非行为性标准要标注测法**：如"用户理解下一步"→ 测法 = "无 ≥10s 停顿 / 无帮助入口点击 / 问卷确认"，不写测法就不算标准。

## 3. Potential Friction → 缓解（摩擦点必须给缓解）

对每个触点列出"潜在摩擦 + 对应缓解动作"。摩擦用**可观察行为**描述（不是"体验不好"），缓解用**可量化改进结果**（呼应 journey-matrix-and-mot §5 痛点→机会）。

| 触点 | 潜在摩擦（可观察） | 缓解动作（可量化） |
|---|---|---|
| 注册 | 表单字段 > 6 个，用户放弃率 40% | 减到 邮箱+密码 2 字段 → 放弃率目标 < 20% |
| 审批 | 合规审查平均 12 天，销售等不起 | 预出合规材料包 → 审批时长目标 ≤ 5 天 |
| 数据迁移 | 迁移失败需全量重来，回滚 3 次 | 迁移前校验 + 断点续传 → 失败回退率目标 -80% |

规则：
1. **每个摩擦点至少 1 个缓解动作**，且缓解动作标注目标值；无法量化的标 `待确认` 交人工。
2. **缓解动作 ≠ 加功能**：写"减少 50% 表单填写时长"这类结果，不写"加个一键填充按钮"这类方案（功能归 feature-list）。

## 4. E1/E2 错误恢复四段式（Error Scenarios）

对旅程中每个**高风险异常路径**（支付/审批/登录/数据迁移/权限不足等）登记 E1/E2 表。四段式固定为：

| 字段 | 定义 | 示例 |
|---|---|---|
| **E1: [错误名]** | | |
| **Trigger（触发）** | 什么条件导致此错误 | 银行卡被发卡行拒绝 |
| **User Sees（用户所见）** | 用户看到的错误信息/状态 | "支付失败，请更换银行卡" |
| **Recovery Path（恢复路径）** | 用户如何回到主流程 | 停留在支付步、其余字段已预填、可换支付方式 |
| **Test（如何验证恢复）** | 自动化/手动验证恢复可用 | 用拒绝卡号走通→换成功卡号→到达确认页 |

要点（吸收 user-journeys Error Scenarios + Recovery Journey 模式）：
- **恢复路径五步**：识别回归用户 → 恢复之前状态（会话/草稿保留）→ 承认发生了什么（明确错误文案）→ 给出清晰前进路径 → 让用户完成原目标。五步缺任一步视为恢复不完整。
- **"用户不被踢出旅程"是底线**：错误发生时不丢上下文（购物车保留、草稿保留、回到同一步骤），这是恢复路径是否合格的第一判据。
- **每个 E1/E2 必须给 Test**：恢复路径写不出来或无法验证 = 该异常未被真正处理，标记 `待确认`。
- **E 编号进入产物**：异常路径在 user-journey.md 中以 E1/E2 小节登记，与触点矩阵的异常退出路径一一对应。

## 5. 旅程级指标（Journey Metrics）

对每条旅程定义 4 类指标（吸收 user-journeys Metrics to Track），每类给公式/口径、目标值与埋点时机：

| 指标 | 口径（公式/定义） | 目标值示例 | 埋点时机 |
|---|---|---|---|
| **完成时长 Time to Complete** | 从入口到"完成原目标"的总时长 | 注册→首个价值 < 5 分钟 | 每步进入/离开时间戳 |
| **各步流失 Drop-off Rate** | 某步离开人数 ÷ 到达该步人数 | 单步流失 < 30% | 每步离开事件 |
| **错误率 Error Rate** | 某步出错次数 ÷ 该步操作次数 | 支付错误率 < 5% | 错误事件（带错误类型） |
| **恢复率 Recovery Rate** | 出错后成功完成该步的人数 ÷ 出错人数 | 支付恢复率 ≥ 80% | 错误事件 + 后续成功事件关联 |

规则：
1. **每类指标必须可埋点**：写清事件名与口径；埋不出来的指标 = 空指标，删掉或标 `待确认`。
2. **指标挂到旅程级而非功能级**：完成时长/流失/错误率/恢复率都是"整条旅程的健康度"，不按单个按钮拆（单步埋点只为算旅程级指标服务）。
3. **恢复率是错误率的对照指标**：只看错误率不看恢复率会误判——高错误率 + 高恢复率 = 可接受的摩擦点；低错误率 + 低恢复率 = 隐性炸弹（一旦出错用户就回不来）。

## 6. 完整示例：to B 采购审批旅程（错误恢复 + 指标）

**场景**：企业客户管理系统后台，销售提交超额折扣审批单。角色：销售、销售主管、财务。已确认 ST-001..ST-003。

**① 触点成功标准（摘取审批提交步）**：

```
### Step 3: 提交审批单
**用户动作：** 填写折扣幅度与理由，点"提交"
**系统响应：** 表单校验通过 → 提交成功 → 进入审批流
**成功标准：**
- [ ] 表单校验响应 ≤ 200ms
- [ ] 必填项缺失时内联提示并定位到缺失字段
- [ ] 提交后 1s 内进入审批流，用户可见"已提交"状态
- [ ] 无"提交后找不到入口/状态不明"求助（测法：帮助中心该页点击率 < 5%）
```

**② 摩擦→缓解（摘取）**：审批理由必填却无模板 → 销售 3 次不填理由被拦 → 缓解 = 提供理由模板选择 + 保存草稿 → "提交卡点求助率"目标 < 10%。

**③ E1/E2 错误恢复（摘取）**：

| 字段 | E1: 审批理由缺失 | E2: 审批流超时未反馈 |
|---|---|---|
| Trigger | 提交时理由为空且未选模板 | 审批超过 3 个工作日无动静 |
| User Sees | "请填写审批理由"内联提示 | 审批列表显示"超时"标记 + 催办按钮 |
| Recovery Path | 停留在编辑页，草稿保留，选模板后重提 | 一键催办给主管，保留原单不丢 |
| Test | 空理由提交→提示→选模板→提交成功 | 构造 3 天无审批→催办→主管收到提醒→完成审批 |

**④ 旅程指标（整条审批旅程）**：

| 指标 | 口径 | 目标 | 埋点 |
|---|---|---|---|
| 完成时长 | 提交→审批通过 | 中位数 ≤ 24h | submit_ts / approve_ts |
| 各步流失 | 提交步→审批步的流失 | 提交后放弃 < 5% | submit_ok / approve_view 事件 |
| 错误率 | 校验失败次数 ÷ 提交次数 | < 15% | validation_error 事件 |
| 恢复率 | 校验失败后成功提交 ÷ 校验失败总数 | ≥ 90% | validation_error→submit_ok 关联 |

## 7. 工作流程

1. **切矩阵**（journey-matrix-and-mot）确认角色×阶段网格完整。
2. **补成功标准**：对每个触点写 2-4 条可勾选成功标准；不可量化的写测法或标 `待确认`。
3. **列摩擦→缓解**：扫全矩阵标摩擦点，逐条给可量化缓解动作；无法量化的进 Clarify。
4. **登记 E1/E2**：对高风险触点写四段式；恢复路径过"五步完整性"检查，每条带 Test。
5. **定义指标**：对整条旅程定 4 类指标（口径/目标/埋点），写入 user-journey.md 指标章节。
6. **输出**：成功标准并入触点矩阵；E1/E2 进异常路径章节；指标进旅程指标章节。

## 8. 核心硬规则

1. **成功标准必须可验证**：每条勾选项可度量或带测法；"体验好/流程顺"不算标准。
2. **摩擦必有缓解**：每个摩擦点至少 1 个缓解动作且带目标值；无缓解 = 未处理。
3. **异常必走四段式**：E1/E2 必须含 Trigger/User Sees/Recovery Path/Test 四段，缺一段不合格。
4. **恢复不踢人**：错误后必须保留上下文（草稿/会话/回原步），恢复路径过"五步完整性"检查。
5. **指标可埋点**：每类指标写清口径、目标与埋点时机；埋不出的事件不写。
6. **恢复率必须与错误率配对看**：二者同出同入，缺一不算完整指标。

## 9. 边界（Do Not）

- 不把成功标准写成功能方案（→ feature-list）——标准是"结果可验证"，不是"加个按钮"。
- 不替下游写 AC——本文档只提供可勾选判据，`acceptance-criteria` 负责转成 G/W/T。
- 不设计埋点数据结构/事件 schema 细节（→ tracking-plan）——本文档只给指标口径与时机。
- 不为凑指标发明不可埋点的数字——数据不可得时标 `待确认`，不编造基线。
- 不把 E1/E2 写成全功能异常清单——只覆盖旅程相关高风险路径，其他异常归 exception-handling。
- 不在主路径之外无限铺 E——每条约 E 必须能写清 Test，写不清就删。

## 10. 质量自检清单

- [ ] 每个触点的成功标准可勾选且可度量（或带测法），无形容词标准
- [ ] 每个摩擦点有 ≥1 个可量化缓解动作（目标值明确）
- [ ] 高风险异常路径均有 E1/E2 四段式（Trigger/User Sees/Recovery Path/Test）
- [ ] 每条恢复路径满足"五步完整性"且不丢上下文（草稿/会话保留）
- [ ] 4 类旅程指标（完成时长/各步流失/错误率/恢复率）均有口径 + 目标 + 埋点时机
- [ ] 恢复率与错误率成对出现
- [ ] 未把缓解动作写成功能方案；未越界写埋点事件 schema
- [ ] 成功标准/E1/E2 可被 acceptance-criteria 直接消费，无需重新调研
