# 研发评审 7 维度可行性门槛（Review Threshold 7D）

> 来源吸收：`product-solution-evaluator` skill 的 SKILL.md「研发评审版方案的可行性评估门槛」模块，作为 feasibility-analysis 的可选落地能力。
> 定位：当评估对象是 PRD、开发方案、原型或即将进入排期的产品方案时，不能只给"可行/不可行"方向判断——用 7 个维度给出放行/补充后放行/降级试点/暂缓的明确门槛判定。
> 触发：feasibility-analysis 的评估对象进入研发评审准备阶段、或 PRD 需判断"能不能排期"时。**按需加载，不设全局闸门**。

## 1. 输入映射（pm-scaffold 语境）

| 外部 skill 输入 | pm-scaffold 对应产物 | 说明 |
|---|---|---|
| PRD/开发方案/原型 | feasibility-report / 上游 PRD 产物 | 评审对象 |
| 7 维度门槛判定 | feasibility-report §结论（有条件做→放行条件） | 决定放行/补充/试点/暂缓 |
| 风险 P0/P1/P2/P3 | feasibility-report §风险 | 优先级排序 |
| 补齐项 | issue-record 的 Q-XXX | 组件级需求缺失项路由澄清 |

> 本门槛适用于"即将排期"的方案评估；评估对象未达 PRD 级时仍走完整可行性流程。

## 2. 7 维度可行性门槛（搬入自 product-solution-evaluator SKILL.md 研发评审模块）

评估必须至少覆盖以下 7 个维度，每维给出**门槛判定**（达标 / 未达标 / 未覆盖）：

### 维度 1：产品可行性
- 目标是否清楚
- MVP 是否收敛
- 用户路径是否闭环
- 成功指标是否可观测

**门槛判定**：四项全达标才可放行；"目标模糊"或"路径断裂"即未达标。

### 维度 2：技术可行性
- 前端组件是否可实现
- 后端配置、接口是否可实现
- 任务编排、文件处理、权限、状态机、降级策略是否可实现

**门槛判定**：核心机制（状态机/权限/降级）必须给出实现方案；"待定"即未达标。

### 维度 3：数据与埋点可行性
- 事件字段是否足够
- 漏斗是否闭合
- 隐私采集边界是否清楚

**门槛判定**：漏斗闭合 + 采集边界明确才可放行；"不知道要埋什么"即未达标。

### 维度 4：体验可行性
- 首屏复杂度是否可控
- 入口可理解性
- 状态反馈、错误提示
- 用户认知负担

**门槛判定**：首屏/入口/反馈/认知负担四项可控才可放行；有致命认知负担即降级试点。

### 维度 5：研发拆解可行性
- 是否能拆成组件、接口、配置、测试、灰度和回滚任务
- 是否存在跨团队阻塞

**门槛判定**：可拆解 + 无未解跨团队阻塞才可放行；拆不细即未达标。

### 维度 6：风险等级与决策建议
- 按 P0/P1/P2/P3 标注风险
- 给出放行 / 补充后放行 / 降级试点 / 暂缓的明确建议

**门槛判定**：无 P0 风险 + P1 有应对才可放行；存在 P0 即暂缓。

### 维度 7：验收与试点建议
- 提出最小试点范围
- 验收用例
- 观测周期
- 上线后复盘指标

**门槛判定**：试点范围 + 验收用例 + 观测周期 + 复盘指标四项齐备才可放行；缺一即"补充后放行"。

## 3. 决策门槛速查（7 维综合判定）

| 综合判定 | 触发条件 | 动作 |
|---|---|---|
| 放行 | 7 维达标 + 无 P0 + P1 有应对 | 进入排期 |
| 补充后放行 | 存在明确补齐项（如缺验收用例/埋点字段） | 补齐指定项后放行 |
| 降级试点 | 产品/技术方向成立但体验或集成有不确定性 | 缩小试点范围先跑 |
| 暂缓 | 存在 P0 风险或关键维度未达标 | 回到设计/澄清，不排期 |

## 4. 补齐项清单（搬入自 SKILL.md 末句）

若 PRD 未包含以下内容，应列为**研发评审前必须补齐项**：

- 组件级需求
- 状态机
- 埋点字段
- 接口建议
- 验收用例
- 异常降级

## 5. 工作流程

1. **判评估对象**：是 PRD/开发方案/原型/即将排期 → 启用 7 维门槛；否则走完整可行性四维度。
2. **逐维过门槛**：按 7 个维度逐条核对，每维标"达标/未达标/未覆盖"。
3. **列补齐项**：组件级需求/状态机/埋点字段等缺失项登记为必须补齐项。
4. **风险定级**：按 P0/P1/P2/P3 排风险，P0 存在即暂缓。
5. **给决策**：放行/补充后放行/降级试点/暂缓四选一，并附试点范围、验收用例、观测周期、复盘指标。

## 6. 核心硬规则

1. **不许只给"可行/不可行"**：进入排期评估必须过 7 维并给四类决策之一。
2. **状态机与权限必须可达**：技术可行性维度核心机制无实现方案即未达标。
3. **漏斗必须闭合**：数据与埋点维度要求事件字段→漏斗闭合→采集边界三条线。
4. **P0 即暂缓**：存在 P0 风险不得放行，也不得用总分掩盖。
5. **补齐项显式列出**：组件级需求/状态机/埋点/接口/验收/降级缺失即列为评审前必须补齐。
6. **试点建议必带四要素**：试点范围 + 验收用例 + 观测周期 + 复盘指标，缺一不成建议。

## 7. 边界（Do Not）

- 不把实现细节当产品方案评估——实现细节级选择路由给工程。
- 不替代研发做技术设计——只评估"是否可实现/可拆解"。
- 不给无补齐项的"放行"——缺验收用例/埋点字段必须列为补齐项。
- 不忽略异常降级——降级策略是技术可行性维度的必需项。
- 不因方向判断模糊给出"有条件做"却无具体条件——条件必须落到 7 维补齐项。

- [ ] 组件级需求/状态机/埋点字段/接口建议/验收用例/异常降级已核对
- [ ] 风险按 P0/P1/P2/P3 标注，P0 存在已暂缓
- [ ] 决策为放行/补充后放行/降级试点/暂缓四类之一
- [ ] 试点建议含范围+用例+观测周期+复盘指标
- [ ] "有条件做"的条件已落到具体补齐项
