# 两阶段对标与 token 成本门禁（Two-Stage Benchmark & Token Gate）

> 来源吸收：`prd-competitor-check`（v4）的核心修复机制——两阶段对标流程（stage1 原型/设计对标默认执行；stage2 业务逻辑校验须用户明确确认）+ token 成本门禁规则，作为 competitive-research 的可选落地能力。
> 定位：竞品分析的产出天然分"可客观比对的硬信息"与"需业务逻辑推演的软校验"两层，本技法用阶段门禁控制 token 消耗，避免每次对标都全额跑完，同时保证 stage2 的推演结论经人工确认才落定。
> 触发：当竞品对标需同时产出"原型/设计对比"与"业务逻辑合理性校验"两层结论、或对标 PRD 较长需控制成本时使用。**按需加载，不设全局闸门**。

## 1. 输入映射

| 外部 skill 输入 | pm-scaffold 对应产物 | 说明 |
|---|---|---|
| PRD 全文 | competitive-research 的 competitive-analysis.md 草稿 | stage1 对标对象 |
| 竞品信息（平台名：模块名） | competitor-refs-pattern 的竞品参考库条目 | 按模块路由竞品清单 |
| `--check-links` | link-validation 三层降级 | 链接可用性检查（仅 stage1） |
| `--stage2` / 用户显式确认 | Human Gate 人工关卡 | stage2 触发闸门 |
| 第一阶段报告末尾的确认提示 | Clarify 二次确认话术 | 等待用户裁决，不自动继续 |

> **上游未 confirmed 不启动对标**：以 competitive-research 已登记 SRC-ID 的竞品来源为准；缺失竞品标 `待确认`，不编造竞品。

## 2. 两阶段流程与 token 成本门禁

### 2.1 阶段总览

| 阶段 | 内容 | 默认行为 | 预估成本 |
|---|---|---|---|
| **第一阶段：原型/设计对标** | 竞品参考手册与截图说明、百分制打分汇总、优势/短板/差异清单 | **默认执行** | ~2000 token |
| **第二阶段：业务逻辑校验** | 异常分支遗漏、逻辑断层、不符合行业通用设计的业务逻辑 | **默认不执行**，须用户明确确认 | 2000-4000 token（按 PRD 长度） |

### 2.2 默认执行流程（不加 `--stage2`）

```
1. 执行第一阶段（原型/设计对标）
2. 输出第一阶段报告
3. 在报告末尾显示：

---
📋 第一阶段校验完成

是否继续执行第二阶段（文字描述合理性校验）？
- 第二阶段将检查：异常分支遗漏、逻辑断层、不符合行业通用设计的业务逻辑
- 预计消耗 token：约 2000-4000（根据 PRD 长度）

请回复以下任一指令：
- "继续" / "是" / "yes" → 执行第二阶段
- "不用了" / "跳过" / "no" → 结束校验

⏳ 等待用户确认中...（不自动继续）
---
```

### 2.3 强制第二阶段（显式触发）

```
1. 执行第一阶段（原型/设计对标）
2. 立即执行第二阶段（业务逻辑校验）
3. 输出完整报告 → ✅ 两阶段校验全部完成
```

### 2.4 第二阶段校验的四类检查项

| # | 检查项 | 示例问题 | 风险等级 |
|---|---|---|---|
| 1 | **异常处理遗漏** | PRD 未说明网络超时/无权限/数据为空时怎么办 | 🔴/🟡 |
| 2 | **逻辑断层** | 前置条件未定义、主流程步骤缺闭环 | 🔴/🟡 |
| 3 | **权限设计缺失** | 未说明功能的权限控制要求 → 补 RBAC 权限设计 | 🔴 |
| 4 | **状态流转未定义** | 未说明审核失败后的状态流转 → 补状态机定义 | 🟡 |

### 2.5 第二阶段问题输出格式

```markdown
## 🔍 第二阶段：业务逻辑校验报告

### 发现的问题

1. 🔴 **权限设计缺失** [高风险]
   - 描述：PRD 未说明功能的权限控制要求
   - 建议：补充 RBAC 权限设计

2. 🟡 **状态流转未定义** [中风险]
   - 描述：未说明技能审核失败后的状态流转
   - 建议：补充状态机定义

---
✅ 两阶段校验全部完成
```

## 3. token 成本门禁对比

| 场景 | 无门禁（两阶段全跑） | 有门禁（按需 stage2） | 节省 |
|---|---|---|---|
| 仅需要原型对标 | ~5000 token | ~2000 token | **60%** |
| 需要完整校验 | ~5000 token | ~5000 token | 0% |
| 多次迭代调整 PRD | 每次 5000×N | 每轮仅 stage1（2000×N），最终一次 stage2 | **60%** |

> **门禁本质**：把"每次必跑"降为"每轮跑便宜的，贵的一次"——与 pm-scaffold 的迭代式 PRD 生成天然契合：草稿阶段只做原型对标，定稿评审前才做业务逻辑校验。

## 4. 工作流程

1. **路由竞品**：按模块从竞品参考库取竞品清单（可外部配置覆盖）。
2. **跑 stage1**：竞品参考手册与截图说明 → 百分制打分 → 优势/短板/差异清单。
3. **输出确认闸**：报告末尾明确标注"等待用户确认"，不自动继续。
4. **等用户裁决**：用户明确"继续/是/yes"才进入 stage2；否则结束。
5. **跑 stage2**：异常遗漏 / 逻辑断层 / 权限设计 / 状态流转四类检查，输出问题清单（含风险等级与建议）。
6. **收口**：两阶段完成或用户中止后，按 competitive-research 的 Audit / Human Gate 流程收口。

## 5. 核心硬规则

1. **stage2 默认不执行**：没有用户明确确认（回复"继续/是/yes"或等价指令），绝不自动跑业务逻辑校验。
2. **成本透明**：确认话术必须预告 stage2 的预估 token 成本，让用户带信息决策。
3. **输出末尾标注等待**：stage1 报告末尾必须出现"⏳ 等待用户确认中...（不自动继续）"，防止被当成已全部完成。
4. **四类检查不遗漏**：stage2 至少覆盖异常处理遗漏、逻辑断层、权限设计、状态流转四项；缺项视为未完成。
5. **问题必须带风险等级与建议**：每条发现问题标注 🔴/🟡 与修复建议，不空泛列出。
6. **迭代模式用"每轮 stage1 + 末轮 stage2"**：多轮迭代时不要把 stage2 每轮都跑，只在最终评审前跑一次，落实 60% 节省。

## 6. 边界（Do Not）

- 不把 stage2 当默认行为——省 token 是设计目标，不是可选项。
- 不把用户的沉默当确认——未回复 = 未确认 = 停在确认闸。
- 不用 stage2 替代 competitive-research 的 Audit/Human Gate——业务逻辑校验是产出增强，权威判定仍走人工关卡。
- 不替业务方裁决逻辑合理与否——只列问题与建议，决策权在人。
- 不省略"异常处理遗漏"检查——异常分支是 to B PRD 的高频缺口，属必查项。

## 7. 质量自检清单

- [ ] 默认路径只跑了 stage1（原型/设计对标），未擅自进入 stage2
- [ ] stage1 报告末尾有显式确认话术 + token 成本预告
- [ ] 用户明确确认后才执行 stage2（有确认记录）
- [ ] stage2 覆盖四类检查：异常遗漏 / 逻辑断层 / 权限设计 / 状态流转
- [ ] 每条发现带风险等级（🔴/🟡）与具体修复建议
- [ ] 迭代模式中 stage2 只在最终评审前执行一次
- [ ] 竞品缺失标 `待确认`，未编造竞品来源
