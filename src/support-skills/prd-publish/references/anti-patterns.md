# AI 常见反模式 · PRD 发布

> 这些是 AI 在 PRD 发布中最容易犯的错误。PM 审查时遇到以下模式应直接进入 Revision 修改确认。
>
> 注：本文示例已统一使用通用业务场景（内容平台、企业服务等），避免与 `test/skills/` 下的测试夹具业务域（招聘网站、设备预测性维护、客户邀约活动等）同域，防止误导。

## AP1：发布未确认的 PRD
- **表现**：PRD 还是 `draft` / `needs_user_input`，AI 认为"99% 完成了，先发出去同步一下"
- **为什么有害**：未确认内容被当作正式版本分发给下游，研发/测试基于错误内容开工，返工成本极高
- **修复**：Preflight 校验 `confirmed` + 有效 ReviewRecord + hash；不满足则 STOP 回流 prd-assembly

## AP2：发布时"顺手改个错别字"
- **表现**：导出过程中修正一个 typo 或"优化"一句表述
- **为什么有害**：发布副本从此不再是确认版本，hash 失联，追溯失效；下游以为看到的就是确认内容
- **修复**：任何内容变更都走 change-management / Reflow，发布操作只允许格式适配

## AP3：信任导出工具，不做目的地验证
- **表现**：导出工具报"成功"，AI 直接宣布发布完成，未检查目的地副本
- **为什么有害**：飞书/PDF/HTML 转换常有丢表、断页、图不渲染的问题，未验证的"成功"等于没发布
- **修复**：对每个渠道做目的地保真核查（标题/章节/表格/图/追溯矩阵/元数据/无漂移）

## AP4：把格式适配做成内容改写
- **表现**：为了让 PDF 排版好看，AI 重新断句、删减章节或改写表头
- **为什么有害**：格式适配是允许的，内容改写是把未确认内容注入交付物
- **修复**：只改字体/分页/布局/链接样式；内容逐字保留

## AP5：AI 自行宣布"已发布"
- **表现**：AI 生成发布记录并标记 published，代替授权发布人签收
- **为什么有害**：发布是有授权语义的治理动作，AI 签收 = 伪造人工授权
- **修复**：发布记录仅到 `ready_for_human_review`，由授权发布人（authorized-reviewers.json）签收

## AP6：发布后内容静默漂移
- **表现**：源 PRD 在发布后被修改，已发布的副本未同步，也无任何变更记录
- **为什么有害**：研发看的是旧副本，业务以为大家看的是同一份，追溯断裂
- **修复**：发布记录留存源 hash 基线；源变更走 change-management，并评估已发布副本是否需重发

## AP7：已知渲染缺陷仍宣称发布成功
- **表现**：飞书 Markdown 的 Mermaid 不渲染，AI 仍记录"已发布，全部通过"
- **为什么有害**：下游拿到的是残缺副本却以为完整，重要流程图缺失
- **修复**：渲染限制必须显式记录在发布记录中，或改用支持该内容的渠道

## AP8：发布记录缺关键字段
- **表现**：publish-record 缺源 hash、验证人、验证时间戳，或渠道链接不可达
- **为什么有害**：发布记录是追溯基线，字段缺失导致后续无法比对、无法定位"哪次发布"
- **修复**：发布记录必须含源 artifact ID + SHA-256、目的地链接、验证人、时间戳、渲染限制
