# 三模式快速分流技法（Mode Dispatch）

> 来源吸收：`prd-generator-cc` skill 的 SKILL.md（快速分流 + 5 类最小信息提取 + 3-7 定向问题 + 质量门禁），作为 brainstorming 的可选落地能力。
> 定位：先判用户真正需要哪种帮助（起草/评审/解释），再决定动作，避免"上来就套模板"或"上来就铺满问题"两种跑偏；用 5 类最小信息判断能不能直接开跑。
> 触发：Preflight 阶段判断任务形态时；或 L0 想法进入发散前需判断是"直接发散"还是"先补关键缺口"时。**按需加载，不设全局闸门**。

## 1. 输入映射（pm-scaffold 语境）

| 外部 skill 输入 | pm-scaffold 对应产物 | 说明 |
|---|---|---|
| 用户意图 | brainstorming 的三路径分类（轻量澄清/标准发散/全景发散） | 分流结果决定发散深度 |
| 5 类最小信息 | Preflight 成熟度评估 | 判断 L0/L1/L2 |
| 定向问题 | Clarify 的 Q-XXX（≤5 per session） | 补齐关键缺口 |
| 质量门禁 | Audit 自检清单 | 输出前兜底 |

> 分流不是"固定套路"，是帮助 AI 判断投入深度——与 brainstorming 的三路径分类（轻量澄清/标准发散/全景发散）互为补充。

## 2. 快速分流表（搬入自 prd-generator-cc 快速分流）

先判断用户真正需要哪种帮助：

| 用户意图 | 默认动作 | 输出 |
|---|---|---|
| 起草 PRD / 发散需求 | 先补关键缺口，再起草/发散 | 问题清单或 Markdown 草稿 / SCN 候选表 |
| 直接出稿 | 立即起草，缺口标 `【推测】` | Markdown 草稿 |
| 评审已有 PRD | 先评审，不默认重写全文 | 评审结论 + 修订建议 |
| 解释方法 | 只讲结构、方法、检查表 | 简明指南 |

**评审模式要点**（用户给已有 PRD/需求片段/截图文字时，先评审再改写）。重点检查：

- 为什么做、为谁做、成功如何衡量
- MVP 做什么、不做什么
- 角色、场景、上下游依赖是否完整
- 需求是否可测试、可验收
- 数据字段、状态流转、唯一性、审计是否明确
- 权限、异常、失败重试、超时、空状态是否覆盖
- 性能、安全、合规、隔离、日志保留是否有明确要求
- 是否存在未决问题且有人负责确认

评审输出格式：① 结论 ② 阻塞问题 ③ 改进建议 ④ 待确认事项

## 3. 5 类最小信息提取（搬入自 prd-generator-cc 默认流程 §1）

从用户输入中提取 5 类最小信息：

| # | 最小信息 | 缺失时的信号 |
|---|---------|-------------|
| 1 | 业务目标 | 不知道"为什么做" |
| 2 | 目标用户/角色 | 不知道"给谁用" |
| 3 | 范围边界 | 不知道"做到哪" |
| 4 | 约束条件 | 不知道"有什么限制" |
| 5 | 成功标准 | 不知道"怎么算成" |

**信息不足时先问，不要直接铺满模板。** 除非用户明确说"直接写一版""先按你的理解出稿"，否则第一轮先提 **3-7 个定向问题**，只问真正缺失的关键项。**最多进行 3 轮问答**；一旦足够起草/发散，就进入产出。

## 4. 质量门禁（搬入自 prd-generator-cc 质量门禁）

输出前快速自检：

- [ ] 是否说清业务目标、用户、边界、约束、成功标准
- [ ] 是否明确"非目标/暂不做"
- [ ] 是否覆盖数据、状态、权限、异常、审计
- [ ] 是否把所有 `【推测】`、`【待补充】` 收拢到待确认事项
- [ ] 高风险领域是否标注 `需专业确认`（税务/法务/隐私/支付/合规）

## 5. 起草时的结构化写法要求（搬入自 prd-generator-cc 默认流程 §3）

至少覆盖 9 部分：背景与业务目标 / 用户角色与使用场景 / MVP 范围与非目标 / 功能需求 / 业务规则与边界条件 / 数据·状态·权限·异常处理 / 非功能要求 / 验收标准 / 待确认事项。

写法要求：

- 需求尽量编号，如 `FR-001`
- 每条核心需求写清触发条件、系统行为、结果状态
- 重要假设标 `【推测】`
- 缺失项进入"待确认事项"，不要静默补造
- 需求描述"做什么"，避免写成具体实现方案

## 6. 工作流程

1. **判意图**：用快速分流表确认用户要起草/直接出稿/评审/解释。
2. **提最小信息**：提取 5 类最小信息，标记缺失项。
3. **定向补问**：缺失关键项 → 3-7 个定向问题（最多 3 轮）；直接出稿指令 → 跳过补问。
4. **产出**：起草（9 部分结构）或评审（结论/阻塞/建议/待确认）或发散（SCN 候选表）。
5. **跑门禁**：按质量门禁 5 项自检，`【推测】`/`【待补充】` 收拢待确认。

## 7. 核心硬规则

1. **先分流再动手**：不判意图就铺模板 = 跑偏；先确认是起草/评审/解释。
2. **缺口先问不硬造**：信息不足先问 3-7 个定向问题，最多 3 轮；直接出稿才允许标 `【推测】`。
3. **最小信息 5 类必查**：业务目标/用户/范围/约束/成功标准缺一即影响产出质量。
4. **假设显式标注**：所有 `【推测】` 收拢到待确认事项，不静默补造。
5. **需求写"做什么"**：不写 API/字段类型/实现方案等具体实现。
6. **高风险标 `需专业确认`**：税务/法务/隐私/支付/合规领域不把推测写成事实。

## 8. 边界（Do Not）

- 不默认重写已有 PRD——评审模式下先给结论与修订建议。
- 不无限追问——最多 3 轮，3 轮后按现有信息产出并标注置信度。
- 不把评审模式当起草模式——对象是已有文档时先评审。
- 不因缺信息就停工——信息不足可产出低置信度初稿，但必须显式标注。
- 不承诺 docx/PDF/调用本地工具链——除非用户明确提出且工具可审计。

## 9. 质量自检清单

- [ ] 已按快速分流表确认用户意图（起草/直接出稿/评审/解释）
- [ ] 5 类最小信息已提取，缺失项有记录
- [ ] 定向问题 3-7 个、最多 3 轮，未无限追问
- [ ] 起草产出覆盖 9 部分结构
- [ ] 评审产出为"结论/阻塞/建议/待确认"四段式
- [ ] 所有 `【推测】`/`【待补充】` 已收拢到待确认事项
- [ ] 高风险领域已标注 `需专业确认`
