# 提问模式 · Brainstorming（发散收敛）

发散阶段的 6 类规范提问模板。每条包含：

- **何时使用** — 触发条件
- **问题句式** — 提示结构
- **示例（脱敏）** — 转述过的通用业务场景案例
- **常见陷阱** — AI 问这类问题时最典型的错误

在 Clarify Session 中生成新问题时以此为参考。运行时规则见 `SKILL.md` § Clarify（≤5 questions/session、按影响排序、每问带 AI 初判 + 选项 + 影响 + owner + blocking）。

---

## 1. 边界澄清（Boundary）

**何时使用**：候选的表层范围不清——"这份想法到底想改变什么"（如只说"做会员活动"，但对象、动作、范围都未知）。

**问题句式**：

```
[为什么重要] 边界不清的发散会产出互不兼容的候选。
这个想法要改变哪个可观察结果?范围到哪、不包含哪?建议初判: [AI 判断]，选项: [A / B / C / 其他]。
```

**示例**：

- "想做的'工单流转'，范围只到'分配与提醒'，还是含'闭环回访'?"
- "'客户邀约'包含赠品发放吗?还是只到邀约成功即止?"
- "这次只做新客邀约，还是老客复访也算?"

**常见陷阱**：

- 替业务方拍板边界
- 把"相邻但不做"的边界当成"要做"写进候选
- 不给互斥选项，逼成开放回答

---

## 2. 目标 / 成功度量（Goal And Success Metric）

**何时使用**：候选发散的方向缺乏预期结果与量化判据，无法判断"纳入后算成功吗"。

**问题句式**：

```
[为什么重要] 没有成功度量，发散后无法收敛到可进入输入包的方向。
目标的预期结果是什么?用什么量化?建议初判: [AI 建议]，选项: [A / B / C / 其他]。
```

**示例**：

- "'提升会员活跃'的判据是月复购率、月登录数还是积分兑换量?"
- "邀约活动的成功标准是到场率，还是报名转化率?"
- "希望把工单平均处理时长从 3 天降到几天?"

**常见陷阱**：

- 用模板字段倒推度量，不尊重真实情境
- 让业务方从零想、不给选项
- 把"过程指标"当成"结果指标"写进候选

---

## 3. 对象范围（Role / Object Scope）

**何时使用**：角色/当事人范围不清——"邀约给谁、谁参与、谁被影响"模糊。

**问题句式**：

```
[为什么重要] 对象范围决定 roles 维度的候选边界。
这个想法涉及的角色/对象范围是?含不含 [角色 X]?建议初判: [AI 判断]，选项: [A / B / C / 其他]。
```

**示例**：

- "参与邀约的'客户'含匿名访客吗?还是仅注册会员?"
- "工单的'处理人'是运营专员，还是也含一线客服 / 门店?"
- "积分活动是否有供应商侧角色（如核销商户）参与?"

**常见陷阱**：

- 把对象的间接参与者（结算、客服）漏掉
- 用统一术语掩盖角色范围差异
- 一次问多个角色范围，难以作答

---

## 4. 时间 / 约束（Time And Constraint）

**何时使用**：deadline、预算、技术、合规等约束会影响候选取舍，但当前缺失。

**问题句式**：

```
[为什么重要] 硬约束无法静默忽略——它直接决定哪些候选现实可行。
[deadline / 预算 / 技术栈 / 合规] 是?这会改变 [哪些候选]。建议初判: [AI 建议]，选项: [A / B / C / 其他]。
```

**示例**：

- "活动的期望上线时间是月底，还是可以放宽到 Q4?"
- "'对接客户积分系统'有无预算上限，决定自建还是采购?"
- "移动端触达是否受合规限制（如短信频率）?"

**常见陷阱**：

- 把 AI 自己脑补的约束当硬约束
- 不注明"这会改变哪个候选"的影响
- 只问时间不问预算/合规，遗漏同型约束

---

## 5. 候选补充确认（Candidate Completeness）

**何时使用**：怀疑某维度有遗漏候选，希望业务方确认是否发散漏了方向。

**问题句式**：

```
[为什么重要] 发散覆盖不全，收敛产物会系统性漏方向。
就 [维度]，我发散出 [候选列表]。是否还有遗漏的方向?建议初判: [AI 认为暂全 / 疑似缺 X]，选项: [补充 X / 已全 / 其他]。
```

**示例**：

- "lifecycle 维度我涵盖了'创建-进行-结束'，是否遗漏了'暂停/归档'阶段?"
- "cancellation 维度有没有'逾期自动作废'这类被我这轮漏掉的候选?"
- "rollback 维度，'积分错发'的回滚边界我没想到，是否要补一条?"

**常见陷阱**：

- 把确认"已全"当成发散完成（仍需人工处置后收敛）
- 让业务方从无到有想维度，不给候选清单参照
- 顺着业务方回答直接加候选却不标 AI_INFERENCE

---

## 6. 处置建议确认（Disposition Recommendation）

**何时使用**：生成完成后、送审前，请业务方对特定候选给出处置方向（include / defer / research），尤其在候选影响大或证据弱时。

**问题句式**：

```
[为什么重要] 处置是业务取舍，AI 只能给初判。
SCN-XXX 我建议 [include / defer / research]，理由 […]。请确认或改判?
```

**示例**：

- "SCN-002「新增门店自助核销」我建议 defer——目前没有明确时间窗，是否同意暂缓?"
- "SCN-005「积分折算差异」证据较弱，我建议 research，登记 issue-record 跟进，可以吗?"
- "SCN-008 我建议 exclude，因为与另一个在建系统重叠，是否同意排除?"

**常见陷阱**：

- 把"推荐"写成"已处置"（处置列只能人填）
- 不给出理由，让业务方无从判断
- 在处置未定时就把它写进输入包

## 跨主题提示（Cross-cutting tips）

0. **一次一问、选择题优先**（吸收自超能力对话启发范式）：**优先一次一问**，题干用选择题（2-4 个互斥选项 + 「其他」）；仅当确有多个独立缺口时才**批量 ≤5 问**。判断题干应用下面的句式模板；务必把开放问法改写成带选项的选择题，别让业务方从零想。
1. **数量上限**：每轮 Session 至多 5 个问题，按 Impact × Uncertainty 排序，先问阻断性高的。
2. **每问必带 AI 初步判断**：不要让业务方从零开始想问题。
3. **三选项常驻**：给 2-4 个互斥选项 + 「其他」兜底。
4. **影响必注**：每个问题说明答案会影响哪个候选或处置；针对 `needs_user_input` 时直接停下等答案。
5. **回写位置必填**：每答一题必须能精确指向 `brainstorming-output.md` 的哪一行（候选表或处置表）。
6. **处置不代填**：AI 给推荐处置，最终 Human Disposition 列只由人工填写。
