# V1 边界定义技法（V1 Boundary）

> 来源吸收：`daedalus-skill` 的 `templates/boundary_template.md` + `rules.md` §4 边界确认规则 + SKILL.md 门槛评估模块，作为 brainstorming 的可选落地能力。
> 定位：在发散收敛后、人工处置前，把"这个版本到底做哪些功能"用三分类边界钉死，防止 V1 功能膨胀；同时用轻量/中等/完整三档门槛把成本预期摆到桌面上。
> 触发：SCN 候选集成形需收敛范围时；处置表里 include 候选超过 3 个需排序时；或 stakeholder 提出新功能需判断是否扩 V1 范围时。**按需加载，不设全局闸门**。

## 1. 输入映射（pm-scaffold 语境）

| 外部 skill 输入 | pm-scaffold 对应产物 | 说明 |
|---|---|---|
| 发散候选 | brainstorming 的 SCN-XXX 候选表 | 边界定义对象 |
| 三分类边界 | include（V1 必须）/ defer（延后）/ exclude（不做） | 与人工四值处置对齐 |
| 门槛路径选择 | 收敛后输入包附注 | 成本/时间预期写入输入包 |
| 边界变更 | issue-record 的 Q-XXX | 新功能触发范围裁决 |

> 边界确认结果直接影响处置表：`include` 候选即 V1 必须有；`defer` 即延后；`exclude` 即明确不做。

## 2. V1 必须功能 ≤3 个 + 边界三分类（搬入自 daedalus boundary_template）

```markdown
**🔲 边界定义**

为了让项目可控，请明确以下三类功能：

1. **当前版本（V1）必须有的功能**（最多 3 个）
   请列出：
   - 
   - 
   - 

2. **可以延后做的功能**（未来版本）
   请列出（可选）：

3. **明确不做的范围**（帮助聚焦）
   请列出（可选）：
```

**数量限制硬规则**：V1 必须功能严格不超过 3 个。用户列出第 4 个时：

> "你列出了 X 个必须功能，但 V1 版本建议不超过 3 个才能快速上线。请按重要性排序，保留最重要的 3 个，其他放入'延后'列表。"

**不做范围的价值**：即使为空也没关系，但建议至少列出 1-2 个"明确不做"的事项，帮助聚焦。

## 3. 边界变更处理（搬入自 daedalus boundary_template 模板版本 2）

当 stakeholder 在后续对话提出新功能且不在当前边界内时：

```markdown
**🔲 边界提醒**

你提到了一个新功能：[用户提出的功能]。

根据之前的边界定义，你当前 V1 版本已有以下必须功能：
- [must_have_1]
- [must_have_2]
- [must_have_3]（如果已有 3 个）

请选择如何处理：
- **A. 替换**：用新功能替换现有的某个 V1 功能（请说明替换哪一个）
- **B. 延后**：将新功能放入"延后列表"，未来版本再做
- **C. 不做**：明确不实现这个功能
```

如果当前 V1 功能不足 3 个，可直接选择 **D. 添加**：将新功能加入 V1 必须功能。

## 4. 边界确认摘要（搬入自 daedalus boundary_template 模板版本 3）

```markdown
**✅ 边界确认摘要**

- **V1 必须功能（不超过 3 个）**：
  1. [功能1]
  2. [功能2]
  3. [功能3]

- **延后功能**：
  - [功能A]（如有）

- **不做范围**：
  - [范围X]（如有）

> 请确认以上边界是否符合你的预期？回复"确认"或提出修改。
```

## 5. 三档门槛评估（搬入自 daedalus SKILL.md 门槛评估模块）

给 stakeholder 明确成本/时间预期，并让其选择路径：

| 档位 | 成本 | 时间 | 形态 | 适用 |
|------|------|------|------|------|
| 1 轻量级验证 | < 500 元 | 几天 | 无后台或纯前端（本地存储、静态地图） | 验证核心假设，MVP 前探 |
| 2 中等完整度 | 几千元 | 几周 | 简单后端（微信小程序云开发、Supabase 免费额度） | 小型工具/小团队可用产品 |
| 3 全功能产品 | 万元以上 | 月固定费用 | 需开发团队或深入学习后端 | 正式商业化产品 |

```markdown
**💰 项目门槛评估**

根据描述，这个产品可能涉及：
- 后端服务器/数据库（如需要用户账号、存储轨迹）
- 地图 API 调用（超过免费额度可能收费）
- 云存储（如图片上传）

**建议你选择一条路径**（回复数字 1、2 或 3）：
1. **轻量级验证**：成本 < 500 元，几天时间，无后台
2. **中等完整度**：成本几千元，几周时间，简单后端
3. **全功能产品**：成本万元以上，月固定费用，需开发团队

请回复 1、2 或 3。
```

选择结果记入 `threshold_choice`，随收敛后输入包写入 project-background-goal，作为非功能约束（成本/时间预期）输入。

## 6. 工作流程

1. **候选成形后问边界**：SCN 候选集聚类去重后，输出边界定义模板，请 stakeholder 填三分类。
2. **限额排序**：V1 必须有超过 3 个时，请 stakeholder 排序保留 3 个，其余转延后。
3. **门槛路径确认**：同步输出三档门槛评估，请 stakeholder 选择路径（轻量/中等/完整）。
4. **输出确认摘要**：三分类边界 + 门槛路径回读确认，标记 boundary_done。
5. **写回输入包**：include 候选 → V1 必须有；门槛路径与成本预期附注写入收敛后输入包。
6. **变更再触发**：新功能超出边界时按边界变更模板走 A/B/C/D 决策。

## 7. 核心硬规则

1. **V1 必须有 ≤3 个**：超限强制排序，不允许第 4 个默认可加入。
2. **三分类缺一不可**：必须有/延后/不做三类都要让 stakeholder 表态（不做可空，但建议至少 1-2 项）。
3. **门槛路径必须显式**：成本/时间预期在发散收敛阶段就摆明，不隐藏。
4. **变更必须裁决**：新功能进 V1 必须替换、延后或不做，不允许静默扩范围。
5. **边界只由人定**：AI 只排序和提示，include/exclude/defer 由 business_owner 拍板。
6. **确认摘要留痕**：每次边界定义或变更后输出确认摘要，防范围漂移。

## 8. 边界（Do Not）

- 不替 stakeholder 决定哪些功能进 V1——只做排序提示。
- 不超过 3 个还继续加——超限即触发替换/延后流程。
- 不把"延后"静默丢掉——延后功能记录在案，进需求池或未来版本规划。
- 不用技术黑话问边界——用"这个版本必须有/延后/不做"的业务语言。
- 不在 V1 范围内塞性能/合规/迁移等非功能约束——它们进门槛评估与可行性分析。

## 9. 质量自检清单

- [ ] V1 必须有功能 ≤3 个，超限已触发排序流程
- [ ] 三分类（必须有/延后/不做）均有 stakeholder 表态
- [ ] 门槛路径（轻量/中等/完整）已选择并附注输入包
- [ ] 边界确认摘要已回读并留痕
- [ ] 新功能变更走 A/B/C/D 决策，无静默扩范围
- [ ] include 候选与 V1 必须功能一致，defer 与延后列表一致
