>
> **类型分支（lite 注释）**：本模板用 HTML 注释标记各节在「迭代」类型下是否可裁剪。
> - 必留节（一句话摘要 / 第一性原理 / 当前现状 / 核心问题与证据 / 目标与成功判断 / 待确认与风险 / 参考资料）无论何种类型都应保留；

## 第一性原理

<!-- 必留 / 迭代必留（迭代类型下压缩为一段：「为什么要加/改 + 不做的代价」） -->

**思想层追问（解决模板填空式思考的根本问题）**：

- **真正要解决的根本问题是什么？**（不是用户描述的表面需求；去掉所有"想做的功能"之后，业务真正卡在哪里？）
- **如果不解决这件事，业务会怎样？**（不做的代价 = 项目存在的根本理由；这条要写得能让 PM 拒绝"为做而做"的项目）
- **为什么是现在做？**（时机论证：触发事件 / 外部约束 / 内部条件；不是"最近有人提了"）
- **核心假设是什么？**（项目成功依赖的 3-5 个关键假设；每条标「待验证 / 已验证 / 已证伪」）
- **问题被解决的标志是什么？**（定性的行为 / 结构 / 关系变化，证明"问题已解"——不是"项目已交付"）

**类型分支写法**：

- **重构**：第一性原理尤其关键——「为什么要重构」必须比「现状有多差」更深。否则容易变成"为重构而重构"或"换皮不换骨"。
- **从 0 到 1**：第一性原理帮助区分"真问题"和"想象中的问题"——避免 solution in search of a problem。如果材料里看不到"不做的代价"，先回到客户访谈再立项。
- **迭代**：压缩为一段——「为什么要加/改 + 不做的代价」，其他追问（核心假设 / 解决标志）不强制；避免对小迭代过度论证。

**护栏 B4**（advisory，不阻断）：若本节五问均无实质回答（每问至少 1-2 句），校验器发 `bg.first_principles_hollow` warning。PM 可在 Generate 阶段勾选"本项目不适用"绕过（例：纯执行类项目），但需在 governance 记录理由。
