## 1. 优化一：事件溯源 + 派生视图（dsh 最核心，优先级最高）

### 1.1 dsh 的做法

dsh 的 Session 是 append-only 的 `SessionEvent` 类型化日志，是 agent 全部交互历史的**单一事实来源**。LLM 消息历史是从日志**派生**的，从不单独存储；replay 就是对同一批事件重新派生。每个事件是无损 JSON，序列号连续。核心不变式：**模型可见 ⟺ 已记录**，运行时断言 [$TRAE_REF](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/session.md)。

### 1.2 我们缺什么

现在 `pipeline.py` 的每次 gate/review/change 结果**即时打印不落盘**，review/change 记录是分散的 markdown 文件，校验是"读文件再校验"，没有统一的 append-only 事件日志。这意味着：
- 无法回答"这个案例的完整运行轨迹是什么"
- 无法 replay 某次 gate 决策
- 无法审计"AI 看到了什么、依据什么生成了产物"

### 1.3 落地设计

新增 `src/scripts/audit_log.py` + 每案例 `requirements/REQ-NNN-*/.audit/events.jsonl`（append-only）：

```jsonl
{"event_type":"init","seq":1,"recorded_at":"...","prev_hash":"000...0","payload":{"work_item":"function-description","req_dir":"REQ-001"},"payload_sha256":"...","event_sha256":"..."}
{"event_type":"review","seq":2,"recorded_at":"...","prev_hash":"<seq1.event_sha256>","payload":{"work_item":"function-description","decision":"approve","reviewer":"张三","record":"review-function-description-2026-08-14.md"},"payload_sha256":"...","event_sha256":"..."}
{"event_type":"change","seq":3,"recorded_at":"...","prev_hash":"<seq2.event_sha256>","payload":{"work_item":"product-ux","from":"confirmed","to":"draft","reason":"范围调整"},"payload_sha256":"...","event_sha256":"..."}
{"event_type":"confirm","seq":4,"recorded_at":"...","prev_hash":"<seq3.event_sha256>","payload":{"work_item":"function-description","from":"ready_for_human_review","to":"confirmed"},"payload_sha256":"...","event_sha256":"..."}
{"event_type":"reflow","seq":5,"recorded_at":"...","prev_hash":"<seq4.event_sha256>","payload":{"work_item":"product-ux","from":"confirmed","to":"superseded","reason":"上游变更级联失效"},"payload_sha256":"...","event_sha256":"..."}
```

**事件类型 token**（与 `audit_log.py` 的 `EVENT_TYPE_TOKENS = {"review", "change", "decision", "confirm", "reject", "reflow", "init"}` 严格对齐，未知 token 拒绝重建会话）：
- `init` — 会话/案例初始化
- `review` — 评审留痕（含 decision / reviewer / record 路径）
- `change` — 变更留痕（含 from / to / reason）
- `confirm` — 状态跃迁到 confirmed
- `reject` — 状态跃迁到 reject
- `reflow` — 级联失效（superseded）
- `decision` — 显式决策事件（FACT/DECISION 落库）

**关键设计（搬运 dsh）**：
1. **事件是单一事实来源**：review/change 记录仍写 markdown（人类可读），但**机器校验一律从 `.audit/events.jsonl` 派生**，不单独读 markdown。这样日志和产物永不漂移。
2. **未知事件类型默认拒绝**：调用方传入 `EVENT_TYPE_TOKENS` 外的 token，`append_event` 直接 raise；`verify_chain` 同样拒绝重建。对应 dsh 的「ignorable 标记」哲学——纯信息性事件不静默跳过 [$TRAE_REF](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/session.md)。
3. **prev_hash 链 + event_sha256 自指纹 + payload_sha256 绑定记录体**：`seq` 连续只是浅校验，真正的防篡改靠三层 hash——删一行/改任一字段（含 prev_hash、recorded_at、payload）都会断链或自指纹不符，被 `verify_chain` 捕获。
4. **单调 recorded_at**：同 session 内每个新事件 `recorded_at >= 上一个事件.recorded_at`（1s clock skew 容差），防止子进程乱序写入。
5. **幂等写入**：同 `(event_type, payload, payload_sha256)` 三元组重复调用 `append_event` 不重复落行（对齐 `hash_anchor.record_anchor` 的幂等契约）。

### 1.4 涉及文件

|---|---|
| `src/scripts/audit_log.py` | **新增（已落地）**：append-only 事件日志 + `EVENT_TYPE_TOKENS` 校验 + prev_hash 链 + event_sha256 自指纹 + payload_sha256 绑定记录体 |

## 2. 优化二：统一校验器契约（Capability Seam 三角色）

### 2.1 dsh 的做法

dsh 的 Capability Seam 由三个角色构成：**Service Definition**（声明接口）、**Service Provider**（实现接口）、**Consumer**（使用接口，通常是模型面对的工具）。"增加一个能力 = 设计全部三个角色"。换一个 provider 就改变整个产品，无需改流水线 [$TRAE_REF](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/capability-seams.md)。

### 2.2 我们缺什么

现在 17 个 `validate_artifact.py` 各自独立，输入输出约定靠惯例，没有统一契约。`pipeline.py` 里 `run_script_json` / `run_json` / `run_property_check` 三个函数分别调用不同脚本，返回结构靠各脚本自觉。新增一个 skill 就要"另写一套校验器"，无法替换、无法组合。

### 2.3 落地设计

定义统一校验器契约（`src/framework/validator-contract.md` + `src/scripts/validator_runner.py`）：

```python
# validator_runner.py — 统一校验器入口
# 每个校验器必须实现：
#   validate(path) -> {"ok": bool, "errors": [...], "warnings": [...], "issues": [...]}
#   issues 每项: {"code": str, "severity": "blocking"|"waiver_required"|"advisory", "message": str, "waivable": bool}
```

**三角色映射**：
| 角色 | 脚手架对应 | 说明 |
|---|---|---|
| Service Definition | `validator-contract.md` | 声明校验器接口（入参/出参/错误码/waivable 语义） |
| Service Provider | 各 `validate_artifact.py` | 实现接口，可替换 |
| Consumer | `pipeline.py` / `validator_runner.py` | 统一调用，不关心具体实现 |

**落地步骤**：
1. 写 `validator-contract.md` 定义统一契约
2. 写 `validator_runner.py` 统一调用（替代 `run_script_json`/`run_json`/`run_property_check` 三个函数）
3. 17 个校验器逐一适配契约（统一返回 `issues` 结构，统一 `--json` 输出）
4. `pipeline.py` 改用 `validator_runner` 调用，删除三个重复函数

### 2.4 涉及文件

| 文件 | 改动 |
|---|---|
| `src/framework/validator-contract.md` | **新增**：校验器接口契约（**未落地**） |
| `src/scripts/validator_runner.py` | **新增**：统一校验器入口（**未落地**） |
| `src/scripts/validation_errors.py` | **新增（已落地）**：`make_issue` 8+ 字段统一错误格式 + `format_issue` + `aggregate_by_check_id` + `wrap_unexpected` |
| 17 个 `validate_artifact.py` | 适配统一契约（**部分落地**：`property_check.py` 已迁移到 `make_issue`，其余 16 个待办） |
| `src/scripts/pipeline.py` | 改用 validator_runner，删除重复函数（**未落地**） |
| `src/scripts/branch_validator.py` | 适配契约（**未落地**） |

> **落地状态（部分落地）**：本优化先落地了「错误格式统一」这一子目标（`validation_errors.py` + `property_check.py` 迁移）；统一调用入口 `validator_runner.py` 与 17 校验器全量适配未完成。后续接线在 §6 第 3 步推进。

### 2.5 验收

## 3. 优化三：配置分层 + Fail Loud（Misconfiguration fails loud）

### 3.1 dsh 的做法

dsh 的配置是 Profile/Bundle 分层组合：bundle 列表 → profile patch → home patch → CLI overlay，`--dump-config` 可审计实际生效配置。核心原则：**配置错误在加载时大声失败，绝不静默跳过缺失引用**。`installFailLoud` 把未处理的 boot rejection 变成 stderr + exit(1)；`assertEntriesLoaded` 对 enabled 但无实现的条目 throw [$TRAE_REF](https://github.com/deepseek-ai/deepseek-harness/blob/master/AGENTS.md)[$TRAE_REF](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/boot/app-boot/README.md)。

### 3.2 我们缺什么

现在 `workflow-registry.json` 是单一 JSON，`workflow_registry.py` 只校验 `schema_version`，不校验引用完整性。如果 registry 里某个 `skill_path` 写错、某个 `artifact_dir` 不存在、某个校验器缺失，**不会报错**，直到跑 gate 时才可能暴露。`pipeline.py` 的 `--work-item` 用了 `choices=[item["id"] for item in work_items()]`，但 registry 本身没有自检。

### 3.3 落地设计

**新增 `src/scripts/registry_contract_check.py`**（脚手架自检，对应 dsh 的 `assertEntriesLoaded`）：

```bash
python3 src/scripts/registry_contract_check.py   # 退出码 0=OK, 1=配置错误；run_tests_mac.sh 首项
```

自检项（全部 fail loud，不静默跳过）：
1. **registry 完整性**：每个 work_item 的 `skill_path` 目录存在、`artifact_dir` 在 registry 中唯一、`artifact_prefix` 唯一（**已落地**）
2. **校验器存在性**：每个 skill 的 `validate_artifact.py` 存在且可执行（**已落地**）
3. **模板存在性**：每个 skill 引用的模板文件存在（**已落地**）
4. **引用完整性**：`predecessors` / `depends_on` / `parent_work_item` 引用的 id 都存在（**已落地**）
5. **模板↔校验器字段闭环（E3_drift）**：模板声明 required 字段而校验器未引用即报错（**已落地**，本脚本的差异化能力）
6. **状态枚举单源**：所有 `VALID_STATUSES` 从 `src/framework/state-machine.md` 派生，消除三处漂移（对应 B14，**未落地**）
7. **schema_version 兼容**：registry schema 升级有迁移路径（**部分落地**：仅校验当前 schema 形状）

**配置分层（对应 dsh Profile/Bundle）**：
- 支持 `src/framework/workflow-registry.override.json`（项目级覆盖层），与主 registry 合并（**未落地**）
- 合并规则：按 id 整行替换（对应 dsh patch 语义），无深合并
- 覆盖层配置错误同样 fail loud

### 3.4 涉及文件

| 文件 | 改动 |
|---|---|
| `src/scripts/registry_contract_check.py` | **新增（已落地）**：脚手架自检（schema + 模板↔校验器闭环 E3_drift + 引用完整性） |
| `src/framework/workflow-registry.json` | 支持 override 层（**未落地**） |
| `src/scripts/workflow_registry.py` | 增加引用完整性校验 + override 合并（**部分落地**：schema 校验交由 `registry_contract_check.py` 承担；override 合并未落地） |
| `src/framework/state-machine.md` | 状态枚举单源化（**未落地**，对应 B14） |
| 各校验器 | VALID_STATUSES 改为 import 单源（**未落地**） |
| `run_tests_mac.sh` | 新增自检测试用例（**已落地**：`registry_contract_check.py` 作为 Phase 0 首项 fail-loud） |

## 4. 优化四：快照回归（Snapshot replay）

### 4.1 dsh 的做法

dsh 用 keyless snapshot 做回归：重放录制会话，diff 归一化输出，CI 强制只读 `DSH_SNAPSHOT=replay`，绝不写期望输出。核心原则：**验证世界而非自报**（e2e 断言外部重跑命令或重读文件）[$TRAE_REF](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/testing.md)。

### 4.2 我们缺什么

现在 79 个测试都是"断言式"，没有"把已跑通的案例产物作为基线快照"。校验器行为悄悄变松（比如某个校验器从 blocking 降为 advisory）不会被发现。`snapshot_cases.py` 已有雏形但未接测试。

### 4.3 落地设计

**把已 confirmed 的案例产物作为基线快照**：

1. 用 `snapshot_cases.py` 生成基线快照（`test/snapshots/` 目录）
2. 回归时重放校验器比对快照，diff 即失败
3. 校验器行为变化必须显式更新快照（`--refresh` 模式），防止悄悄变松
4. **验证世界而非自报**：e2e 断言外部重跑校验器命令的结果，而非校验器自报

### 4.4 涉及文件

| 文件 | 改动 |
|---|---|
| `src/scripts/snapshot_cases.py` | 扩展为基线快照生成 + 比对 |
| `test/snapshots/` | **新增**：基线快照目录 |
| `run_tests_mac.sh` | 新增 snapshot 回归步骤 |
| 各校验器 | 保证快照可重放（确定性输出） |

### 4.5 验收

- 回归含 snapshot 比对步骤
- 故意放宽一个校验器，snapshot 回归失败
- 快照更新必须显式 `--refresh`，CI 只读

## 5. 优化五：Registrations are effects（注册即效果）

### 5.1 dsh 的做法

dsh 的每个注册都通过 `ctx.effect()` / `ctx.on()` 进行，返回 disposer（卸载函数），reload 和 teardown 时按注册逆序撤销。HMR 事务性重组 [$TRAE_REF](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/cordis-primer.md)。

### 5.2 我们缺什么

现在脚手架是静态注册：workflow-registry.json 写死，校验器写死，没有"动态挂载/卸载能力"的概念。新增/移除一个 skill 需要手工改 registry + 改 pipeline + 改测试。

### 5.3 落地设计

把 registry 从"静态 JSON"升级为"可组合注册表"：
- 每个 skill 自带 `manifest.json`（声明：id、name、artifact_dir、artifact_prefix、校验器路径、模板路径、依赖）
- `workflow_registry.py` 扫描 `src/stages/*/skills/*/manifest.json` 自动组装 registry
- 新增 skill = 新建目录 + manifest.json，无需改主 registry
- 移除 skill = 删除目录，注册表自动消失
- 依赖冲突（两个 skill 声明同一 artifact_dir）fail loud

### 5.4 涉及文件

| 文件 | 改动 |
|---|---|
| 各 skill 的 `manifest.json` | **新增**：skill 自描述 |
| `src/scripts/workflow_registry.py` | 改为扫描 manifest 组装 registry |
| `src/framework/workflow-registry.json` | 降级为"默认基线 + 覆盖层"，不再手写全量 |
| `src/scripts/registry_selfcheck.py` | 校验 manifest 完整性 |

### 5.5 验收

- 新增一个测试 skill（manifest.json + 校验器），registry 自动识别，pipeline 可用
- 删除该 skill，registry 自动消失，无残留
- 依赖冲突被自检捕获
