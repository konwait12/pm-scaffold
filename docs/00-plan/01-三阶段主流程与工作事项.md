# 三阶段主流程与工作事项

## 1. 主流程

```text
原始需求与已有材料
→ 001 业务需求阶段
  → 项目背景与目标
  → 用户旅程与用户故事
→ 002 产品需求阶段
  → 产品 UX
  → 功能描述
→ 003 PRD 汇总阶段
  → PRD 汇总
→ 人工最终确认的 prd.md
```

每个 Work Item 都执行 AI 自审和人工停点。阶段不是额外 Skill；完成该阶段最后一个 Work Item 且满足退出条件，即完成阶段。

## 2. 001 业务需求阶段

**目标**：脱离页面和技术方案，先讲清为什么做、谁参与、业务如何发生以及希望改变什么。

**进入条件**：存在可登记来源的原始需求；能识别需求提出方或事实责任人。信息不足可以进入澄清状态，但不能伪造事实。

| 顺序 | Work Item / Skill | 必出物 |
|---|---|---|
| 1 | `project-background-goal` | 项目背景与目标基线 |
| 2 | `user-journey-and-stories` | 用户旅程地图、用户故事集 |

内部顺序固定为：识别生命周期和角色 → 形成旅程骨架 → 填充已知事实 → 角色代入和场景发散 → 业务筛选 → 从旅程提炼故事 → 双向校验。

**条件能力**：业务竞品调研、业务方案对比。

**禁止事项**：提前设计页面、字段、接口或技术架构；把候选场景写成已确认需求。

**退出条件**：背景、目标、核心角色、业务生命周期、旅程和用户故事均经业务责任人确认；未决问题已明确责任人和影响。

## 3. 002 产品需求阶段

**目标**：把已确认的业务需求转成明确的产品范围、系统功能、使用路径和可实现的功能规则。

**进入条件**：业务需求阶段已确认；至少存在一个可追溯的用户故事。

| 顺序 | Work Item / Skill | 必出物 |
|---|---|---|
| 1 | `product-ux` | 引用已确认范围基线；按三阶段产出：功能结构（Scope）、UX 流程与交互规则（Structural）、页面与原型（Framework） |
| 2 | `function-description` | 分功能描述、业务规则、权限、校验、状态、异常恢复和验收依据，并引用上游交互规则 |

`product-ux` 负责 WHAT 和页面层体验，内部按产品设计三层推进：**功能结构（Scope）** 先理清"有哪些功能"，**UX 流程与交互规则（Structural）** 定义用户怎么操作、系统怎么反应，**页面与原型（Framework）** 定义长什么样并把原型作为 UX 的落地产物（UX 与原型一体）。它不能自行改变业务范围；发现范围变化时必须回流。`function-description` 负责领域行为（FR）：消费已确认的 UX，引用 `IX`，定义 `BR`、`VL`、权限、状态变化、失败恢复和 `AC`。

**条件能力**：功能竞品调研、多方案比较、可行性分析；字段规则和埋点作为功能描述的条件章节。

**禁止事项**：UX 擅自新增无法追溯的功能；以原型代替规则；功能描述编写测试用例或技术实现方案。

**退出条件**：每个 P0 功能能追溯到故事，主支流程和关键状态完整，规则可由开发理解、由测试据此设计验证，并经产品及必要协作角色确认。

## 4. 003 PRD 汇总阶段

**目标**：把前两阶段的正式基线组合成唯一、一致、可沟通和可核验的 `prd.md`。

**进入条件**：前四个 Work Item 已确认；不存在阻断汇总的范围冲突。

| Work Item / Skill | 必出物 |
|---|---|
| `prd-assembly` | `prd.md`、追溯审查结果、最终变更摘要 |

汇总只允许编排、消歧和暴露冲突，不允许新增需求。正向检查目标到故事、功能和验收依据；反向检查每个功能、规则和验收依据都有合法来源。

**退出条件**：结构、追溯、一致性和未决风险检查通过，并由授权人工最终确认。

## 5. 正式产出物清单与关系

主流程共有 **10 类细粒度正式产出物**，由 5 个 Work Item 写入 5 份阶段文件。这里的“产出物”是进入 PRD 基线的业务或产品内容，不把提问记录、调研记录、审查报告、评审记录和回流记录混入同一层级；后者是证明过程受控的过程记录。同一文件可承载多类产出物，但每类仍有独立依赖和追溯关系。

| # | 正式产出物 | 生产 Work Item | 直接依据 | 在最终 PRD 中的作用 |
|---|---|---|---|---|
| 1 | 项目背景与目标基线 | `project-background-goal` | 原始需求、来源证据、业务确认 | 定义为什么做、现状、问题、目标、角色、约束和初步边界 |
| 2 | 用户旅程地图 | `user-journey-and-stories` | 已确认背景与目标 | 定义业务生命周期、角色行为、场景路径、交接与恢复 |
| 3 | 用户故事集 | `user-journey-and-stories` | 已确认旅程条目 | 把被业务选择的旅程需要转为可追溯需求 |
| 4 | 项目范围基线 | `user-journey-and-stories` | 背景目标、旅程和故事、业务决策 | 锁定 In Scope、Out of Scope、假设和依赖，供产品阶段引用 |
| 5 | 功能清单 | `product-ux`（Scope） | 范围基线、用户故事 | 将故事映射为模块和 `FEA-XXX`，约束后续设计范围 |
| 6 | UX/功能流程 | `product-ux`（Structural） | 功能清单、用户旅程 | 定义入口、状态、主支路径及跨系统交接 |
| 7 | 页面层交互规则 | `product-ux`（Structural） | UX/功能流程 | 形成 `IX-XXX`，定义操作反馈、跳转、弹窗和表单交互 |
| 8 | 页面与原型 | `product-ux`（Framework） | UX 流程与交互规则 | 定义页面骨架、步骤、前置条件、操作与下一状态；原型是 UX 的落地产物（UX 与原型一体） |
| 9 | 功能描述与规则集 | `function-description` | 功能清单、UX/功能流程、IX | 形成 `FUN` 并引用 `IX`，定义 `BR`、`VL`、权限、状态、异常恢复和 `AC` |
| 10 | 最终 PRD | `prd-assembly` | 前 9 类已确认基线 | 组合内容、暴露冲突并完成正反向追溯，形成唯一 `prd.md` |

权威依赖关系为：

```text
原始需求与来源证据
→ 项目背景与目标（G）
→ 用户旅程条目
→ 用户故事（ST）
→ 项目范围基线 ─┐
                 ├→ 功能清单（FEA）→ UX/功能流程 → 页面与步骤 → 交互规则（IX）
用户旅程 ────────┘                                      ↓
                                                   功能描述（FUN）
                                                   ├→ 业务规则（BR）
                                                   ├→ 校验规则（VL）
                                                   └→ 验收依据（AC）
                                      ↓
                                  PRD 汇总
                                      ↓
                                    prd.md
```

范围基线约束功能清单；功能清单、UX/功能流程、页面与步骤及 IX 是 `product-ux` 的顺序产出。功能描述消费这些内容但不重复定义 IX。`prd-assembly` 只汇总已确认基线，不在汇总时补需求。机器校验职责分开：产物 Validator 检查文档契约，Traceability Checker 检查显式关系边，共享记录 Validator 检查评审、变更和回流记录。

结构化索引以 `src/framework/workflow-registry.json` 的 `artifact_types` 为准；规范和注册表不一致时必须停止并修正。

## 6. 工作事项人工停点

每个 Work Item 至少有两个停点：阻断事实或方案无法确定时进入 `needs_user_input`；候选产物自审通过后进入 `ready_for_human_review`。只有人工通过后才能形成 `confirmed` 基线并进入下一项。
