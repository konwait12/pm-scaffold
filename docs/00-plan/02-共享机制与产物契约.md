# 共享机制与产物契约

## 1. 通用执行循环

```text
Preflight → Intake → Think → Clarify → Generate
→ Audit → Human Gate → Commit / Reflow
```

- `Preflight`：读取治理规则、阶段上下文和已确认上游。
- `Intake`：登记来源并区分事实、决定、假设、推演、未知和冲突。
- `Think`：按当前 Skill 的领域框架分析，必要时启动支持 Skill。
- `Clarify`：汇总阻断问题、初步判断、依据、选项和影响后暂停询问。
- `Generate`：按模板生成候选，不自行设置确认状态。
- `Audit`：执行完整性、第一性原理、对抗式、逆向和追溯检查。
- `Human Gate`：人工通过、要求修改或暂缓。
- `Commit / Reflow`：通过后形成基线；修改时回到最早受影响环节。

## 2. 知识状态

| 类型 | 含义 | 可否直接进入正式结论 |
|---|---|---|
| `FACT` | 有明确来源的业务事实 | 可以 |
| `DECISION` | 有决策人和时间的选择 | 可以 |
| `ASSUMPTION` | 人工声明的暂定前提 | 必须显式标记 |
| `AI_INFERENCE` | AI 根据证据推演 | 不可伪装成事实 |
| `UNKNOWN` | 尚未取得答案 | 按影响决定是否阻断 |
| `CONFLICT` | 来源或角色意见冲突 | 关键冲突必须停下 |

## 3. 状态与人工确认

允许状态：`draft`、`needs_user_input`、`conditional_review`、`ready_for_human_review`、`confirmed`、`superseded`、`simulated`。

`confirmed` 必须包含 reviewer、reviewed_at 和明确决定记录。AI、自审脚本、`--yes`、示例数据或模拟角色都不能产生该状态。人工拒绝必须保留修改意见，并使当前 Work Item 继续保持未确认状态。

## 4. 最小记录契约

- `SourceRecord`：来源 ID、位置、类型、提供者、时间和适用范围。
- `QuestionRecord`：问题、AI 初判、依据、选项、影响、责任人和回流点。
- `DecisionRecord`：决定、备选项、决策人、理由、时间和影响范围。
- `ReviewRecord`：Work Item、版本、决定、reviewer、问题和时间。
- `ChangeRecord`：新增、修改、删除、原因、来源和下游影响。
- `TraceabilityLink`：源 ID、目标 ID、关系类型和证据位置。

## 5. 正式产物与过程记录

正式产物只有背景目标、用户旅程、用户故事、产品 Scope、功能清单、UX 流程、功能描述和 PRD。来源、问题、调研、方案比较、审查、决定和变更属于过程记录；它们可被引用，但不反向成为主流程节点。

## 6. 共享与支持能力

`shared/` 承载入口判断、材料提取、澄清、头脑风暴、自审、人工闸门、追溯、决定和回流。它们由主 Skill 调用，不提供独立业务入口。

三个支持 Skill：

- `competitive-research`：按业务方案或功能设计模式调研，结论不强制进入 PRD。
- `solution-assessment`：比较多个方案并评估技术、资源、合规和依赖可行性，最终选择由人工完成。
- `prd-publish`：只发布已确认 PRD，不改变内容或确认状态。

图表和原型属于表达工具。除非产物自身要求流程图，否则不得设置“必须先询问是否画图”的全局闸门。
