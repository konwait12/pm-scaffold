# 模板调研参考 · 权威方法论可借鉴点

> 编制日期：2026-08-11
> 调研方式：子智能体对 Volere / BABOK / GitHub Issue / 行业 PRD 模板 / ISO-IEEE 29148 的权威来源调研
> 用途：**后续实际落地 Skill 模板时按需增补**。当前不强制改模板（v0.1 已定稿），本文档作为"待增补清单"沉淀，防止遗忘。

## 一句话结论

可借鉴的"硬货"集中在三层——**结构层**（Volere 26 节与社区 PRD 模板字段）、**语句层**（IEEE 29148 单一需求 9 特性 + INVEST）、**治理层**（BABOK 验收/追踪 + GitHub DoR/DoD）。当前脚手架最缺的是**验收标准、非功能需求、追踪矩阵**三块。

## 五个权威来源的模板/字段发现

### 1. Volere Requirements Specification Template

26 节模板分四组：Project Drivers（Purpose / Stakeholders / Mandated Constraints）→ Project Constraints（Naming & Terminology / Facts & Assumptions）→ Functional（Scope of Work / Business Data Model & Data Dictionary / Scope of Product / Functional Requirements）→ NFR（Look&Feel / Usability / Performance / Operational / Maintainability / Security / Cultural / Legal）→ Project Issues（Open Issues / Off-the-Shelf / Migration / Risks）。

- **Blastoff**：前 8 项检查完毕才进入需求发现，显式 Go/NoGo 决策点
- **Snow Card / Requirements Shell**：每条原子需求带 Description / Rationale / Originator / **Fit Criterion**（量化判据，无判据 = 需求不成立）

### 2. BABOK / IIBA

- **验收标准** = "需求被接受必须满足的条件集"，与 evaluation criteria（方案择优）严格区分
- **追踪矩阵 RTM**：需求 ↔ 来源 / 设计元素 / 测试用例 / 业务目标 四方互链
- **Verification vs Validation 分离**：well-formed（clear/complete/consistent/feasible/testable）vs 解决真实业务问题
- **MoSCoW 优先级**

### 3. GitHub Issue Templates / Feature Spec

- Issue Forms 强制字段：Summary / Problem or Goal / **Acceptance Criteria**（须"二值且可测"）/ Validation or Evidence，禁用空白 issue
- 工程级模板把 AC 分 Functional / Technical / UX / Accessibility / Docs 五类，配 Non-Goals / Mandatory Constraints / Testing Requirements / Operational Handover
- **DoR 与 DoD 分离**（开工前有 AC vs 测试通过+文档更新+UAT）
- Epic > Feature > Story/Enabler > Test 层级；Blocks/Blocked by 依赖字段；Out of Scope 防蔓延

### 4. Google / 行业 PRD 模板（PM 社区共识）

核心 6-8 节：Overview（问题陈述+战略契合）→ Goals & Success Metrics（**主指标 + guardrail 指标**）→ User Stories & Requirements（含 edge cases）→ Design/UX → Technical Considerations → Launch & Rollout（feature flags / 回滚计划）→ Open Questions → Risks。

> ⚠️ "Google 官方模板"无公开一手来源，为 PM 社区共识（Lenny Rachitsky / Marty Cagan / Shreyas Doshi / Amazon PR-FAQ）。

### 5. ISO/IEC/IEEE 29148:2018

- **单一需求 9 特性**：Appropriate / Complete / Conforming / Correct / Feasible / Necessary / Singular / Unambiguous / Verifiable
- 推荐句式：`The [system] shall [verb] [object] [constraint] [condition]`
- 区分 BRS / StRS / SyRS / SRS 四类信息项

## 共识标注

**多源印证（行业共识）**：验收标准须可测、Non-goals/Out of Scope、目标可量化、NFR 分类、追踪矩阵、DoR/DoD、PRD 问题-目标-指标骨架。

**单一来源/需谨慎**：Volere 18-26 节具体列表、GitHub 工程 issue 具体章节（社区实践非官方）、"Google 官方 PRD 模板"（无一手来源）、Given/When/Then 归属（应为 BDD，非 BABOK）。

## 建议落地时机

- **高优先级 3 项**：建议在 `user-journey-and-stories`（user-journey-and-stories）或 `product-ux`（product-ux）启动时，作为模板升级批次加入
- **中低优先级**：遇到真实项目卡点（如范围蔓延、追踪断裂）时按需引入
- 不强制一次性全加——与 2026-08-10 会议"避免过度规划、先核心主流程切入"原则一致
