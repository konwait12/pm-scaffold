# 实施迁移与验证计划

## 1. 实施顺序

1. 收敛计划库并冻结三阶段、五 Work Item 的术语。
2. 建立 `src/stages`、`src/shared`、`src/support-skills` 和注册表。
3. 迁移 Skill、脚本和测试；真实需求目录在首个真实需求进入时按 `requirements/REQ-NNN-*/` 布局创建；提供一个基线周期的旧 Wave 兼容。
4. 依次重构五个 Skill 内部，单项真实验证通过后再推进下一项。

## 2. 迁移规则

- 迁移脚本先 dry-run，输出旧新路径、源哈希和冲突；apply 后输出迁移清单。
- 已有正式产物只移动和修正内部路径，不复制、不重写业务内容。
- `*-zh` 的说明合并到主 Skill README；执行规范只保留一份。
- 旧 `--wave` 映射到 Work Item 并显示弃用信息；新写入只使用阶段目录。
- 真实需求产物按 `requirements/REQ-NNN-*/` 布局；迁移不引入模拟案例，所有确认率仅统计真实需求。

## 3. Skill 优化顺序

`project-background-goal` → `user-journey-and-stories` → `product-ux` → `function-description` → `prd-assembly`。

每项必须完成：边界检查、内部流程统一、模板和审查表修正、单元测试、充分/缺失/冲突输入样例，以及至少一次真实需求人工走查（首个真实需求待定）。

## 4. 验收标准

- 非归档规范中不再把 Wave、产出物或 B1/B2/B3 当业务层级。
- 注册表中的所有阶段、Skill、产物路径和前置依赖都能解析。
- 状态、DoR/DoD、追溯和评审脚本读取注册表，不重复硬编码流程。
- 自动模式、拒绝和追溯失败均不能返回整体成功或产生 `confirmed`。
- UX 与功能描述边界符合计划库定义。
- 旧 CLI 在兼容期可读，新 CLI 和新需求目录成为默认写入路径。

## 5. 当前基线

本次分层迁移完成后标记为结构基线 v3.0。内部 Skill 仍按顺序逐项升级，不因完成目录迁移而宣称全部能力已通过真实验证。
