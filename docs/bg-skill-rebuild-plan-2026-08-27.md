# BG Skill 重做计划（可独立 · 人读纯净 · 类型分支）

> 版本：v1 · 2026-08-27
> 驱动：① 会议评审（俞明宏定：BG 按项目类型分支、验证用原始材料）② 用户方向（skill 可独立使用、产出物人读纯净去机器格式）

## 0. 背景

- **会议（2026-08-27）**：俞明宏要求 BG 必须按项目类型分支写（重构 / 从0到1 / 迭代），且验证须用原始业务材料（PPT 几页 / 口述 / 几步流程），禁用成品需求文档自证。会议原文：[飞书会议文档](https://ccegroup.feishu.cn/docx/MDVkds3yJocDvGxSYCGceULBn8f?from=from_copylink)。本会议也是后续 `user-journey` 重建的直接基线。
- **用户方向（2026-08-27）**：
  - 方向 A：今后所有 skill 都要能**单独拿出来用**，不局限于 pm-scaffold 项目内部循环（registry / pipeline / 下游 artifact / 治理链）。
  - 方向 B：产出物不要"奇奇怪怪的格式"，要**人能全部看懂**。

本计划把 BG skill 作为第一个改造样本，落实以上三条。

## 1. 目标

将 `project-background-goal` 重做为：
1. **独立可运行**的能力单元——不依赖 `pipeline.py` / `workflow-registry.json` / 下游 artifact 也能单独跑；
2. **产出纯人读文档**——正文无六态表、SRC 矩阵、Constitution PASS/FAIL 表等机器格式；
3. **按项目类型分支**——重构 / 从0到1 / 迭代 三种写法差异明确。

## 2. 设计原则

| 原则 | 含义 |
|---|---|
| P1 可独立 | SKILL + references + 模板 + validate 四件套自包含；可直接对话 / CLI 触发；不隐式依赖 framework / registry / 下游 |
| P2 人读纯净 | reader-facing 正文纯自然语言；六态 / SRC 追溯 / Constitution / ReviewRecord / 哈希锚点等治理数据**外置**，不进正文 |
| P3 类型分支 | 重构 / 从0到1 / 迭代 三种类型，写法维度不同，不统一模板 |

## 3. 当前 vs 目标

| 维度 | 当前（项目内循环 + 机器格式） | 目标（可独立 + 人读纯净 + 类型分支） |
|---|---|---|
| 入口 | 必须走 `pipeline.py` 串联 | 直接对话 / CLI 即可触发，pipeline 为可选编排 |
| 依赖 | 隐式依赖 framework / contracts / constitution | 四件套内聚，思维透镜内联或显式附带 |
| 输入 | 要求上游 artifact / BRD | 吃"原始材料"，自描述契约，禁成品 PRD |
| 正文 | 15 章含六态表 / SRC 矩阵 / Constitution 表 / Clarifications 表 / 质量增强表 / 待确认寄存器 | 纯叙述 + 类型声明，按类型分支写差异 |
| 治理 | 六态 / SRC / Constitution / ReviewRecord 在正文 | 外置 `.governance.md` 或 frontmatter，机器可读不扰人 |
| 类型 | 无类型概念 | 重构 / 0→1 / 迭代 分支 + 类型驱动必填维度 |

## 4. 改造清单

### 4.1 SKILL.md
- 新增 **项目类型判定**步骤（Preflight / Intake）：判定 重构 / 从0到1 / 迭代。
- 新增 **三类型分支提示词**：每种类型侧重维度不同（重构→现状 before/after + 动机量化；0→1→线下执行步骤；迭代→需求级 2 句）。
- 新增 **独立入口**说明：可直接对话或 CLI 触发，独立于 pipeline。
- 强化 **第一性原理发问链**：什么类型？为什么写？分别写什么？
- 新增 **多视角自检**步骤（Audit）：把 BG 丢给另一 AI 当项目组成员，问"你有什么疑问？能理解要做什么吗？"
- 输入策略：明确"原始材料输入、禁用成品需求文档"。

### 4.2 模板 `background-goal.md`（reader-facing 纯净版）
- frontmatter 精简为**人读友好字段**（项目类型、负责人、日期），机器治理字段外置。
- 正文结构（纯叙述）：
  1. 类型声明
  2. 项目背景（业务环境 / 由来 / 为什么现在做）
  3. 当前现状与已有做法
  4. 核心问题与证据
  5. 目标与成功判断（量化写成人话："邀约转化率 47%→60%，12 个月内"）
  6. 角色与干系人
  7. 约束与依赖
  8. 边界与非目标
- 类型分支章节指引（在模板注释 / references 中，不污染正文）：
  - 重构型：必须写"之前现状 → 要改成什么样" + 重构动机（体验差 / 流程长 / 转化率低 量化）
  - 从0到1型：必须写"线下怎么执行、分多少步、具体流程"
  - 迭代小需求：降级为需求级背景目标（为什么加、加了干什么，2 句）
- 删除：六态表、SRC 矩阵、Constitution 表、Clarifications 表、质量增强记录表、待确认问题寄存器、Fit Criterion 提示块。
- 文末加**人读友好「参考资料」列表**（替代 SRC-ID 矩阵）。

### 4.3 治理外置
- 新建 `<artifact>.governance.md`（或 frontmatter 区块）承载：六态登记、SRC 追溯、Constitution 对齐、ReviewRecord、哈希锚点。
- 项目集成时由 adapter 读取，不进 reader-facing 正文。
- 来源可追溯在正文保留为文末「参考资料」列表（人读友好），详情在外置治理层。

### 4.4 `validate_artifact.py`
- 改为校验**外置元数据 / frontmatter**，不再强制正文含机器表。
- 新增**类型分支必填维度校验**：
  - 重构型：缺"现状 before→after"或重构动机量化 → 报错
  - 从0到1型：缺"线下执行步骤" → 报错
  - 迭代型：非需求级 2 句或越写越厚 → 警告
- 可独立运行（不依赖 `pipeline.py` 状态机）。

### 4.5 references
- 新增 `background-by-type.md`：三类型分支写作指引（含 SVP 重构 / DP 从0到1 / 迭代 示例）。
- 保留 `thinking-framework.md`（内联或显式附带，满足 P1 自包含）。
- 新增 `multi-perspective-selfcheck.md`：多视角自检（丢另一 AI 问疑问）操作指引。

## 5. reader-facing 产出物示例（重构型，目标态）

```
# 项目背景与目标

类型：重构

## 项目背景
SVIP 活动预约目前通过 H5 + 服务号完成，主客与协办两种角色。随着活动量增长，现有方式暴露三个硬伤：体验差（预约页跳转 3 次）、流程长（平均 6 分钟完成）、转化率低（仅 47%）。业务方决定重构为一体化小程序。

## 当前现状
- 主客预约：H5 填写 → 服务号确认 → 人工核销
- 协办：EC 系统手动建活动，无自动化
- 现有系统：H5、服务号、EC，三者数据不互通

## 核心问题
预约流程断点多导致弃单；协办侧完全依赖人工，活动搭建耗时 2 人日。

## 目标与成功判断
重构后：预约转化率 47% → 60%（CRM 数据，12 个月）；协办活动搭建 2 人日 → 0.5 人日；预约完成时长 6 分钟 → 2 分钟。

## 角色与干系人
主客（参会客人）、协办（活动方）、运营（看得数）。

## 约束与依赖
依赖统一身份服务；合规：需脱敏手机号。

## 边界与非目标
本期不含直播能力；不含跨境多币种。

参考资料：SVIP 活动预约现状 BRD（业务方 2026-08）、CRM 转化率报表 Q2。
```

## 6. 类型分支写法规则（校验依据）

| 类型 | 必写维度 | 量化要求 | 篇幅 |
|---|---|---|---|
| 重构 | 现状 before → after + 重构动机 | 动机须量化（体验/流程/转化率） | 中 |
| 从0到1 | 线下执行步骤 / 具体流程 | 步骤数、当前做法 | 中 |
| 迭代小需求 | 需求级背景（为什么加、加了干什么） | 无 | 2 句即可 |

## 7. 验证方式

- **独立运行**：不启动 pipeline，直接对话 / CLI 触发 BG，产出 reader-facing 文档。
- **类型案例三连**：SVP 重构案例 / DP 从0到1 案例 / 某迭代小需求案例，各跑一遍。
- **validate 独立跑**：`validate_artifact.py` 检查类型必填维度 + 外置元数据，不依赖 pipeline 状态。
- **人读测试**：拿给非项目成员看，能答"项目是什么 / 做什么 / 为什么做"即通过。
- **多视角自检**：另一 AI 当成员问疑问，无阻断性疑问即通过。
- **双人 review**：你 + 俞明宏 review 定"可用"。

## 8. 实施步骤

3. 外置治理层 + 改 `validate_artifact.py`（类型校验 + 外置元数据，去 pipeline 依赖）。
4. 补三类型案例 fixture（SVP 重构 / DP 从0到1 / 迭代）。
5. 独立跑通三案例 + 人读测试 + 多视角自检 + 双人 review。
6. 沉淀为《可独立 + 人读纯净 skill 设计规范》母模板，推广到其他 skill。

## 9. 风险与红线调和

- **架构红线冲突**：原红线要求六态 / Constitution / ReviewRecord「在产物中」。本计划改为「随产物但外置」——正文纯净，治理数据机器可读。需在集成层确认 adapter 能读取外置治理层。
- **E3_drift 风险**：改造只动**产物表达层**（模板正文 + SKILL 提示词 + validate 逻辑），不碰 `workflow-registry.json` / SKILL 主干 8 步循环 / 模板 frontmatter 校验字段 / AST 校验字段，避免触发漂移。
- **validate 改造**：若现脚本硬编码"正文必须含六态表"，需改为校验外置 `.governance.md`，属 P2 必要改动。

## 10. 推广

BG 作为首个样本跑通后，将其结构抽象为《可独立 + 人读纯净 skill 设计规范》，作为今后所有 skill 的母模板，逐个重做（下一个建议：user-journey / user-stories，按会议渐进式顺序）。
