# Project_001 产品 AI 脚手架 — 项目评判报告

> 评判日期：2026-08-12
> 方法：阅读治理文档（`constitution.md` / `workflow.md` / `contracts.md` / `workflow-registry.json`）、实际执行编排脚本、随机抽样 Skill 与共享机制、运行一致性检查与单元测试，并核实产物目录。
> 结论一句话：**设计成熟度远高于落地成熟度——治理与工程是同类一流水准，但核心交付物（真实 prd.md）为零，且文档宣称的验证案例并不存在。**

---

## 一、项目定位

一个 "PRD-only 产品经理 AI 工作流" 脚手架：把原始需求源逐步转化为经人类确认、可沟通、可实现、可核验的中文 `prd.md`。设计哲学三条硬原则：业务真相由人类拥有、证据与不确定性必须可见、AI 不得伪造人工确认。

---

## 二、评判维度与发现

### 1. 治理与设计 —— 强（约 9/10）
- 宪法六条（`constitution.md`）把"人类拥有业务真相""不确定性可见""AI 不越权确认"落成可执行原则，而非口号。
- 运行契约（`contracts.md`）定义了完整的知识状态机：`FACT / DECISION / ASSUMPTION / AI_INFERENCE / UNKNOWN / CONFLICT`，以及产物状态机：`draft / needs_user_input / conditional_review / ready_for_human_review / confirmed / superseded / simulated`。
- **确认不变量**是亮点：机器检查只能产出候选，不能产出 `confirmed`；真实命名 reviewer 需匹配 `00-input/authorized-reviewers.json`，且每次审查绑定产物版本与 SHA-256。这从机制上封堵了"AI 幻觉冒充人类拍板"这一最大风险。
- `workflow-registry.json`（schema_version 4）作为单一机器可读事实源，含阶段 / 工作项 / 内部能力 / 支持技能 / `artifact_types` 依赖图，避免 AGENTS.md 所禁止的"多处硬编码重复规范"。

### 2. 工程实现 —— 强（约 8/10）
- `src/scripts/pipeline.py`（250 行）真实可用：`status / entry / gate / review / reflow` 五个子命令齐全；`machine_gate()` 串联 DoR + DoD + 跨产物追溯；`review()` 写入 SHA-256 `ReviewRecord`，显式拒绝含 "simulat/模拟/待确认" 的 reviewer，检测越级激活项（`invalid_active_items`），`reflow` 能列出将被 `superseded` 的下游产物。
- Skill 内容充实：抽样的 `project-background-goal/SKILL.md`（102 行）含 8 步思考提示、反模式对照表、稀疏输入降级样例、references 加载表；`product-ux`、`prd-assembly` 同样充实，嵌套的内部能力 Skill（ux-flow / state-machine 等）也有真实 workflow 指令与 `validate_artifact.py`。
- 共享机制（`src/shared/` 下 audit / brainstorming / change-management / clarify / decision-log / human-gate / intake-routing / project-init / traceability）目录均有 README + 模板 + 真实脚本，非空壳。
- 支持技能（competitive-research / solution-assessment / prd-publish）充实，含决策矩阵、敏度分析等。

### 3. 测试与质量门禁 —— 中（约 7/10）
- `consistency_check.py` 实测：`0 errors, 0 warnings, Consistent.`
- 单元测试直接运行全部通过：跨技能集成 5 项、工作流运行时 11 项、5 个主 Skill 校验器各 3 项、2 个支持/子 Skill 校验器各 3 项。
- **隐患**：完整 `run_tests.sh` 在前台运行会挂起（实测 6 分钟无输出后被强制终止）；Explore 子代理报告 43 passed，说明套件本身能通过，但存在某个环节（fixture 循环或某测试阻塞）导致在部分环境下卡死，CI 可用性存疑，需排查。

### 4. 文档与一致性 —— 中偏下（约 7/10）
- `docs/00-plan/` 四篇规范充实，含明确验收标准，层次清晰。
- **脱节问题**：`README.md` 与 `docs/00-plan/03-实施迁移与验证计划.md` 均把 REQ-002（模拟案例）、REQ-004（RSVP 已确认）当作"已验证实例"引用，但全仓 `find -type d -name 'REQ-*'` 结果为空——这两个目录根本不存在。
- 一致性检查有盲区：`consistency_check.py` 只校验 registry↔docs↔Skill 路径，**不检查 `requirements/` 实际内容**，因此"空需求目录"与"引用不存在的 REQ 案例"均未被自动化捕获。恰好踩中了 AGENTS.md 硬规则 9（不允许文档与现实长期脱节）想要防却没防住的点。

### 5. 真实落地 —— 弱（约 2/10，核心硬伤）
- `requirements/` 目录**压根不存在**，全仓无任何 `REQ-*` 需求目录，没有任何一份真正走完流程、由真人确认产出的 `prd.md`。
- 唯一的 `prd.md` 是 `src/templates/stage-3-prd/prd.md`（143 行模板），以及测试夹具中的样例。
- 含义：这套精密治理系统目前是一个"未被真实需求端到端验证过的样板间"。

## 五、结论与建议

**结论**：这是一个方法论与工程质量都相当高、但目前尚未被真实需求验证的"框架就绪型"项目。它的治理设计（尤其是确认不变量与知识状态分离）在 AI 辅助产品工作流里属于稀缺且高水位的能力；工程实现也对得起设计。短板非常集中——没有一份真实产物，且文档把不存在的案例说成已验证。

**建议（按优先级）**：
1. 用一个真实（哪怕很小的内部）需求跑通端到端，生成第一份真实 `REQ-*` 与 `prd.md`，把"验证计划"里的 REQ-002/REQ-004 要么落地、要么删除。
2. 让 `consistency_check.py` 增加一项：仓库应至少存在一份非 `simulated` 的真实需求产物，否则报错——关掉当前盲区。
3. 排查 `run_tests.sh` 挂起根因（疑似某 fixture 循环或某测试阻塞），保证可在 CI 稳定跑完。
4. README 当前状态应明确标注为"框架已就绪，待首个真实需求验证"，避免对外误读为已投产。
