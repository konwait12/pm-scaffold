# 方案修订建议（AI 视角）

> 本节为 AI 对《PM Scaffold 双 Skill 优化方案》的反馈。围绕方案 P0–P2 共 11 项，给出 5 项具体修订（按原文章节定位，附原文引用与建议措辞）与 1 项盲区补遗。所有建议为 advisory 级，不阻断交付。

## 修订 1：P0-1 测试用例集的工作量与方案自相矛盾

**原文引用：**

> P0-1 建原始材料测试用例集 ... 每次改版跑同一组用例，记录差异，形成回归基线 | 两仓库各加 tests/ 目录

**观点：**方案要求"把 DP 案例与 SVIP 案例固化为两个标准用例：原始材料（PPT 导出 / 口述记录 / 会议纪要）+ 预期产出要点清单"。但 DP / SVIP 是真实业务案例，含客户名、订单数据、内部代号；公开仓库的 fixture 直接嵌入原文会触犯会议自身提出的"原始材料测试"边界——一旦仓库对外可见，原始材料原文外泄本身就是泄露。

**建议措辞（替换原文）：**

> P0-1 建原始材料测试用例集（脱敏版）| 用脱敏摘要 + 原始材料外链清单（指向但不嵌入）作为 fixture；仓库只存用例与脱敏摘要，原文材料清单放在 governance 伴随文件的「原始材料来源记录」段或外部受控位置。验收跑测时，由执行人按清单获取原文喂入，CI 不直接拉取。涉及脱敏的两仓库各加 tests/ 目录 + tests/fixtures/SOURCES.md（仅清单不存原文）。

## 修订 2：P0-4 审阅板不该所有产物默认化，应按"是否含可视化阶段"触发

**原文引用：**

> P0-4 HTML 审阅板默认化 | 产品层展开时默认输出 .board.html，不再可选 | user-journey SKILL.md §5 Generate

**观点：**方案一刀切要求所有产物默认输出 board.html。但 BG（项目背景与目标）是纯叙事型产物，没有"阶段 × 角色 × 路径"的可视化骨架，强行加 board 是冗余渲染、拖慢小迭代场景，**与会议"展现形式不倒退"原则自相矛盾**——把一个本可以 5 分钟看清楚的纯文本产物塞进浏览器流程图才是倒退。UJ 才是审阅板的核心场景。

**建议措辞（替换原文）：**

> P0-4 HTML 审阅板默认化（限 UJ）| UJ 默认输出 .board.html；BG 默认仍为 markdown 主文档，**仅当产物含旅程可视化需求时**才生成 board.html。SKILL.md §5 Generate 增加触发判断：UJ → 必出；BG → 仅当「角色 × 阶段 × 路径」任一维度 ≥ 2 项时生成。验收沿用原方案——未参与过程的 PM 只看板子能否复述旅程。

## 修订 3：P0-3 lite 模式不应另出模板，分支写在主模板注释里

**原文引用：**

> 建议模板内用注释标出「迭代类型可裁剪节」，**或另出 background-goal.lite.md**。

**观点：**另出 `background-goal.lite.md` 是工程冗余。同一 skill 两份模板会让 PM 在选用时困惑（"我用的是哪份？"），且两份模板的内容漂移是几乎不可控的长期债务。governance lite 同理。

**建议措辞（限定为单模板）：**

> P0-3 迭代类型轻量化 | 仅维护主模板 `background-goal.md` 与 `background-goal.governance.md` 两份文件；模板内用 HTML 注释 `<!-- type=迭代: 以下节可裁剪 -->` 标识可裁剪节（基础信息、一句话摘要、核心问题与证据、目标与成功判断、待确认），其余节在迭代类型下不强制。governance 模板用同一注释机制标识 lite 字段（仅登记 UNKNOWN 与 CONFLICT，FACT 类主张直接进正文引用）。裁剪判断由 PM 在 Generate 阶段做，校验器对裁剪节仅发 advisory warning，不阻断。

## 修订 4：P1-1 触点形态枚举协议——三层模型而非一团"触点家族"

**原文引用：**

> P1-1 触点形态枚举协议 | 把「枚举 → 呈选项 → PM 选择 → 落 governance」固化为标准子流程，覆盖**通知、分享、登录、支付**等触点家族

**观点：**通知、分享、登录、支付不是同一层级概念。支付不只是触点（它有金额、退款、合规、风控），把它和"短信提醒"并列会让 PM 在枚举选项时困惑——"我选'邮件支付'还是'支付通知'？"

**建议措辞（替换为三层模型）：**

> P1-1 触点 / 渠道 / 交互 三层枚举协议 | 先建三层模型：
> - **触点 (touchpoint)**：用户与系统发生接触的接口——短信 / 邮件 / App 推送 / 站内信 / 服务号消息 / 模板消息 / 公众号
> - **渠道 (channel)**：触点的载体分类——外部 vs 内部；主动推送 vs 被动拉取
> - **交互 (interaction)**：触点承载的动作类型——提醒 / 分享 / 登录 / 支付 / 订阅 / 收藏 / 评价
>
> 枚举子流程：先列交互（用户要做什么）→ 再列触点（用哪个接口）→ 再标注渠道属性（外部/内部、主动/被动）。例如"客人收到预约提醒"→ 交互=提醒 → 触点=短信/邮件/服务号 → 渠道=外部主动。每层独立维护枚举清单 references/{touchpoint,channel,interaction}-catalog.md，三两两组合的覆盖关系由 references/touchpoint-coverage-matrix.md 给出。PM 选定后在 governance 落 `<interaction>-<touchpoint>` 对（如 reminder-sms）作为唯一标识。

## 修订 5：P1-2 入口对比表应是"选定后才生成"的视图，不是默认结构

**原文引用：**

> P1-2 入口对比表 | 产品层展开子块加固定小节：入口 / 步骤数 / 关键差异 / 待确认，**强制呈现同目的不同入口的差异（短信 3 步 vs 邮件 4 步）**

**观点：**方案要求"强制呈现同目的不同入口的差异"。但若 PM 未指定入口列表，AI 怎么知道有哪些入口？"短信 3 步 vs 邮件 4 步"是已经选定的入口集合上的对比结果，不是凭空生成的视图。把对比表写成基础结构会让 AI 自作主张枚举入口，违背"不猜测"原则。

**建议措辞（替换为按需生成的视图）：**

> P1-2 入口对比视图（按需生成）| UJ 模板产品层子块加基础字段「已选入口清单」（PM 显式登记的入口集合），入口对比表作为可选视图——仅当清单中 ≥ 2 个入口同目的不同时生成。生成时 AI 提示 PM「检测到已选 2+ 入口，是否生成对比视图？」由 PM 触发而非自动产出。视图字段：入口 / 步骤数 / 关键差异 / 待确认，与原方案一致。

## 盲区补遗：方案未触及的工程化风险

**1. 跨 skill 版本协同**

方案独立编号 UJ v1.8 / BG v1.3，但 P0-2 用户故事种子、P0-4 审阅板默认化、P1-4 上游主张回链 都涉及 UJ 与 BG 的产出衔接。若 BG 走 lite 模式（裁剪大量节），下游 UJ 引用上游 confirmed 主张时拿不到必要的角色 / 现状信息——lite 链路会丢上下文。建议加版本协同规则：UJ 与 BG 的 minor 版本必须同时演进，pipeline 启动时校验版本对（"UJ v1.x ↔ BG v1.x"）。

**2. 测试用例失败回收策略**

P0-1 要求建回归基线，但未规定失败行为：80% pass / 20% fail 时是阻断交付（fail-fast）、告警（advisory）、还是按阶段拆分（部分可交付）？建议明文：

- 校验类（validate_artifact.py 失败）→ **阻断**
- 内容类（fixture 对照预期要点缺失）→ **告警 + 标注差异**，不阻断
- 性能类（产物行数 / 表格密度等回归）→ **告警 + 趋势图**

**3. lite 模式与下游链路的传导**

P0-3 lite 模式让 BG 产物变薄，但下游 UJ / user-stories / page-design 的产物接口未变——下游可能因上游字段缺失而出现「未知」或「待确认」暴涨。建议在 lite 模式出口处加一份「链路传导检查」：自动比对下游 skill 的必填字段与 BG lite 实际产出，未填字段列入 BG 的「下游依赖清单」，下游 skill 在 Generate 时优先走澄清而非默认推断。
